왜 TCP가 아니라 UDP 패킷부터 만드는가?

이번 Step에서 UDP를 선택한 가장 큰 이유는 구조가 단순하기 때문입니다.
UDP는 TCP처럼 연결을 먼저 맺는 과정이 없습니다. 그래서 송신자가 목적지 IP와 포트, Payload를 정한 뒤 바로 패킷을 만들어 보낼 수 있습니다. 처음 패킷 구조를 볼 때는 이 단순함 덕분에 IP → UDP → Payload 관계를 훨씬 쉽게 확인할 수 있습니다.
비교 항목UDPTCP
연결 설정없음. 바로 전송 가능먼저 연결 설정이 필요함
초기 동작패킷을 만들어 바로 보냄SYN → SYN/ACK → ACK 과정이 먼저 나타남
헤더 구조상대적으로 단순Sequence Number, ACK Number, Flags 등 확인할 항목이 많음
Payload 관찰바로 데이터 중심으로 보기 쉬움연결 제어 패킷과 데이터 패킷을 함께 구분해야 함
이번 Step 적합성매우 적합UDP를 이해한 뒤 다음 단계에서 다루기 좋음

TCP로 하면 무엇이 더 복잡해지는가?

TCP는 데이터를 보내기 전에 먼저 상대방과 연결 상태를 만듭니다. 대표적으로 다음과 같은 3-Way Handshake가 먼저 보입니다.

송신자                수신자
  | ---- SYN --------> |
  | <--- SYN/ACK ----- |
  | ---- ACK --------> |
  |
  | ---- DATA -------> |

즉 TCP로 시작하면 처음부터 SYN, ACK, Sequence Number, Acknowledgment Number 같은 개념까지 같이 등장합니다. 이번 Step의 목적은 우선 내가 만든 데이터가 UDP Payload에 들어가고, 그것이 IP 패킷 안에 들어가 실제로 전송되는 구조를 보는 것이므로 UDP가 더 적합합니다.

UDP라고 해서 중요하지 않은 프로토콜은 아니다

UDP는 단순히 연습용 프로토콜이 아닙니다. DNS 질의, 음성·영상 스트리밍, 온라인 게임, 실시간 통신처럼 연결 설정과 재전송보다 빠른 전달이 더 중요한 상황에서 실제로 많이 사용됩니다. 다만 UDP 자체는 TCP처럼 전달 성공, 순서 보장, 재전송을 책임지지 않습니다. 필요하면 응용 프로그램이 그 기능을 별도로 구현합니다.

이번 Step에서 UDP를 쓰는 이유를 한 줄로 정리하면

TCP보다 구조가 단순해서
IP + UDP + Payload의 관계를 먼저 눈으로 확인하기 좋기 때문이다.

4ubuntu에서 패킷을 기다리기

실행 위치: ubuntu

sudo tcpdump -i eth0 -nn -A udp port 9999
부분뜻옵션/값 해설
sudo관리자 권한으로 실행패킷 캡처는 NIC를 낮은 수준에서 읽기 때문에 일반 사용자 권한으로 제한될 수 있음
tcpdump패킷 캡처 및 분석 도구인터페이스를 지나가는 패킷을 터미널에서 확인
-i eth0eth0 인터페이스에서 캡처-i = interface, eth0 = -i에 전달하는 인터페이스 이름
-nnIP와 포트를 이름으로 변환하지 않고 숫자로 표시첫 번째 -n은 주소 이름 해석을 끄고, 두 번째 n까지 사용하면 포트 서비스명 변환도 끔. 실습에서는 숫자를 그대로 보는 편이 구조 파악에 유리
-AASCII로 표현 가능한 바이트를 문자로 함께 표시대문자 A. Payload의 ORIGINAL DATA 같은 문자열을 눈으로 찾기 쉬움
udpUDP 패킷만옵션이 아니라 tcpdump의 캡처 필터 표현식
port 99999999번 포트 관련 패킷만9999는 port 조건에 전달하는 포트 번호
-A는 “Payload만 깔끔하게 출력”하는 옵션은 아닙니다. 패킷 바이트 중 ASCII로 보이는 부분을 함께 보여주므로 헤더 부분은 점(.)이나 알아보기 어려운 문자로 보일 수 있고, Payload 문자열은 비교적 쉽게 찾을 수 있습니다.

ip -br link
부분뜻
ipLinux 네트워크 조회/설정 명령

linkIP 주소보다 아래 단계인 네트워크 인터페이스(Link Layer) 자체의 상태를 조회
ip -br addr는 “IP 주소 중심”, ip -br link는 “NIC 상태 중심”이라고 구분하면 쉽습니다.

5ubuntu1에서 첫 Python 파일 만들기

실행 위치: ubuntu1

부분뜻

packet_step1.py열거나 새로 만들 파일 이름. .py는 Python 소스 파일 확장자
파일이 없으면 새 파일로 열리고, 이미 있으면 기존 파일을 엽니다.

아래 코드를 입력합니다.

from scapy.all import IP, UDP, Raw, send

DEST_IP = "172.21.128.10"
SOURCE_PORT = 12345
DEST_PORT = 9999
PAYLOAD = b"ORIGINAL DATA"

packet = (
    IP(dst=DEST_IP)
    / UDP(sport=SOURCE_PORT, dport=DEST_PORT)
    / Raw(load=PAYLOAD)
)

send(packet)
DEST_IP 값만 자신의 ubuntu IP로 변경합니다. SOURCE_PORT=12345를 명시한 이유는 tcpdump 결과를 처음 볼 때 출발지 포트가 항상 같게 보여 구조를 이해하기 쉽도록 하기 위해서입니다.

12-1“안녕.”을 보냈을 때 49바이트가 되는 이유

왜 이 계산을 해보는가?
패킷 캡처 화면에서 49 bytes라고 보이면, 그 숫자를 그냥 외우는 것이 아니라 Ethernet → IP → UDP → 실제 데이터가 각각 몇 바이트를 차지하는지 더해서 확인할 수 있어야 합니다. 이번에는 Payload로 안녕.을 보낸 경우를 기준으로 계산합니다.

1. 먼저 “안녕.”은 몇 바이트인가?

화면에서는 안녕.이 3글자로 보이지만, 글자 수와 바이트 수는 항상 같지 않습니다. UTF-8에서 한글 한 글자는 보통 3바이트를 사용하고, 영문 마침표 .은 1바이트를 사용합니다. 

안  → 3바이트
녕  → 3바이트
.   → 1바이트
----------------
합계 → 7바이트

Python에서 직접 확인하려면:

python3 -c 'data="안녕.".encode("utf-8"); print(data); print(len(data))'
부분뜻
python3Python 3 인터프리터 실행
-ccommand. 별도의 .py 파일을 만들지 않고 뒤의 Python 코드를 바로 실행
"안녕."Python 문자열
.encode("utf-8")문자열을 네트워크에서 다루기 좋은 UTF-8 바이트로 변환
len(data)변환된 데이터가 실제로 몇 바이트인지 확인. 결과는 7
Python에서 주의:
영문 ASCII 데이터는 b"ORIGINAL DATA"처럼 바로 bytes 리터럴로 쓸 수 있지만, 한글은 b"안녕."처럼 직접 쓰면 Python에서 오류가 납니다. Scapy 코드에서는 다음처럼 작성하는 것이 안전합니다. 
PAYLOAD = "안녕.".encode("utf-8")

2. 캡처에서 보이는 49바이트를 계층별로 나누기

구성크기무엇이 들어 있는가?
Ethernet Header14바이트목적지 MAC 6 + 출발지 MAC 6 + EtherType 2
IPv4 Header20바이트IPv4 기본 헤더. IP 옵션이 없는 일반적인 경우
UDP Header8바이트출발지 포트, 목적지 포트, UDP Length, Checksum
Payload7바이트안녕.을 UTF-8로 인코딩한 실제 데이터
Ethernet Header   14 bytes
IPv4 Header       20 bytes
UDP Header         8 bytes
Payload            7 bytes
---------------------------
캡처에서 합계       49 bytes
계산:
14 + 20 + 8 + 7 = 49

즉, 캡처 화면에서 보이는 49 bytes는 단순히 “데이터가 49바이트”라는 뜻이 아니라, 여러 계층의 헤더와 실제 Payload가 합쳐진 크기라고 이해해야 합니다.

3. UDP Length와 IP Total Length도 같이 계산해보기

Wireshark를 열면 프레임 전체 크기뿐 아니라 각 계층 내부에도 길이 값이 있습니다. 같은 안녕. 패킷을 기준으로 계산하면 다음과 같습니다. 

Payload                     = 7 bytes

UDP Length
= UDP Header 8 + Payload 7
= 15 bytes

IPv4 Total Length
= IPv4 Header 20 + UDP Length 15
= 35 bytes

캡처된 Ethernet Frame 크기
= Ethernet Header 14 + IPv4 Total Length 35
= 49 bytes
Wireshark에서 볼 항목예상 값계산
User Datagram Protocol → Length15UDP 헤더 8 + 데이터 7
Internet Protocol Version 4 → Total Length35IP 헤더 20 + UDP 전체 15
Frame → Frame length49 bytes로 보일 수 있음Ethernet 헤더 14 + IP 패킷 35

4. 실제로 관찰한 화면과 연결

중요한 실무 보충:
여기서 49 bytes는 tcpdump/Wireshark 같은 캡처 지점에서 보이는 길이로 이해하는 것이 좋습니다. 실제 물리 Ethernet에서는 너무 작은 프레임에 Padding이 붙을 수 있고, NIC가 처리하는 FCS 4바이트도 일반적인 캡처에서는 보이지 않는 경우가 많습니다. 따라서 “물리선 위의 Ethernet 최소 프레임 크기”와 “Wireshark가 보여주는 캡처 길이”는 다를 수 있습니다. 이번 단계에서는 우선 캡처에서 확인한 49바이트 = 14 + 20 + 8 + 7의 계층 구조를 이해하면 됩니다.

5. 이 패킷을 그림처럼 읽기

[ Ethernet Header : 14B ]
        ↓
[ IPv4 Header     : 20B ]
        ↓
[ UDP Header      :  8B ]
        ↓
[ "안녕." UTF-8   :  7B ]

캡처 기준 합계 = 49B
여기서 꼭 연결해야 할 개념
MAC 주소는 Ethernet Header에, IP 주소는 IP Header에, 포트 번호는 UDP Header에, 우리가 직접 작성한 안녕.은 Payload에 들어갑니다.
따라서 패킷 캡처 한 줄에는 지금까지 따로 배웠던 MAC → IP → Port → Data가 실제로 한 번에 들어 있습니다.

18이해도 확인

Q1. IP(dst=DEST_IP)에서 dst는 무엇인가?
destination의 약자이며 목적지 IP를 지정합니다.
Q2. sport와 dport는 각각 무엇인가?
sport = source port, dport = destination port입니다.
Q3. b"ORIGINAL DATA"의 b는 왜 붙였는가?
일반 문자열이 아니라 네트워크 Payload에 넣기 좋은 bytes 값으로 만들기 위해서입니다.
Q4. Scapy 코드의 /는 무엇을 하는가?
Scapy가 네트워크 계층을 결합하도록 별도로 정의한 연산입니다. IP / UDP / Raw 구조를 만듭니다.
Q5. 이번 코드에서 MAC 주소를 직접 입력하지 않은 이유는?
이번 코드는 Scapy의 send()로 3계층 IP 패킷을 보내는 예제이며, 링크 전송에 필요한 2계층 처리는 라우팅/이웃 정보와 함께 처리됩니다.
Q6. ORIGINAL과 MODIFIED 패킷에서 의도적으로 바꾼 부분은?
Raw Payload입니다. IP와 UDP 포트 설정은 그대로 유지합니다.

Step 1에서 확실히 알아야 할 것

IP(dst=...)
    ↓
3계층 목적지

UDP(sport=..., dport=...)
    ↓
4계층 포트

Raw(load=...)
    ↓
실제 Payload

IP / UDP / Raw
    ↓
하나의 패킷으로 결합

send(packet)
    ↓
전송
