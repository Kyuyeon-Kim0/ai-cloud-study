왜 이 작업을 하는가?
패킷의 Payload를 바꾸면 단순히 문자 부분만 바뀌는 것이 아닙니다. Payload 길이가 달라지면 UDP Length와 IP Total Length도 달라질 수 있고, 내용이 달라지면 UDP Checksum도 다시 계산되어야 합니다. 이번 Part는 패킷의 필드들이 서로 독립적이지 않고 연결되어 있다는 것을 확인하는 단계입니다.
이 작업은 실제로 어디에 쓰이는가?
pcap 복사본을 수정하는 방식은 네트워크 분석 도구 테스트, 장애 재현용 샘플 생성, 프로토콜 파서 검증, 개인정보가 포함된 테스트 Payload 치환, 원본/변형 패킷 비교 같은 작업에 활용할 수 있습니다. 중요한 원칙은 원본 캡처는 보존하고 수정본을 별도 파일로 만든다는 것입니다.
원본 pcap을 덮어쓰지 않는 이유
원본은 “실제로 캡처된 당시 상태”를 나타내는 기준 자료입니다. 수정 작업 중 실수가 생기거나 결과를 다시 검증해야 할 때 원본이 필요합니다. 따라서 이번 Part에서도 part5_original.pcap은 읽기만 하고, part5_modified.pcap과 part5_compare.pcap을 새로 만듭니다.

코드 전에 알아둘 개념: pcap · 객체 · 바이트 · 직렬화

pcap은 무엇인가?

pcap은 packet capture 형식의 파일입니다. 네트워크에서 캡처한 패킷의 바이트와 캡처 시간 같은 정보를 저장해 두었다가 tcpdump, Wireshark, Scapy 같은 도구에서 다시 읽을 수 있습니다.

파일 속 패킷과 Python 객체는 같은 것인가?

파일 안에는 패킷이 바이트 형태로 저장되어 있습니다. Scapy의 rdpcap()이 그 바이트를 읽고 Ethernet, IP, UDP, Raw 같은 계층으로 해석해서 Python에서 다룰 수 있는 Packet 객체로 만들어 줍니다.

Scapy Packet 객체
        ↓ 수정
Scapy Packet 객체
        ↓ bytes()
실제 패킷 bytes
        ↓ wrpcap()
새 pcap 파일

직렬화(serialization)란?

Python의 Packet 객체를 실제 저장/전송 가능한 바이트 형태로 바꾸는 과정입니다. 이번 코드의 bytes(modified)가 이 역할을 합니다.

파싱(parsing) 또는 역직렬화는?

반대로 바이트를 읽어 “이 부분은 Ethernet Header, 이 부분은 IP Header, 이 부분은 UDP”처럼 구조화된 객체로 해석하는 과정입니다. rdpcap()과 Ether(bytes(...))에서 이런 일이 일어납니다.

왜 이 개념이 중요한가?
Checksum과 Length는 단순히 화면에 적혀 있는 문자가 아닙니다. Scapy가 Packet 객체를 실제 바이트로 만드는 직렬화 시점에 자동 계산할 수 있는 필드입니다. 그래서 기존 값을 삭제한 뒤 bytes()를 실행하는 과정이 중요합니다.

1원본 UDP 패킷 만들기

이번 Part가 독립적으로 실행될 수 있도록 원본 패킷을 다시 하나 만듭니다.

실행 위치: ubuntu1

nano part5_sender.py

코드

from scapy.all import IP, UDP, Raw, send

DEST_IP = "172.21.128.10"

packet = (
    IP(dst=DEST_IP)
    / UDP(sport=12345, dport=9999)
    / Raw(load=b"ORIGINAL DATA")
)

send(
    packet,
    verbose=False
)

print("ORIGINAL DATA 전송 완료")
DEST_IP는 자신의 ubuntu 실제 IP로 변경합니다.

왜 이 코드를 사용하는가?

pcap에서 수정할 “원본”이 필요하기 때문입니다. 출발지 Port와 목적지 Port를 고정하면 나중에 원본/수정본을 비교하기 쉽습니다.

verbose=False

Scapy의 자세한 전송 메시지를 줄이고 우리가 만든 print() 메시지만 보기 쉽게 합니다.

5rdpcap()으로 pcap 읽기

가장 작은 예제

from scapy.all import rdpcap

packets = rdpcap("part5_original.pcap")

print(packets)

rdpcap는?

read pcap의 의미로 이해하면 됩니다. pcap 파일 안의 패킷들을 Scapy 객체로 읽어옵니다.

packets에는 무엇이 들어가나?

rdpcap()의 결과는 Scapy의 PacketList입니다. 일반 Python 리스트와 완전히 같은 클래스는 아니지만, 순서가 있고 [0], [1]처럼 접근할 수 있는 리스트형 객체입니다. pcap에 여러 패킷이 있으면 여러 Packet 객체가 캡처 순서대로 들어갑니다. 이번 파일은 -c 1로 만들었기 때문에 한 개만 있어야 합니다.

두 종류의 대괄호를 구분
packets[0]은 “PacketList에서 첫 번째 패킷”을 고르는 것이고, packet[Raw]은 “한 패킷 안에서 Raw 계층”을 고르는 Scapy 문법입니다. 모양은 둘 다 [ ]이지만 의미가 다릅니다.

패킷 개수 확인

print(len(packets))

len()

리스트나 bytes 같은 객체의 길이를 구하는 Python 기본 함수입니다. 여기서는 읽은 패킷 개수를 확인합니다.

6첫 패킷 선택과 copy()

original = packets[0]
modified = original.copy()

[0]은 무엇인가?

Python의 순서는 0부터 시작합니다. 

packets[0] → 첫 번째 패킷
packets[1] → 두 번째 패킷

왜 copy()를 사용하는가?

원본 객체 자체를 수정해버리면 원본과 수정본을 같은 프로그램 안에서 비교하기 어렵습니다. 그래서: 

original = 원본 유지
modified = 수정할 복사본
실무에서도 왜 원본을 보존하는가?
패킷 분석, 로그 분석, 포렌식 형태의 작업에서는 원본을 수정하지 않고 복사본에서 작업하는 습관이 중요합니다. 그래야 언제든 원본 상태와 비교할 수 있습니다.

7원하는 Layer가 실제로 있는지 확인

if not modified.haslayer(IP):
    raise ValueError("IP 계층이 없습니다.")

if not modified.haslayer(UDP):
    raise ValueError("UDP 계층이 없습니다.")

왜 바로 modified[Raw]를 수정하지 않는가?

pcap에 예상과 다른 패킷이 들어 있을 수 있기 때문입니다. UDP가 아닌 패킷이나 Payload 없는 패킷을 무조건 수정하려 하면 오류가 납니다. 먼저 구조를 확인하면 오류 원인을 명확하게 알 수 있습니다.

haslayer()

Scapy 패킷 안에 특정 계층이 존재하는지 True/False로 확인합니다.

not

Boolean 값을 반대로 만듭니다. 

True  → not True  → False
False → not False → True

raise ValueError()

조건이 맞지 않을 때 프로그램을 계속 진행하지 않고 명확한 오류 메시지를 발생시킵니다.

8Payload 수정

원본 Payload 확인

print("원본 Payload:", original[Raw].load)

수정

modified[Raw].load = b"MODIFIED OFFLINE DATA"

modified[Raw] 의미

Scapy 패킷에서 Raw 계층을 선택합니다. 여기서 [Raw]는 리스트의 몇 번째 요소를 고르는 것이 아니라 “Raw라는 네트워크 계층을 찾아 달라”는 Scapy의 Packet 접근 방식입니다. 

packets[0]      → PacketList의 첫 번째 패킷
modified[Raw]   → 한 패킷 안의 Raw 계층
modified[UDP]   → 한 패킷 안의 UDP 계층
modified[IP]    → 한 패킷 안의 IP 계층

.load

Raw 계층이 가지고 있는 실제 Payload 바이트입니다.

=

새 bytes 값을 Payload에 저장합니다.

길이 확인

왜 일부러 길이까지 다르게 하는가?
내용만 바뀌면 Checksum 변화는 볼 수 있지만 Length 변화는 보기 어렵습니다. 이번에는 Payload 길이를 13 → 21바이트로 바꿔 UDP Length와 IP Total Length가 함께 변하는 것을 확인합니다.

Ethernet Padding은 왜 확인하는가?

Ethernet은 실제 링크에서 너무 작은 Frame을 보낼 때 최소 크기를 맞추기 위해 뒤쪽에 Padding 바이트가 붙을 수 있습니다. 짧은 UDP 패킷을 실제 NIC에서 캡처한 pcap에는 환경에 따라 Scapy가 그 남는 바이트를 Padding 계층으로 해석할 수 있습니다. 

if modified.haslayer(Padding):
    del modified[Padding]

왜 제거하는가?

기존 Ethernet Frame을 위해 붙었던 Padding은 새 Payload 길이에 맞춰 다시 판단되어야 합니다. 오프라인에서 Payload 길이를 바꾼 뒤 옛 Padding까지 그대로 남기면 “실제 Payload를 늘린 것인지, 기존 Frame의 Padding까지 데이터가 된 것인지” 해석이 꼬일 수 있습니다. 그래서 수정본을 재구성하기 전에 기존 Padding을 제거합니다.

모든 pcap에 Padding 계층이 보이는 것은 아닙니다. NIC, 드라이버, 가상화, 캡처 위치에 따라 Padding이 pcap에 남지 않을 수도 있습니다. 그래서 haslayer(Padding)로 존재할 때만 제거합니다.

9기존 Length와 Checksum 값을 삭제

del modified[IP].len
del modified[IP].chksum
del modified[UDP].len
del modified[UDP].chksum
왜 삭제하는가?
pcap에서 읽은 패킷에는 이미 캡처 당시 계산된 Length와 Checksum 값이 들어 있습니다. Payload만 바꾸고 기존 값을 그대로 두면 새 Payload와 Header 값이 서로 맞지 않는 패킷이 됩니다. 그래서 기존 계산값을 제거하고 Scapy가 다시 계산하도록 합니다.

del 문법

Python에서 객체의 특정 값이나 항목을 삭제할 때 사용합니다.

각 필드가 왜 다시 계산되어야 하나?

필드이유
IP.lenPayload가 길어져 IP 전체 길이가 변함
IP.chksumIP Header의 Total Length 값 등이 달라지면 다시 계산 필요
UDP.lenUDP Payload 길이가 달라졌으므로 UDP 전체 길이 변경
UDP.chksumPayload 내용과 길이가 달라져 다시 계산 필요
IPv4 Header Checksum은 Payload 자체를 직접 계산하지 않지만, 이번에는 Payload 길이가 변하면서 IPv4 Total Length Header 필드도 바뀌므로 IP Header Checksum도 다시 계산해야 합니다.

그 바이트를 다시 Scapy 패킷으로 해석

bytes()는 왜 필요한가?

Scapy Packet 객체는 “구조화된 패킷 설계도”와 비슷합니다. bytes(modified)는 그 설계도를 실제 네트워크 패킷 바이트로 직렬화합니다. 이때 값이 None 또는 삭제된 자동 계산 필드는 Scapy가 현재 Header와 Payload를 기준으로 채울 수 있습니다.

그냥 wrpcap(modified)만 해도 되지 않나?
Scapy는 저장 과정에서도 직렬화를 수행하므로 자동 계산이 일어날 수 있습니다. 하지만 이번에는 저장하기 전에 재계산된 Length와 Checksum을 Python에서 직접 출력하려고 bytes()로 먼저 바이트를 만들고 다시 파싱하는 단계를 명시적으로 넣었습니다.

왜 다시 Ether()로 감싸는가?

계산된 실제 바이트를 다시 파싱해서 Length와 Checksum이 구체적인 값으로 채워진 Scapy 객체를 만들기 위해서입니다.

즉: 
필드 삭제
→ bytes()로 실제 바이트 생성
→ Scapy가 Length/Checksum 계산
→ Ether()로 다시 읽기
순서입니다.

코드

from scapy.all import (
    rdpcap,
    wrpcap,
    Ether,
    IP,
    UDP,
    Raw,
    Padding,
)

INPUT_FILE = "/home/ubuntu/part5_original.pcap"
MODIFIED_FILE = "/home/ubuntu/part5_modified.pcap"
COMPARE_FILE = "/home/ubuntu/part5_compare.pcap"

NEW_PAYLOAD = b"MODIFIED OFFLINE DATA"


# 1. pcap 읽기
packets = rdpcap(INPUT_FILE)

print("읽은 패킷 수:", len(packets))


# 2. 패킷이 하나 이상 있는지 확인
if len(packets) == 0:
    raise ValueError("pcap 안에 패킷이 없습니다.")


# 3. 첫 번째 패킷 선택
original = packets[0]


# 4. 원본 보존을 위해 복사
modified = original.copy()


# 5. 필요한 계층 확인
if not modified.haslayer(IP):
    raise ValueError("IP 계층이 없습니다.")

if not modified.haslayer(UDP):
    raise ValueError("UDP 계층이 없습니다.")

if not modified.haslayer(Raw):
    raise ValueError("Raw Payload가 없습니다.")


# 6. 원본 정보 출력
print("원본 Payload:", original[Raw].load)
print("원본 Payload 길이:", len(original[Raw].load))


# 7. Ethernet Padding이 캡처에 남아 있으면 제거
if modified.haslayer(Padding):
    del modified[Padding]


# 8. Payload 수정
modified[Raw].load = NEW_PAYLOAD

print("수정 Payload:", modified[Raw].load)
print("수정 Payload 길이:", len(modified[Raw].load))


# 9. 기존 자동 계산 필드 제거
del modified[IP].len
del modified[IP].chksum
del modified[UDP].len
del modified[UDP].chksum


# 10. 실제 패킷 bytes로 직렬화하면서 자동 필드 재계산
packet_bytes = bytes(modified)


# 11. 계산된 bytes를 Ethernet Frame으로 다시 파싱
rebuilt = Ether(packet_bytes)


# 12. 재계산 결과 확인
print()
print("[재계산 결과]")
print("IP Total Length:", rebuilt[IP].len)
print("UDP Length:", rebuilt[UDP].len)
print("IP Checksum:", hex(rebuilt[IP].chksum))
print("UDP Checksum:", hex(rebuilt[UDP].chksum))


# 13. 수정본 저장
wrpcap(
    MODIFIED_FILE,
    rebuilt
)


# 14. 원본 + 수정본 비교 파일 저장
wrpcap(
    COMPARE_FILE,
    [original, rebuilt]
)


print()
print("저장 완료:")
print(MODIFIED_FILE)
print(COMPARE_FILE)

왜 UDP Header는 항상 8바이트인가?
일반 UDP Header는 Source Port, Destination Port, Length, Checksum 네 필드로 구성되며 각 필드가 2바이트라 총 8바이트입니다.

Checksum을 다시 한 번 정확히 이해하기

IPv4 Header Checksum

IPv4 Header 자체의 오류를 검사하기 위한 값입니다. Payload를 직접 계산하는 것은 아니지만, 이번에는 Payload 길이가 바뀌어 IP Total Length 필드가 변하므로 Header Checksum도 다시 계산해야 합니다.

UDP Checksum

UDP Header와 Payload, 그리고 Source/Destination IP 등으로 만든 pseudo-header를 이용해 계산합니다. 따라서 Payload 내용이나 길이가 바뀌면 다시 계산해야 합니다.

pseudo-header는 실제 패킷에 별도 계층으로 붙어 전송되는 Header가 아닙니다. UDP Checksum 계산을 위해 Source IP, Destination IP, Protocol, Length 같은 정보를 잠시 조합한 계산용 구조입니다.
Wireshark에서 Checksum이 이상하게 보일 때
실제 NIC에서 캡처한 패킷은 checksum offload 때문에 송신 측 캡처에서 Checksum이 아직 하드웨어에 의해 계산되기 전 값처럼 보일 수 있습니다. 따라서 Wireshark의 incorrect 또는 unverified 표시만으로 곧바로 실제 네트워크 오류라고 단정하지 않습니다. 이번 Part에서 Scapy가 오프라인으로 다시 만든 pcap은 직접 계산된 Header 값을 비교하는 데 더 적합합니다.

실무형 확장: “첫 번째 패킷”이 아니라 조건으로 찾기

이번 기본 실습은 -c 1로 패킷 하나만 캡처했기 때문에 packets[0]을 사용해도 안전합니다. 하지만 실제 pcap에는 수십~수천 개의 패킷이 있을 수 있습니다. 그때 무조건 첫 번째 패킷을 수정하면 전혀 다른 패킷을 바꿀 수 있습니다. 
target = None

for packet in packets:

    if (
        packet.haslayer(UDP)
        and packet.haslayer(Raw)
        and packet[UDP].dport == 9999
    ):
        target = packet
        break

if target is None:
    raise ValueError("조건에 맞는 UDP 9999 패킷이 없습니다.")

for packet in packets

pcap 안의 패킷을 하나씩 확인합니다.

and

여러 조건이 모두 True일 때만 전체 조건이 True가 됩니다.

packet[UDP].dport == 9999

UDP 계층의 destination port가 9999인지 비교합니다. ==는 값을 저장하는 =와 달리 “같은가?”를 비교하는 연산자입니다.

break

is None

끝까지 찾지 못해서 target이 여전히 값 없음(None)인지 확인합니다.

이 방식이 실제 pcap 분석에 더 가깝습니다. 파일의 몇 번째 패킷인지보다 “어떤 조건의 패킷인가”로 대상을 찾는 습관이 중요합니다.

17왜 TCP pcap 수정은 더 복잡한가?

UDP는 각각의 Datagram을 독립적으로 보기 쉽습니다.

하지만 TCP에서 Payload 길이를 바꾸면:

TCP Segment 1 Payload 길이 변경
        ↓
다음 Sequence Number 위치 변경
        ↓
상대 ACK Number 관계도 변경 가능
        ↓
이후 TCP Stream 전체와 불일치 가능
예:
원래 10바이트였던 TCP Payload를 20바이트로 늘렸다면, 다음 Segment의 Sequence Number는 원래보다 10만큼 더 이동해야 자연스럽습니다. 그런데 pcap의 다음 TCP Segment를 그대로 두면 Stream 관계가 맞지 않게 됩니다.
따라서 Part 5의 목표는 “패킷 필드를 수정하면 어떤 값들을 다시 계산해야 하는가”를 UDP에서 정확히 이해하는 것입니다. TCP Stream 전체 수정은 별도의 더 높은 단계로 보는 것이 적절합니다.

19이해도 확인

Q1. rdpcap()의 역할은?
pcap 파일을 읽어 Scapy 패킷 객체들로 가져옵니다.
Q2. 왜 original.copy()를 사용하는가?
원본 패킷 객체를 그대로 보존하면서 복사본만 수정하기 위해서입니다.
Q3. modified[Raw].load는 무엇인가?
Raw 계층에 들어 있는 실제 Payload bytes입니다.
Q4. Payload를 바꾼 뒤 왜 UDP.len과 UDP.chksum을 다시 계산해야 하는가?
Payload 길이와 내용이 UDP Length 및 UDP Checksum 계산에 영향을 주기 때문입니다.
Q5. 이번 예제에서 왜 IP.chksum도 다시 계산하는가?
Payload 길이가 바뀌어 IPv4 Header의 Total Length 필드가 바뀌므로 Header Checksum도 다시 계산해야 합니다.
Q6. bytes(modified)를 사용하는 이유는?
Scapy 패킷 객체를 실제 바이트로 직렬화하면서 삭제해 둔 자동 계산 필드들을 다시 계산하도록 하기 위해서입니다.
Q7. wrpcap()의 역할은?
Scapy 패킷 객체를 새 pcap 파일로 저장합니다.
Q8. TCP Payload 길이를 바꾸는 것이 UDP보다 더 복잡한 이유는?
TCP는 바이트 스트림의 Seq/Ack 관계를 유지해야 하므로 한 Segment 길이 변화가 이후 Segment들의 번호 관계에 영향을 줄 수 있기 때문입니다.
Q9. packets[0]과 packet[Raw]의 차이는?
packets[0]은 PacketList의 첫 번째 패킷을 고르고, packet[Raw]은 한 패킷 안에서 Raw 계층을 선택합니다.
Q10. 캡처에 기존 Ethernet Padding이 남아 있다면 수정 전에 제거하는 이유는?
기존 Frame 크기를 맞추기 위한 Padding을 새 Payload의 실제 데이터로 잘못 포함시키지 않고, 수정된 길이에 맞게 패킷을 새로 구성하기 위해서입니다.
Q11. 실무형 pcap에서 무조건 packets[0]을 수정하면 위험한 이유는?
실제 pcap에는 다양한 프로토콜과 연결의 패킷이 섞여 있으므로 첫 번째 패킷이 원하는 대상이라는 보장이 없기 때문입니다. Protocol, Port, IP 등의 조건으로 대상을 찾는 편이 안전합니다.
