왜 이렇게 계층별로 나누어 보는가?
하나의 네트워크 전송에는 여러 종류의 주소가 동시에 존재합니다. MAC은 2계층, IP는 3계층, Port는 4계층입니다. 각 주소가 담당하는 범위가 다르기 때문에 하나라도 잘못되면 정상 전달이 안 될 수 있습니다.

2두 VM이 같은 네트워크인지 확인

실행 위치: ubuntu

ip -4 addr show eth0
ip route

실행 위치: ubuntu1

ip -4 addr show eth0
ip route

ip -4 addr show eth0를 왜 보는가?

eth0의 IPv4 주소와 Prefix Length를 확인하기 위해서입니다. 예를 들어: 

172.21.128.10/24
172.21.128.11/24

둘 다 /24이고 앞의 네트워크 부분이 같다면 같은 서브넷에 있을 가능성이 높습니다.

ip route를 왜 보는가?

목적지 IP로 갈 때 Linux가 어느 인터페이스와 어느 다음 홉을 선택하는지 확인하기 위해서입니다. 라우팅 테이블을 보면: 

default via ...
172.21.128.0/24 dev eth0 ...

같은 대역은 eth0로 직접 나가고, 다른 대역은 default gateway를 통해 나간다는 구조를 확인할 수 있습니다.

왜 Step 3에서 같은 서브넷 여부가 특히 중요한가?
같은 서브넷이면 목적 MAC은 보통 최종 상대방인 ubuntu의 MAC입니다. 하지만 다른 네트워크라면 목적 MAC은 최종 서버 MAC이 아니라 현재 링크의 다음 홉인 게이트웨이 MAC이 됩니다.

3MAC 주소 확인

실행 위치: ubuntu

왜 ip link를 사용하는가?

ip addr가 IP 주소를 중심으로 본다면, ip link는 네트워크 인터페이스 자체의 상태와 2계층 정보를 확인할 때 사용합니다.

출력에서 찾을 부분

link/ether 52:54:00:aa:bb:11 brd ff:ff:ff:ff:ff:ff
부분의미
link/etherEthernet 계열 링크 주소
52:54:...현재 NIC의 MAC 주소
brdbroadcast 주소
ff:ff:ff:ff:ff:ffEthernet Broadcast MAC
MAC 주소는 NIC의 링크 계층 주소입니다. 이번 Step에서는 이 값을 직접 Ethernet Header의 src와 dst에 넣습니다.

왜 ip neigh가 중요한가?
IP 통신이 되더라도 실제 Frame을 만들려면 MAC 주소가 필요합니다. ip neigh는 Linux가 현재 어떤 IP를 어떤 MAC으로 알고 있는지 확인하는 명령입니다. 네트워크 문제에서 “IP는 맞는데 왜 전달이 안 되지?”를 볼 때 매우 중요합니다.

6Ethernet Frame을 직접 만드는 코드

실행 위치: ubuntu1

nano packet_step3.py

코드

from scapy.all import Ether, IP, UDP, Raw, sendp

INTERFACE = "eth0"

SOURCE_MAC = "52:54:00:aa:bb:11"
DEST_MAC = "52:54:00:aa:bb:10"

SOURCE_IP = "172.21.128.11"
DEST_IP = "172.21.128.10"

SOURCE_PORT = 12345
DEST_PORT = 9999

PAYLOAD = b"STEP3 MAC TEST"

frame = (
    Ether(src=SOURCE_MAC, dst=DEST_MAC)
    / IP(src=SOURCE_IP, dst=DEST_IP)
    / UDP(sport=SOURCE_PORT, dport=DEST_PORT)
    / Raw(load=PAYLOAD)
)

frame.show()

sendp(
    frame,
    iface=INTERFACE,
    verbose=False
)

print("Ethernet Frame 전송 완료")
위 IP/MAC은 예시입니다. 반드시 자신의 ubuntu / ubuntu1 실제 값으로 변경합니다.
왜 변수로 따로 분리했는가?
MAC, IP, Port, Payload를 코드 안에 직접 여러 번 쓰면 무엇을 바꾸는지 구분하기 어렵습니다. 변수로 분리하면 2계층, 3계층, 4계층 값을 한눈에 볼 수 있고 실험할 때 특정 값만 바꾸기 쉽습니다.

8Ether()를 자세히 보기

Ether(
    src=SOURCE_MAC,
    dst=DEST_MAC
)

src

source, 출발지 MAC입니다.

dst

destination, 목적지 MAC입니다.

왜 MAC을 직접 지정하는가?

Step 1·2에서는 운영체제가 링크 계층 처리를 맡았습니다. 이번에는 Ethernet Header를 직접 만들기 때문에 어떤 MAC에서 어떤 MAC으로 보내는지 코드에서 명시합니다.

중요:
같은 LAN의 상대방에게 직접 보낼 때는 목적 MAC이 상대방 MAC입니다. 하지만 다른 네트워크로 갈 때는 목적 MAC이 최종 서버 MAC이 아니라 기본 게이트웨이 MAC입니다.

9sendp()를 자세히 보기

sendp(
    frame,
    iface=INTERFACE,
    verbose=False
)

frame

전송할 완성된 Ethernet Frame 객체입니다.

iface=INTERFACE

어느 네트워크 인터페이스로 Frame을 내보낼지 지정합니다. 여기서는 eth0입니다.

verbose=False

Scapy가 전송 과정의 자세한 메시지를 줄이고 결과만 간단히 보여주도록 합니다.

왜 send()가 아니라 sendp()인가?

함수주로 다루는 시작 계층사용 이유
send()3계층IP 패킷을 전송할 때
sendp()2계층Ethernet Header까지 직접 만든 Frame을 전송할 때
sendp()의 p는 “packet at layer 2” 방식으로 이해하면 좋습니다. 중요한 것은 이름 암기가 아니라, Ether()를 만들었기 때문에 sendp()를 쓴다는 연결입니다.

13ARP와 Neighbor Table 연결

ubuntu1

sudo ip neigh flush dev eth0

옵션/문법 설명

부분의미
ip neighNeighbor Table 관리
flush저장된 항목 삭제

왜 비우는가?

이미 MAC 정보가 저장되어 있으면 ARP가 새로 동작하는 과정을 보기 어렵습니다. 한 번 비운 뒤 다시 ping하면 Linux가 상대 MAC을 다시 알아내는 과정을 확인할 수 있습니다.

다시 통신 발생

ping -c 1 <UBUNTU_IP>

다시 확인

ip neigh show <UBUNTU_IP>
왜 이 과정이 Step 3과 연결되는가?
우리는 코드에서 목적 MAC을 직접 넣었지만, 일반 통신에서는 운영체제가 ARP와 Neighbor Table을 이용해 이 값을 자동으로 알아냅니다. 즉 Step 3의 수동 작업은 Linux가 평소 자동으로 해주는 과정을 눈에 보이게 만든 것입니다.

왜 안 보일 수 있는가?

Ethernet NIC는 Frame을 받을 때 먼저 목적 MAC을 봅니다. 목적 MAC이 자신의 MAC도 아니고 Broadcast/Multicast도 아니라면 일반적으로 해당 Frame을 자신에게 온 것으로 처리하지 않습니다.

즉: 
IP 목적지가 맞다
하지만
MAC 목적지가 틀리다
→ 같은 LAN에서는 정상 수신되지 않을 수 있음

15MAC 주소를 코드에서 자동으로 가져오기

from scapy.all import (
    Ether,
    IP,
    UDP,
    Raw,
    sendp,

    getmacbyip,

INTERFACE = "eth0"
DEST_IP = "172.21.128.10"

SOURCE_MAC = get_if_hwaddr(INTERFACE)
DEST_MAC = getmacbyip(DEST_IP)

print("내 MAC:", SOURCE_MAC)
print("상대/다음 홉 MAC:", DEST_MAC)

get_if_hwaddr()

지정한 인터페이스의 MAC 주소를 가져옵니다.

getmacbyip()

목적 IP로 실제 전송할 때 필요한 MAC 주소를 알아냅니다. 같은 네트워크라면 상대 MAC, 다른 네트워크라면 다음 홉 MAC을 얻는 방향으로 동작할 수 있습니다.

왜 자동 조회를 마지막에 하는가?
처음부터 자동으로 값을 가져오면 MAC이 왜 필요한지 보이지 않습니다. 먼저 직접 확인하고 넣어 본 뒤 자동 조회를 보면 운영체제와 Scapy가 어떤 일을 대신해주는지 이해하기 쉽습니다.

16추가 실험

A. Source MAC 비교

ip link show eth0

코드의 SOURCE_MAC과 비교합니다.

왜?

코드에 넣은 값이 실제 NIC MAC과 일치하는지 확인하기 위해서입니다.

B. Destination MAC 비교

ip neigh show <UBUNTU_IP>

코드의 DEST_MAC과 비교합니다.

왜?

Neighbor Table이 알고 있는 상대 MAC과 우리가 직접 넣은 MAC이 일치하는지 확인하기 위해서입니다.

C. Broadcast MAC 확인

ff:ff:ff:ff:ff:ff

모든 비트가 1인 Ethernet Broadcast 주소입니다. 같은 Broadcast Domain의 여러 장비가 받을 수 있습니다. 이번 기본 실험은 unicast MAC을 사용합니다.

18이해도 확인

Q1. 왜 Step 3에서 tcpdump -e를 사용하는가?
Ethernet Header의 Source MAC, Destination MAC 같은 2계층 정보를 보기 위해서입니다.
Q2. 같은 LAN에서 목적 MAC은 누구의 MAC인가?
직접 통신하는 상대 호스트의 MAC입니다.
Q3. 다른 네트워크로 갈 때 목적 MAC은 최종 서버 MAC인가?
아닙니다. 현재 링크에서의 다음 홉인 게이트웨이/라우터 인터페이스 MAC입니다.
Q4. ip neigh를 왜 확인하는가?
Linux가 현재 특정 IP를 어떤 MAC 주소로 알고 있는지 확인하기 위해서입니다.
Q5. send()와 sendp() 차이는?
send()는 주로 3계층 IP 패킷, sendp()는 2계층 Ethernet Frame을 직접 전송할 때 사용합니다.
