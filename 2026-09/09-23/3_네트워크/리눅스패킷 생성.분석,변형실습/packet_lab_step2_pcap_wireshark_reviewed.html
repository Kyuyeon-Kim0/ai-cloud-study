왜 pcap으로 저장하는가?
터미널에서 실시간으로 지나가는 패킷을 보는 것만으로는 세부 필드를 차분히 비교하기 어렵습니다. pcap은 캡처한 패킷을 파일로 보관하기 때문에 나중에 Wireshark에서 동일한 패킷을 반복해서 열어보고, 각 헤더와 실제 바이트를 비교할 수 있습니다.
pcap이란?
pcap은 packet capture에서 나온 이름입니다. 네트워크에서 캡처한 패킷을 파일에 저장해 두었다가 tcpdump나 Wireshark에서 다시 읽을 수 있습니다. 즉, 화면 캡처 이미지가 아니라 패킷 자체의 바이트와 메타정보를 보관하는 파일입니다.

먼저 예상 결과부터 보기

이번에 보내는 두 Payload는:

ORIGINAL DATA
MODIFIED DATA

둘 다 ASCII 기준 13 bytes입니다.

항목예상값이유
Payload Length13 bytes두 문자열 길이가 같음
UDP Length21 bytesUDP Header 8 + Payload 13
IPv4 Total Length41 bytes일반적인 IPv4 Header 20 + UDP 21
Ethernet 관련 길이환경에 따라 표시값이 다를 수 있음IP 41 + Ethernet Header 14 = 55B이지만, Ethernet 최소 프레임 패딩과 FCS 처리, 캡처 지점에 따라 Wireshark 표시값이 달라질 수 있음
UDP Checksum두 패킷이 달라질 수 있음Payload 내용이 바뀌었기 때문
IPv4 Header ChecksumIP 헤더가 같다면 같을 수 있음IPv4 Header Checksum은 Payload 자체를 계산하지 않음
Frame 길이는 고정값으로 외우지 않습니다.
이번 예제의 IP 패킷은 41바이트이고 Ethernet Header 14바이트를 단순히 더하면 55바이트입니다. 하지만 Ethernet은 최소 프레임 크기를 맞추기 위해 Padding이 붙을 수 있고, FCS 4바이트가 캡처 파일에 포함되는지 여부도 NIC/드라이버/가상화 환경에 따라 다릅니다. 따라서 Wireshark에서 55, 60 등 다른 값이 보일 수 있습니다. 여기서는 UDP Length와 IP Total Length를 먼저 정확히 이해하고, Frame Length는 실제 캡처값을 관찰하는 방식으로 봅니다.

2두 패킷을 연속으로 보내는 Python 파일 만들기

실행 위치: ubuntu1

nano packet_step2.py

아래 코드를 입력합니다.

from scapy.all import IP, UDP, Raw, send
import time

DEST_IP = "172.21.128.10"
SOURCE_PORT = 12345
DEST_PORT = 9999

messages = [
    b"ORIGINAL DATA",
    b"MODIFIED DATA",
]

for message in messages:

    packet = (
        IP(dst=DEST_IP)
        / UDP(sport=SOURCE_PORT, dport=DEST_PORT)
        / Raw(load=message)
    )

    send(packet)
    print("보낸 데이터:", message)
    time.sleep(1)
DEST_IP는 자신의 ubuntu 실제 IP로 변경합니다.
왜 Step 1처럼 파일을 두 번 수정하지 않는가?
이번 목적은 두 패킷을 하나의 pcap에 순서대로 저장해 바로 비교하는 것입니다. 그래서 리스트와 반복문을 사용해 ORIGINAL과 MODIFIED를 자동으로 한 번씩 전송합니다.

4ubuntu에서 pcap 캡처 시작

실행 위치: ubuntu

sudo tcpdump -i eth0 -nn -s 0 -c 2 -w /home/ubuntu/step2_compare.pcap 'udp dst port 9999'
옵션의미
-i eth0eth0에서 캡처
-nn주소와 포트를 숫자로 유지
-s 0충분히 큰 snap length를 사용해 이번 패킷이 중간에서 잘리지 않도록 캡처
-c 2조건에 맞는 패킷 2개를 캡처하면 자동 종료
-w화면 대신 pcap 파일로 저장
udp dst port 9999목적지 UDP 9999 패킷만 저장
-w를 사용하면 패킷 세부 내용이 화면에 평소처럼 출력되지 않습니다. 대신 원본 패킷 데이터가 pcap 파일에 저장됩니다.

Frame 항목에서 확인

Wireshark의 Frame 항목을 펼쳐 다음을 찾습니다.

  • Frame Number
  • Frame Length
  • Arrival Time
Frame Length란?
Wireshark가 캡처한 한 프레임의 전체 길이입니다. Ethernet Header와 그 안의 IP 패킷 등이 포함됩니다. 다만 Ethernet의 Padding과 FCS가 캡처 시점에서 어떻게 처리되는지는 환경마다 다를 수 있습니다. 그래서 이번 단계에서는 Frame Length를 특정 숫자로 맞추기보다 실제 보이는 값을 기록하고, IP Total Length와 구분하는 것이 핵심입니다.
참고: Ethernet 최소 크기
일반적인 Ethernet 프레임은 실제 링크에서 최소 크기를 맞추기 위해 Padding이 추가될 수 있습니다. 또 FCS는 보통 하드웨어에서 처리되어 pcap에 보이지 않는 경우가 많습니다. 따라서 “IP 41B + Ethernet Header 14B = 반드시 Wireshark Frame Length 55B”라고 외우면 안 됩니다.

14Checksum 비교

Checksum을 왜 보는가?

Checksum은 데이터가 전달되는 동안 비트가 바뀌었는지 확인하기 위한 검사값입니다. 아주 단순하게 비유하면, 내용을 바탕으로 만든 요약 숫자와 비슷합니다. 내용이 바뀌면 보통 이 검사값도 바뀝니다.

UDP Checksum

첫 번째 패킷과 두 번째 패킷의 UDP Checksum 값을 비교합니다.

ORIGINAL DATA  → UDP Checksum A
MODIFIED DATA  → UDP Checksum B

Payload 내용이 달라졌으므로 보통 UDP Checksum도 달라집니다.

UDP Checksum은 UDP Header + Payload만 보는 것이 아닙니다. 출발지 IP, 목적지 IP, 프로토콜 번호, UDP 길이 등을 이용해 만든 pseudo-header(계산용 가상 헤더)도 함께 사용합니다. pseudo-header는 실제 UDP 패킷 앞에 따로 붙어 전송되는 헤더가 아니라 Checksum 계산을 위해서만 사용하는 정보 묶음입니다. 따라서 Payload 한 바이트만 바뀌어도 UDP Checksum은 보통 달라집니다.

IPv4 Header Checksum

IPv4 Header Checksum은 IPv4 헤더 자체를 검사합니다. Payload 내용은 직접 계산 대상이 아닙니다.

따라서 두 패킷의 IPv4 헤더 필드가 모두 동일하다면 IPv4 Header Checksum은 같을 수 있습니다. 반대로 IP ID, TTL, 주소, 길이 등 헤더 필드 중 하나라도 달라지면 Header Checksum도 달라질 수 있습니다.

가상화 환경이나 NIC checksum offload 영향으로 Wireshark가 Checksum validation disabled, unverified 또는 비정상처럼 표시하는 경우가 있을 수 있습니다. 그 표시만으로 실제 네트워크 패킷이 손상되었다고 단정하지 않습니다.

17이해도 확인

Q1. pcap 파일을 만드는 tcpdump 옵션은?
① -A ② -w ③ -r ④ -n
정답: ② -w — 캡처한 패킷을 파일에 기록합니다.
Q2. 저장된 pcap을 tcpdump에서 읽는 옵션은?
-r입니다.
Q3. Payload가 13바이트일 때 UDP Length는 몇 바이트인가?
21바이트입니다. UDP Header 8 + Payload 13입니다.
Q4. 일반적인 IPv4 Header가 20바이트이고 UDP Length가 21이면 IP Total Length는?
41바이트입니다.
Q5. ORIGINAL DATA와 MODIFIED DATA의 길이가 같은데도 달라질 가능성이 큰 값은?
UDP Checksum입니다. Payload 내용이 달라졌기 때문입니다.
Q6. IPv4 Header Checksum이 Payload 변경에 직접 영향을 받지 않는 이유는?
IPv4 Header Checksum은 IPv4 헤더 자체를 계산하며 Payload는 직접 계산 대상이 아니기 때문입니다.
Q7. 이번 예제에서 Ethernet Frame Length를 무조건 55바이트라고 외우면 안 되는 이유는?
Ethernet 최소 프레임을 위한 Padding, FCS 포함 여부, 가상 NIC와 캡처 지점에 따라 Wireshark가 보여주는 Frame Length가 달라질 수 있기 때문입니다.
Q8. Wireshark의 가운데/아래 Packet Bytes 영역에서 Hex를 보는 이유는?
네트워크에서 실제로 전달된 바이트 값을 16진수 형태로 직접 확인하기 위해서입니다.

Step 2 완료 체크

  • step2_compare.pcap 파일을 만들었다.
  • tcpdump의 -w와 -r 차이를 이해했다.
  • Wireshark의 Packet List / Details / Bytes 영역을 구분할 수 있다.
  • Payload 13B → UDP Length 21B → IPv4 Total Length 41B 계산을 이해했다.
  • Frame Length는 캡처 환경에 따라 달라질 수 있음을 이해했다.
  • ORIGINAL과 MODIFIED의 Hex/ASCII 차이를 찾았다.
  • UDP Checksum과 IPv4 Header Checksum의 계산 대상이 다르다는 것을 이해했다.
