TCP란?

TCP는 Transmission Control Protocol의 약자이며 OSI 관점에서 4계층 전송 계층에 해당합니다. TCP는 단순히 데이터를 한 번 보내고 끝나는 방식이 아니라, 상대와 연결 상태를 만들고, 데이터의 순서와 수신 여부를 관리합니다.

특징의미
연결지향데이터를 보내기 전에 연결 상태를 먼저 만듦
순서 관리바이트가 순서대로 전달되도록 Sequence Number 사용
수신 확인ACK로 상대가 어디까지 받았는지 확인
재전송필요한 경우 유실된 데이터를 다시 보낼 수 있음
흐름 제어상대가 받을 수 있는 양을 고려하며 전송
왜 UDP 다음에 TCP를 보는가?
UDP는 연결을 만들지 않아 패킷 하나의 구조를 보기 좋았습니다. TCP는 여기에 상태가 추가됩니다. 즉, 이제부터는 “패킷 하나”뿐 아니라 “패킷들이 서로 어떤 순서와 의미로 연결되는가”까지 봐야 합니다.

TCP Segment란?

4계층 TCP에서 다루는 데이터 단위를 보통 TCP Segment라고 부릅니다. 실제 전송에서는: 

Ethernet Frame
 └─ IP Packet
     └─ TCP Segment
         └─ Application Data

따라서 tcpdump에서 보는 TCP 패킷도 실제로는 IP 패킷 안에 TCP Segment가 들어 있는 형태입니다.

왜 3단계인가?
TCP는 양방향 통신입니다. 클라이언트가 서버에 보낼 수 있다는 것뿐 아니라 서버도 클라이언트에 보낼 수 있다는 사실을 양쪽이 확인해야 합니다. 또 양쪽이 각각 사용할 초기 Sequence Number도 교환해야 합니다.

Port와 Socket을 먼저 이해하기

Port란?

IP 주소가 “어느 컴퓨터인가?”를 구분한다면, Port는 그 컴퓨터 안에서 “어느 프로그램/서비스인가?”를 구분하는 번호입니다. 

172.21.128.10:8000
│             │
IP            Port

Socket이란?

네트워크 프로그램이 통신을 위해 운영체제에 만들어 놓는 통신 끝점이라고 보면 됩니다. TCP 서버는 특정 IP/Port에 Socket을 만들고 새 연결을 기다립니다.

LISTEN이란?

서버 Socket이 새 TCP 연결 요청을 받을 준비가 된 상태입니다. LISTEN은 아직 특정 클라이언트와 연결되었다는 뜻이 아닙니다.

ESTABLISHED란?

3-Way Handshake가 끝나 실제 데이터 송수신이 가능한 연결 상태입니다.

38000번 Port가 LISTEN인지 확인

실행 위치: ubuntu의 다른 터미널

ss -lntp | grep ':8000'

왜?

프로그램을 실행했다고 해서 원하는 Port가 실제로 열렸다고 단정할 수 없습니다. TCP 서버가 연결 요청을 받으려면 8000번 Socket이 LISTEN 상태여야 합니다.

ss란?

Socket Statistics의 약자로, 현재 시스템의 TCP/UDP Socket 상태를 확인할 때 사용합니다.

옵션뜻이번에 필요한 이유
-llistening새 연결을 기다리는 Socket만 보기
-nnumericPort를 서비스 이름 대신 숫자로 표시
-tTCPTCP Socket만 보기
-pprocess가능한 경우 Socket을 사용하는 프로세스 표시

Pipe와 grep

ss -lntp | grep ':8000'

|는 앞 명령의 출력을 뒤 명령으로 넘기는 Pipe입니다. grep ':8000'은 출력 중 :8000이 포함된 줄만 보여줍니다.

예상:

LISTEN 0 5 0.0.0.0:8000 0.0.0.0:*
LISTEN을 확인하는 이유
Handshake에서 첫 번째 SYN이 서버에 도착했을 때 운영체제가 “이 Port를 기다리는 서버가 있다”고 판단해야 SYN/ACK를 돌려줄 수 있습니다.

4먼저 단순한 tcpdump로 Handshake 보기

실행 위치: ubuntu

sudo tcpdump -i eth0 -nn 'tcp port 8000'

왜 처음부터 옵션을 많이 넣지 않는가?

첫 번째 목표는 SYN → SYN/ACK → ACK의 흐름을 찾는 것입니다. 처음부터 Sequence 절대값이나 매우 자세한 필드를 모두 표시하면 출력이 복잡해질 수 있으므로 기본 흐름부터 확인합니다.

부분의미
sudo패킷 캡처 권한을 위해 관리자 권한 사용
tcpdump네트워크 패킷 캡처/출력 도구
-i eth0eth0 인터페이스에서 캡처
-nn주소/Port를 이름으로 변환하지 않고 숫자로 표시
tcp port 8000TCP이며 8000번 Port와 관련된 패킷만 표시
왜 -nn을 쓰는가?
TCP 연결을 볼 때는 실제 Port 번호를 그대로 보는 것이 중요합니다. 이름 변환이 일어나면 숫자 관계를 보기 어려울 수 있습니다.

5ubuntu1에서 실제 연결 발생

실행 위치: ubuntu1

curl -v http://<UBUNTU_IP>:8000/

curl이란?

URL로 네트워크 요청을 보낼 수 있는 명령입니다. 여기서는 HTTP 요청을 보내기 전에 TCP 연결을 만들기 때문에 Handshake를 발생시키는 데 사용합니다.

-v

verbose의 약자입니다. 연결 과정과 HTTP 요청/응답 정보를 더 자세히 보여줍니다.

예:

* Connected to ...
> GET / HTTP/1.1
> Host: ...
< HTTP/1.0 200 OK
curl의 “Connected”는 무엇을 뜻하는가?
TCP 3-Way Handshake가 완료되어 응용계층 HTTP 요청을 보낼 수 있는 상태가 되었다는 의미입니다. tcpdump에서는 그 “Connected”가 만들어지는 직전의 3개 TCP Segment를 봅니다.

6SYN → SYN/ACK → ACK 해석

tcpdump에서 다음 형태를 찾습니다.

ubuntu1.53000 > ubuntu.8000: Flags [S], seq 1000, ...
ubuntu.8000 > ubuntu1.53000: Flags [S.], seq 5000, ack 1001, ...
ubuntu1.53000 > ubuntu.8000: Flags [.], ack 5001, ...
위 숫자는 이해를 위한 예시입니다. 실제 Sequence Number와 클라이언트 Port는 실행할 때마다 달라질 수 있습니다.

1단계: SYN

Flags [S]

클라이언트가 서버에 “TCP 연결을 시작하고 싶다”고 요청합니다. 이때 자신의 초기 Sequence Number도 함께 보냅니다.

2단계: SYN + ACK

Flags [S.]

서버는 클라이언트의 SYN을 받았다고 ACK하고, 동시에 서버 자신의 SYN도 보냅니다. 즉 하나의 Segment에 SYN과 ACK 두 Flag가 같이 설정됩니다.

3단계: ACK

Flags [.]

클라이언트가 서버의 SYN을 받았다고 확인합니다. 이 단계가 끝나면 TCP 연결은 일반적으로 ESTABLISHED 상태가 됩니다.

9Sequence Number 이해

TCP의 Sequence Number는 “몇 번째 패킷인가?”를 세는 번호가 아닙니다. 바이트 스트림에서 어느 바이트 위치인가를 관리하는 값입니다. 이 점이 매우 중요합니다.

예를 들어 클라이언트가:

seq = 1000

으로 SYN을 보냈다고 가정합니다.

TCP는 이후 데이터 바이트들의 순서를 Sequence Number로 추적합니다. 그래서 데이터가 순서가 바뀌어 도착하거나 일부가 유실되어도 어느 부분이 필요한지 판단할 수 있습니다.

실제 초기 Sequence Number(ISN)는 큰 값일 수 있으며 연결마다 달라질 수 있습니다. tcpdump와 Wireshark는 보기 쉽게 상대 Sequence Number를 표시하는 기능을 사용하기도 합니다.

10Acknowledgment Number 이해

Ack 번호는 “마지막으로 받은 번호”가 아니다

TCP의 Acknowledgment Number는 보통 “다음에 받고 싶은 Sequence Number”를 의미합니다.

클라이언트 SYN:

seq = 1000

서버 SYN/ACK:

ack = 1001

왜 1001인가?

SYN은 Payload가 없어도 Sequence Number 공간에서 1을 소비합니다. 그래서: 

상대 SYN seq = 1000
다음에 기대하는 번호 = 1001

서버 SYN:

seq = 5000

클라이언트 마지막 ACK:

ack = 5001
기억하기 좋은 문장:
ACK 번호 = “다음에는 이 번호부터 보내줘.”

11이번에는 절대 Sequence Number 보기

실행 위치: ubuntu

sudo tcpdump -i eth0 -nn -tttt -S -vvv 'tcp port 8000'

왜 두 번째 tcpdump 명령을 따로 보는가?

앞에서는 Handshake 흐름을 쉽게 보기 위해 기본 출력으로 봤습니다. 이제 Seq/Ack의 실제 숫자 관계를 확인하기 위해 자세한 옵션을 추가합니다.

옵션의미왜 사용하는가?
-tttt날짜와 시간을 자세히 표시각 패킷 순서를 시간까지 함께 비교
-STCP Sequence Number를 절대값으로 표시실제 Seq/Ack 숫자 관계 확인
-vvv매우 자세한 출력추가 TCP 필드 확인
-S 없이 tcpdump가 상대 Sequence Number를 보여주면 0, 1처럼 단순하게 보일 수 있습니다. 학습 초반에는 상대값이 쉽고, 실제 숫자 관계를 보고 싶을 때 -S를 사용하면 됩니다.

-c 3030개를 캡처한 뒤 종료Handshake + HTTP + 종료 흐름까지 넉넉하게 저장
-wpcap 파일로 저장Wireshark에서 다시 분석

15TCP 종료에서 FIN 보기

HTTP 요청이 끝난 뒤 다음과 같은 Flag 흐름을 찾습니다.

Flags [F.]
Flags [.]
Flags [F.]
Flags [.]

왜 종료도 여러 단계인가?

TCP는 양방향 연결입니다. 한 방향의 송신 종료와 반대 방향의 송신 종료가 독립적이기 때문에 한쪽 FIN과 다른쪽 FIN이 별도로 나타날 수 있습니다.

FIN도 Sequence Number를 1 소비

SYN과 마찬가지로 FIN도 Sequence Number 공간에서 1을 소비합니다. 따라서 FIN을 받은 상대의 ACK는 보통 FIN의 Sequence Number + 1 관계를 보입니다.

TCP 연결 단계에서 너무 오래 기다리지 않도록 최대 연결 대기 시간을 제한합니다.

같은 호스트까지 도달하지만 8000번에 LISTEN Socket이 없다면 보통:

    ↓
Server RST/ACK
    ↑

형태의 즉시 거절을 볼 수 있습니다.

방화벽 정책에 따라 패킷을 조용히 버리는 경우에는 RST 대신 응답 자체가 없을 수도 있습니다. 따라서 “RST가 없으면 항상 다른 원인”이라고 단정하지 않습니다.
왜 실무적으로 중요한가?
“ping은 되는데 서비스 접속이 안 된다”는 상황에서 서버까지 SYN이 도착했는지, 서버가 RST를 돌려줬는지, 아무 응답도 없는지를 보면 포트 미오픈과 방화벽/경로 문제를 구분하는 데 도움이 됩니다.

18이해도 확인

Q1. TCP 3-Way Handshake 순서는?
SYN → SYN/ACK → ACK입니다.
Q2. LISTEN 상태는 무엇을 의미하는가?
특정 TCP Port에서 새 연결 요청을 받을 준비가 된 서버 Socket 상태입니다.
Q3. Sequence Number는 패킷 번호인가?
아닙니다. TCP 바이트 스트림의 위치를 관리하는 번호입니다.
Q4. ACK Number는 보통 무엇을 의미하는가?
다음에 받고 싶은 Sequence Number를 의미합니다.
Q5. SYN seq가 1000이면 상대의 ACK가 1001이 되는 이유는?
SYN은 Payload가 없어도 Sequence Number 공간에서 1을 소비하기 때문입니다.
Q6. 클라이언트의 Source Port가 매번 달라질 수 있는 이유는?
운영체제가 새 연결마다 사용 가능한 임시(ephemeral) Port를 선택하기 때문입니다.
Q7. 서버 Port가 닫혀 있을 때 대표적으로 볼 수 있는 응답은?
RST 또는 RST/ACK입니다. 다만 방화벽이 조용히 버리면 응답이 없을 수도 있습니다.
