모든 것이 파일이다02
EVERYTHING IS A FILE

리눅스에서는 모든 것이 파일이다

WHY

리눅스는 “모든 것이 파일이다(Everything is a file)”라는 철학을 기반으로 설계되었습니다.

프로세스, 하드웨어 장치, 네트워크 소켓까지 모두 디렉터리 트리 아래 파일 형태로 표현됩니다. 따라서 체계적인 디렉터리 관리는 단순한 파일 정리를 넘어 시스템의 안정성, 보안, 성능을 좌우하는 핵심 작업입니다.

/ ← 모든 것은 여기서 시작 ├── home/ubuntu/.bashrc ← 보통 파일 ├── etc/passwd ← 설정도 파일 ├── dev/sda1 ← 디스크(하드웨어)도 파일 ├── dev/null ← 버리는 곳도 파일 └── proc/meminfo ← 메모리 상태(커널 정보)도 파일

디렉터리 관리가 중요한 다섯 가지 이유

이유한 줄 요약
1. 시스템 안정성한 디렉터리의 용량 폭주가 서버 전체를 멈추지 않게 한다
2. 보안과 권한 통제디렉터리별로 권한과 옵션을 달리해 피해 범위를 줄인다
3. 백업과 복구디렉터리 성격에 따라 백업 방법과 주기를 다르게 한다
4. 성능입출력 특성에 맞는 저장 장치에 디렉터리를 배치한다
5. 협업과 자동화표준 구조를 따르면 누구나, 어떤 도구든 바로 찾는다
지금 단계에서는 다음 두 쪽의 자세한 내용을 읽고 용어만 익혀 두면 됩니다. 마운트, 쿼터 같은 설정은 이후 운영 파트에서 직접 다룹니다.

1. 시스템 안정성 및 장애 방지 (디스크 고갈 격리)

리눅스에서는 파티션을 나눠 디렉터리에 마운트(mount)하는 방식으로 파일 시스템을 구성합니다. 체계적인 관리가 없으면 한 영역의 용량 급증이 시스템 전체를 마비시킬 수 있습니다.

  • 로그 및 임시 파일 격리: /var/log나 /tmp 같은 가변 데이터 디렉터리가 루트(/)와 분리되어 있지 않으면, 로그 폭주나 비정상 프로세스로 루트 파티션이 100% 꽉 찰 수 있습니다.
  • 서비스 중단 방지: 루트 파일 시스템 용량이 바닥나면 OS 핵심 데몬이 멈추고 SSH 접속조차 안 되는 다운타임이 생깁니다. 디렉터리별 파티션과 쿼터(Quota) 관리로 이를 막습니다.

2. 보안 강화 및 접근 권한 통제

FHS(Filesystem Hierarchy Standard) 표준에 맞춰 디렉터리를 나누면 최소 권한 원칙을 엄격하게 적용할 수 있습니다.

  • 마운트 옵션을 통한 방어: 누구나 쓸 수 있는 /tmp에 noexec(실행 금지), nosuid(권한 상승 금지)를 주어 악성 스크립트 실행을 막습니다. 바뀌면 안 되는 디렉터리는 ro(Read-Only, 읽기 전용)로 마운트해 무단 변조를 막습니다.
  • 사용자 및 프로세스 격리: 웹 문서 루트(/var/www), 사용자 홈(/home), 시스템 설정(/etc)이 명확히 나뉘어 있어야 공격(Path Traversal 등)이 생겨도 피해를 해당 디렉터리로 제한할 수 있습니다.

WHY ③ ④ ⑤

성격에 맞게 백업하고, 배치하고, 표준을 지킨다

3. 백업 및 재해 복구(DR)의 효율성

모든 데이터를 한 번에 백업하는 것은 비효율적이며 복구 시간(RTO)을 늘립니다. 디렉터리를 기능별로 구조화하면 백업 전략을 유연하게 세울 수 있습니다.

디렉터리 유형대표 경로백업 전략
정적 시스템 파일/bin /usr /libOS 이미지나 패키지 관리자로 복구 가능 → 잦은 백업 불필요
환경 설정/etc가벼운 텍스트 위주 → Git 형상 관리 또는 일일 백업
가변·데이터 파일/var/lib/mysql /srv /data실시간 증분 백업 및 스냅샷 필수
임시·캐시 파일/tmp /var/cache백업 대상에서 영구 제외

4. I/O 성능 최적화 및 리소스 배치

데이터의 입출력 특성에 따라 디렉터리를 알맞은 저장 장치에 연결해야 서버 성능이 극대화됩니다.

  • 초고속 NVMe/SSD: 트랜잭션이 많은 DB 데이터 디렉터리나 웹 캐시 경로
  • RAM 디스크(tmpfs): 휘발성이고 매우 빠른 속도가 필요한 /run, /dev/shm 같은 메모리 기반 경로
  • 대용량 HDD/NAS: 백업 아카이브, 정적 미디어 파일처럼 비용 효율이 중요한 데이터

5. 협업 및 자동화 유지보수

리눅스 표준 규격(FHS)을 지키면 운영 비용(OPEX)이 크게 줄어듭니다.

  • DevOps 및 IaC 연계: Ansible, Terraform, Docker 같은 자동화 도구는 정형화된 디렉터리 구조를 전제로 작성됩니다.
  • 인수인계 및 모니터링 표준화: 신규 관리자나 관제 도구(Prometheus, Datadog 등)가 살펴야 할 핵심 경로(/var, /opt 등)를 바로 찾을 수 있습니다.

DR = Disaster Recovery(재해 복구) · RTO = Recovery Time Objective(목표 복구 시간) · tmpfs = 메모리를 디스크처럼 쓰는 파일 시스템 · IaC = Infrastructure as Code(인프라를 코드로 관리) · OPEX = 운영 비용

디렉터리 지도 (FHS)06
FHS MAP

루트(/) 아래 디렉터리마다 하는 일이 정해져 있다

리눅스의 디렉터리는 FHS(Filesystem Hierarchy Standard)라는 표준에 따라 배치됩니다. 배포판이 달라도 큰 틀은 같아서, 지도를 한 번 익혀 두면 어느 서버에서든 길을 찾을 수 있습니다.

ubuntu
ubuntu@myUbuntu:~$ ls /
bin boot dev etc home lib lib64 lost+found media mnt opt
proc root run sbin snap srv sys tmp usr var (버전에 따라 조금 다를 수 있음)
디렉터리들어 있는 것알아 둘 점
/루트 · 모든 경로의 시작root 계정의 홈 /root와 다르다
/bin /sbin기본 명령 · 관리용 명령Ubuntu에서는 /usr/bin, /usr/sbin을 가리키는 링크
/boot부팅에 필요한 파일 (커널)함부로 지우면 부팅이 안 된다
/dev장치 파일 (디스크, 터미널)하드웨어도 파일로 보인다
/etc시스템 설정 파일passwd, group, sudoers가 여기에
/home일반 사용자의 홈/home/ubuntu, /home/st1
/rootroot 계정의 홈다른 계정은 들어갈 수 없다
/lib프로그램이 함께 쓰는 라이브러리Windows의 DLL과 비슷한 역할
/media /mntUSB · 임시 마운트 위치외부 저장 장치를 연결하는 자리
/opt따로 설치한 프로그램패키지 관리자 밖에서 설치한 것
/proc /sys프로세스 · 커널 · 하드웨어 정보디스크에 없는 가상 파일
/run실행 중에 생기는 임시 정보메모리 위에 있어 재부팅하면 사라진다
/srv서비스가 제공하는 데이터웹·FTP 데이터를 두기도 한다
/tmp임시 파일누구나 쓸 수 있고, 재부팅 때 정리될 수 있다
/usr프로그램과 명령의 대부분/usr/bin/ls처럼 실제 명령이 있는 곳
/var계속 바뀌는 데이터로그(/var/log), 캐시, 웹 파일(/var/www)

처음에는 /etc(설정), /home(사용자), /var/log(로그), /tmp(임시) 네 곳부터 확실히 기억합니다.

ls는 옵션을 붙여야 제대로 보인다

ls와 chmod는 파일 정보를 확인하고 권한을 제어하는 한 쌍입니다. ls(list)는 현재 위치의 파일 목록을 보여 주지만, 옵션 없이 쓰면 정보가 너무 적습니다.

옵션원래 말하는 일
-llong format가장 많이 쓴다. 권한, 소유자, 크기, 수정 날짜를 자세히 보여 준다
-aall이름이 .으로 시작하는 숨김 파일까지 모두 보여 준다
-hhuman-readable크기를 K, M, G 단위로 읽기 쉽게. -l과 함께 쓴다 (ls -lh)
-ttime수정 시간 순으로 정렬 (최근 것이 위)
-rreverse정렬 순서를 뒤집는다 (ls -ltr → 최근 것이 맨 아래)
-RRecursive하위 디렉터리까지 모두 보여 준다
-ddirectory디렉터리 안이 아니라 디렉터리 자체의 정보 (ls -ld /home)

chmod로 권한을 바꾼다 · 기호 방식

chmod(change mode)는 파일의 권한을 바꿉니다. 크게 기호 방식과 숫자 방식이 있습니다. 먼저 기호 방식입니다.

1. 실행 권한 주기 · 미리 해 보기

ubuntu
ubuntu@myUbuntu:~$ chmod +x sysinfo.txt
ubuntu@myUbuntu:~$ ls -l sysinfo.txt
-rwxrwxr-x 1 ubuntu ubuntu 123 … sysinfo.txt
ubuntu@myUbuntu:~$ ./sysinfo.txt
./sysinfo.txt: line 1: Linux: command not found
왜 또 오류일까? 이번에는 권한 문제가 아닙니다. 실행은 되었지만, 파일 안의 첫 줄 Linux myUbuntu …를 Bash가 명령으로 읽으려 했고 Linux라는 명령은 없기 때문입니다. 실행 권한이 있어도, 내용이 명령이어야 실행된다는 것을 알 수 있습니다.

2. 기호 방식 읽는 법

누구에게

u · g · o · a

user(소유자) · group · others · all(모두). 생략하면 모두에게

어떻게

+ · - · =

+ 추가 · - 제거 · = 정확히 이것만

무엇을

r · w · x

읽기 · 쓰기 · 실행

명령결과
chmod +x 파일모두에게 실행 권한 추가
chmod u+x 파일소유자에게만 실행 권한 추가
chmod go-w 파일그룹과 기타에서 쓰기 권한 제거
chmod o-rwx 파일기타 사용자의 권한을 모두 제거
chmod u=rw,go=r 파일소유자는 읽기·쓰기, 나머지는 읽기만으로 정확히 설정

WHY

리눅스에서 그룹 계정을 쓰는 근본적인 이유는 ‘효율적인 권한 관리’와 ‘보안 및 협업의 균형’ 때문입니다.

리눅스는 기본적으로 다중 사용자(Multi-user) 환경을 전제로 설계되었기 때문에, 사용자 수가 늘어날수록 개별 계정 단위로 권한을 관리하는 것은 불가능에 가깝습니다.

1. 대규모 권한 관리의 효율화 (중복 작업 제거)

  • 개별 관리의 한계: 50명의 개발자에게 특정 프로젝트 폴더의 읽기·쓰기 권한을 주어야 한다면, 그룹이 없을 경우 50명 각각에 대해 파일 권한을 일일이 수정해야 합니다.
  • 그룹 적용 시: dev_team이라는 그룹을 하나 만들고 폴더의 소유 그룹을 dev_team으로 설정한 뒤, 사용자를 그 그룹에 넣기만 하면 한 번에 해결됩니다.

2. 신규 입사 및 퇴사(인사 이동) 처리 단순화

새 팀원이 합류했을 때 파일 수백 개의 권한을 다시 줄 필요 없이, 사용자를 기존 그룹에 추가하기만 하면 즉시 모든 권한을 상속받습니다. 반대로 팀을 옮기거나 퇴사하면 그룹에서 제외하는 즉시 모든 접근 권한이 한 번에 회수되므로 관리 실수를 막습니다.

3. 최소 권한 원칙(PoLP)과 보안

시스템 관리 시 최고 관리자(root) 계정의 비밀번호를 여러 사람이 공유하는 것은 매우 위험합니다. 작업 성격에 맞게 역할을 분리한 그룹(웹 서버 관리 www-data, 시스템 관리자 sudo 또는 wheel, 백업 담당 그룹 등)을 두고 필요한 사용자에게만 그 그룹 권한을 주어 사고와 보안 위협을 최소화합니다.

4. 안전하고 격리된 협업 환경 구축

특정 디렉터리에 SetGID 비트 등을 함께 설정하면, 여러 사용자가 협업 폴더 안에서 각자 파일을 만들어도 모든 파일의 소유 그룹이 동일하게 유지됩니다. 다른 부서나 외부 계정(Others)에는 아무 권한도 주지 않으면서, 같은 그룹원끼리만 읽고 수정하는 안전한 공유 공간이 만들어집니다.

SPECIAL BITS

권한 숫자는 원래 네 자리다

리눅스 권한 숫자는 원래부터 4자리입니다. 평소 쓰던 3자리는 맨 앞의 0을 생략한 것뿐입니다.

자리1번째2번째3번째4번째
대상특수 권한소유자 (User)그룹 (Group)기타 (Others)
평소 표기0 (생략됨)7 (rwx)5 (r-x)5 (r-x)
SetGID 적용27 (rwx)5 (r-x)5 (r-x)

chmod 755 = 사실상 chmod 0755(특수 권한 없음) · chmod 2755 = 맨 앞자리에 2를 넣어 SetGID를 켜겠다는 뜻

1번째 자리의 숫자 계산법

뒤의 3자리를 r(4) + w(2) + x(1)로 더하듯이, 맨 앞자리도 고유 숫자를 더해서 만듭니다.

숫자이름뜻
4SetUID실행 파일에 붙으면 파일 주인의 권한으로 실행된다
2SetGID디렉터리에 붙으면 그 안의 새 파일이 디렉터리의 그룹을 물려받는다
1Sticky Bit모두가 쓰는 디렉터리에서 자기 파일만 지울 수 있게 한다

맨 앞에 2를 쓰고 나머지 3자리는 평소 권한을 이어 붙입니다. 2 + 770 → 2770, 2 + 755 → 2755. 기호 방식은 chmod g+s 대상.

ubuntu@myUbuntu:~$ ls -ld /srv/project/front

IN THE WILD

SetUID와 Sticky Bit는 이미 쓰이고 있다

특수 권한은 우리가 처음 만든 것이 아닙니다. 시스템에 이미 적용된 대표 사례 두 개를 직접 확인합니다.

1. SetUID · 비밀번호 변경 명령

ubuntu
ubuntu@myUbuntu:~$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root … /usr/bin/passwd

일반 사용자가 자기 비밀번호를 바꾸려면 /etc/shadow를 고쳐야 하는데, 이 파일은 root만 쓸 수 있습니다. passwd 명령에 SetUID(s)가 붙어 있어서, 누가 실행하든 파일 주인인 root의 권한으로 실행되기 때문에 비밀번호 변경이 가능합니다.

SetUID는 함부로 주지 않는다 내가 만든 스크립트에 SetUID를 붙이면, 그 스크립트를 실행하는 모든 사람이 주인의 권한을 쓰게 됩니다. 공격자가 노리는 대표적인 통로라서, 점검 시 sudo find / -perm -4000 -type f로 목록을 확인합니다.

2. Sticky Bit · 모두가 쓰는 임시 폴더

ubuntu
ubuntu@myUbuntu:~$ ls -ld /tmp
drwxrwxrwt … root root … /tmp

/tmp는 누구나 파일을 만들 수 있는 폴더(rwxrwxrwx)입니다. 그대로 두면 남의 파일도 지울 수 있게 됩니다. 마지막 칸의 t(Sticky Bit)가 “지우는 것은 자기 파일만”이라는 제한을 겁니다.

표기 정리

특수 권한숫자보이는 자리표기
SetUID4000소유자의 x 자리-rwsr-xr-x
SetGID2000그룹의 x 자리drwxrws---
Sticky Bit1000기타의 x 자리drwxrwxrwt

실행 권한이 없는데 특수 권한만 있으면 대문자(S, T)로 표시됩니다. 대문자가 보이면 x를 빠뜨린 설정 실수일 때가 많습니다.
