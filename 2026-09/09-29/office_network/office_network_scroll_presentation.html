Office Network
장애 분석 실습

정상 통신을 먼저 확인한 뒤, Gateway → DNS → HTTP/TCP 장애를 순서대로 만들어 보면서 “통신이 안 된다”는 현상을 패킷 관점에서 단계적으로 좁혀가는 실습입니다.

정상 구성 확인→장애 발생→패킷/증상 관찰→원인 구간 특정
발표 시작 멘트 — “이번 실습의 핵심은 단순히 Ping 성공/실패를 보는 것이 아니라, 어느 단계에서 통신이 멈췄는지를 구분하는 것입니다.”
1

네트워크 구성

개발팀과 운영팀을 서로 다른 VLAN으로 분리하고, L3 Switch가 두 VLAN 사이의 통신을 담당하도록 구성했습니다.

Packet Tracer에서 구성한 기본 토폴로지

구성 장비

L3 Switch 1대 — Inter-VLAN Routing

L2 Switch 2대 — 각 VLAN 단말 연결

DEV-PC 2대 — VLAN 10

OPS-PC 2대 — VLAN 20

Server 1대 — DNS + Web

한 문장으로: “팀별 VLAN은 분리되어 있지만, L3 Switch를 통해 서로 통신할 수 있는 구조”입니다.
2

VLAN과 IP 구성

발표에서는 모든 IP를 외울 필요 없이, 10번 VLAN = 개발팀, 20번 VLAN = 운영팀이라는 구조만 먼저 이해시키면 됩니다.

3

이번 실습에서 볼 3가지 프로토콜

프로토콜을 계층별로 나누면 장애 지점을 찾기가 훨씬 쉬워집니다.

ARP

“이 IP의 MAC은 누구?”

같은 LAN에서 IP 주소에 대응하는 MAC 주소를 찾습니다. Request는 Broadcast, Reply는 보통 Unicast입니다.

ICMP

“IP 통신이 되는가?”

ping에서 사용됩니다. Echo Request와 Echo Reply로 네트워크 도달 가능성을 확인합니다.

TCP

“서비스 연결이 되는가?”

3-way handshake로 연결을 만들고, 순서·재전송 등을 통해 신뢰성 있는 통신을 제공합니다.

웹 접속을 단순화하면 ARP → (필요 시 DNS) → TCP → HTTP 순서로 생각할 수 있습니다.
4

정상 상태: 먼저 “되는 상태”를 확인

장애 분석 전에 정상 패킷 흐름을 알아야, 장애 상태에서 무엇이 사라졌는지 비교할 수 있습니다.

정상 통신 시 Simulation 화면

5

장애 1 — Gateway 주소 오류

OPS-PC1의 정상 Gateway 192.168.20.1을 존재하지 않는 192.168.20.254로 바꿨습니다.

OPS-PC의 Default Gateway를 192.168.20.254로 변경
왜 통신이 실패할까?

다른 네트워크로 가려면 PC는 먼저 Gateway에게 프레임을 보내야 합니다.

하지만 잘못 입력한 192.168.20.254는 실제 장비가 아니므로, 그 IP의 MAC 주소를 얻을 수 없습니다.

즉, ARP Request는 발생하지만 ARP Reply가 오지 않습니다.

정상

ARP Target: 192.168.20.1

ARP Reply: 있음

ICMP 전달: 성공

Gateway 장애

ARP Target: 192.168.20.254

ARP Reply: 없음

ICMP 전달: 진행되지 못함

Simulation에서 ARP 단계에서 반복되거나 이후 통신이 이어지지 않는 모습을 확인
발표 포인트 — “Ping 실패 자체보다 중요한 것은, 그 앞 단계인 ARP에서 이미 Gateway의 MAC을 얻지 못했다는 점입니다.”
6

장애 2 — DNS 서비스 중지

이번에는 네트워크 자체는 정상으로 두고, Server의 DNS 서비스만 OFF했습니다.

Server → Services → DNS 설정 화면

DNS의 역할

사람은 www.company.local처럼 이름을 사용하지만, 실제 네트워크 통신은 IP 주소를 사용합니다.

DNS는 이 이름을 IP 주소로 바꾸는 역할을 합니다.

따라서 DNS가 멈춰도 IP 자체로 하는 통신은 살아 있을 수 있습니다.
도메인 이름으로 접속 시 실패
DNS 요청은 발생하지만 정상 응답이 없는 상황
가능

ping 192.168.10.100

서버 IP에 직접 접근

실패 가능

www.company.local

이름 → IP 변환이 필요

발표 포인트 — “IP로는 되는데 이름으로 안 된다면, 네트워크 전체보다 DNS를 먼저 의심할 수 있습니다.”
7

장애 3 — HTTP/TCP 서비스 장애

DNS는 정상으로 유지하고, HTTP 서비스만 OFF해서 “서버는 살아 있지만 웹 서비스만 죽은 상태”를 만들었습니다.

정상 상태에서는 웹 페이지가 표시됨
HTTP 서비스 중지 후 웹 접속 실패
Ping
정상 가능
서버까지 IP 통신은 됩니다.
DNS
정상
도메인 이름을 IP로 해석할 수 있습니다.
HTTP
실패
최종 웹 서비스가 응답하지 않습니다.
즉, “서버까지 가는 길”과 “서버의 웹 서비스”는 별개의 문제입니다.

장애 분석 순서

현장에서 “인터넷이 안 됩니다”라는 말만 듣고 바로 한 원인을 찍지 않고, 아래처럼 아래 계층부터 단계적으로 확인합니다.

1

ARP / Gateway 확인

같은 네트워크 또는 다음 홉의 MAC을 얻을 수 있는가?

2

ICMP / IP 통신 확인

목적지 IP까지 패킷이 도달하고 응답이 오는가?

3

DNS 확인

도메인 이름이 IP 주소로 정상 변환되는가?

4

TCP / HTTP 확인

목적지 서비스 포트와 실제 애플리케이션이 응답하는가?

발표 멘트 — “핵심은 어디까지는 되고 어디서부터 안 되는지를 찾는 것입니다. 그 경계가 곧 장애 원인을 좁히는 단서가 됩니다.”
Conclusion
“통신 실패”를
단계별 원인으로 바꾸는 것이 목표

Gateway 장애는 ARP·경로 단계, DNS 장애는 이름 해석 단계, HTTP/TCP 장애는 최종 서비스 단계에서 구분할 수 있었습니다.

최종 한 줄 요약: 패킷을 계층별·프로토콜별로 순서대로 확인하면, 단순히 “안 된다”에서 끝나지 않고 장애 발생 범위를 빠르게 좁힐 수 있습니다.
