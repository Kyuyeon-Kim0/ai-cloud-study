장애의 상당수는 코드가 아니라 환경에서 옵니다. 개발에서는 되고 운영에서는 안 되는 상황, 스케줄러에 등록했더니 실패하는 상황, 컨테이너로 옮기니 파일을 찾지 못하는 상황이 모두 여기에 속합니다.

시스템 엔지니어가 이것을 알아야 하는 이유
  • 운영체제가 달라지면 무엇이 달라지는지 판단할 수 있다
  • “설치했는데 없다”는 상황의 원인을 스스로 찾을 수 있다
  • 실행 위치에 따라 경로가 달라지는 구조를 이해한다
  • 어디서 실행해도 같은 곳을 가리키는 기준점을 잡을 수 있다
코드를 고치기 전에 어디서 실행되는지부터 확인합니다. 이 판단이 되지 않으면 원인을 코드에서만 찾다가 시간을 소모하게 됩니다.

컨테이너와 같은 줄기입니다

가상환경이 라이브러리를 격리한다면, 이후 과정에서 배우는 컨테이너는 운영체제 환경 전체를 격리합니다. “같은 환경을 어디서나 재현한다”는 목적이 동일합니다.

환경을 기록으로 남기는 방법

어떤 라이브러리를 어떤 버전으로 설치했는지 파일로 남겨 두면 다른 장비에서 같은 환경을 다시 만들 수 있습니다. 서버에 배포하거나 동료에게 전달할 때 필요한 절차입니다.

단계내용
설치 목록 저장현재 환경의 라이브러리와 버전을 requirements.txt로 기록
저장소에 포함이 파일은 Git에 함께 올립니다. 코드만으로는 환경을 알 수 없습니다
다른 장비에서 복원같은 파일을 읽어 동일한 버전으로 설치
버전 고정 여부운영 배포는 버전을 고정합니다. 자동 업그레이드로 동작이 바뀌는 것을 막기 위해서입니다

이후 과정의 컨테이너 이미지 작성에서도 같은 파일을 사용합니다. 환경을 코드처럼 관리한다는 개념의 출발점입니다.

설치 관련 자주 겪는 상황

증상확인할 것
설치했는데 찾지 못함설치한 파이썬과 실행한 파이썬이 같은지 — sys.executable 확인
권한 오류로 설치 실패시스템 파이썬에 설치를 시도한 경우. 가상환경을 사용하면 발생하지 않습니다
버전이 맞지 않는다는 메시지라이브러리가 요구하는 파이썬 버전 확인
서버에서만 실패인터넷이 차단된 환경일 수 있습니다. 사내 저장소나 오프라인 설치가 필요합니다

예방 규칙  파일과 폴더 이름은 영문 소문자와 하이픈으로 통일합니다. 공백과 한글은 사용하지 않습니다. Git 저장소에서 동일한 규칙을 적용하는 이유와 같습니다.

컨테이너에서는 경로가 다릅니다

컨테이너 내부에는 호스트의 폴더가 존재하지 않습니다. 필요한 폴더를 볼륨으로 연결해야 하며, 연결된 경로의 이름도 별도로 지정합니다.

호스트 C:\ai-starter\images→볼륨 연결→컨테이너 /app/images
그래서 경로는 설정으로 분리합니다

같은 코드가 로컬·서버·컨테이너에서 모두 동작해야 합니다. 경로를 코드에 직접 작성하면 환경마다 수정이 필요하고, 어느 것이 최신인지 관리가 어려워집니다.

Git에서 주의할 점

비어 있는 폴더는 Git이 기록하지 않습니다  logs/나 output/처럼 결과가 저장되는 폴더는 일반적으로 .gitignore로 제외합니다. 그러면 폴더 자체가 저장소에 포함되지 않아, 다른 사람이 내려받아 실행하면 해당 폴더가 없다는 오류가 발생합니다. 코드에서 폴더가 없으면 생성하도록 처리해 두면 이 문제가 발생하지 않습니다.

어디서 실행해도 같은 곳을 가리키게

앞에서 본 문제의 해결책입니다. 실행 위치가 아니라 이 코드 파일이 놓인 자리를 기준으로 삼으면, 어떤 방식으로 실행하든 같은 폴더를 가리킵니다.

세 조각으로 되어 있습니다

기준점 잡기PYTHON
from pathlib import Path BASE = Path(__file__).resolve().parent # ① ② ③
① __file__이 파일 자신의 경로
파이썬이 자동으로 넣어 주는 값입니다. 직접 만들지 않아도 이미 들어 있습니다. 실행 방식에 따라 run.py처럼 짧게 들어올 수도, 전체 경로로 들어올 수도 있습니다.
② resolve()완전한 경로로 정리
상대경로를 절대경로로 바꾸고, 경로 안의 ..을 정리하고, 바로가기(심볼릭 링크)를 실제 위치로 풀어 줍니다. 어떤 형태로 들어와도 같은 결과가 나오게 만드는 단계입니다.
③ parent파일명을 떼고 폴더만
C:\project\run.py → C:\project. 기준으로 삼고 싶은 것은 파일이 아니라 그 파일이 들어 있는 폴더이기 때문입니다.

이어서 읽으면 이렇습니다. “이 파일이 → 정확히 어디 있는지 확정하고 → 그 폴더를 기준으로 삼는다.”

__file__이 없는 경우

대화형 환경에서는 동작하지 않습니다  터미널에서 python만 입력한 대화형 셸이나 일부 노트북 환경에는 __file__이 존재하지 않습니다. 파일로 저장된 스크립트에만 있는 값이기 때문입니다. NameError가 발생하면 이 경우를 의심합니다.
양쪽 모두에서 동작하게PYTHON
try: BASE = Path(__file__).resolve().parent except NameError: BASE = Path.cwd() # 현재 폴더로 대체

더 나아가면 — 경로를 밖에서 주입

스크립트 기준으로 잡아도 한계가 있습니다. 운영 환경에서는 데이터가 전혀 다른 위치에 있을 수 있습니다. 이때는 경로를 코드가 아니라 실행 시점에 전달합니다.

환경변수로 받기PYTHON
import os from pathlib import Path BASE = Path(__file__).resolve().parent # 환경변수가 있으면 그것을, 없으면 기본값을 사용 IMAGES = Path(os.getenv("IMAGE_DIR", BASE / "images"))

컨테이너를 실행할 때 IMAGE_DIR=/app/images처럼 지정하면 코드를 수정하지 않고 위치를 바꿀 수 있습니다. 개발·테스트·운영이 같은 코드를 사용하게 됩니다.

계산한 값과 화면의 값이 다를 때

측정을 하다 보면 직접 계산한 값과 화면에 표시된 값이 일치하지 않는 상황을 만납니다. 대부분 계산이 틀린 것이 아니라 기준이 다른 것입니다.

1000인가 1024인가

표기기준사용처
KB · MB · GB1000배씩저장장치 제조사, 통신 속도
KiB · MiB · GiB1024배씩정확히 구분하기 위한 공식 표기
OS 표시1024배인데 GB로 표기Windows 탐색기, 작업 관리자
512GB 디스크가 476GB로 표시되는 이유  제조사는 512 × 1000³바이트를 512GB로 판매합니다. 운영체제는 같은 바이트 수를 1024³으로 나누어 표시합니다. 그래서 476이 됩니다. 용량이 줄어든 것이 아니라 나누는 기준이 다릅니다.

바이트와 비트

Byte · B

저장 단위

파일 크기, 메모리 용량. 1바이트 = 8비트.

bit · b

전송 단위

네트워크 속도. 100Mbps는 초당 약 12.5MB입니다.

회선 속도가 500Mbps인데 다운로드가 60MB/s 내외인 이유가 이것입니다. 대문자 B와 소문자 b는 서로 다른 단위입니다.

소수는 정확하지 않습니다

파이썬에서 확인PYTHON
>>> 0.1 + 0.2 0.30000000000000004 >>> 0.1 + 0.2 == 0.3 False

컴퓨터는 소수를 2진수로 근사하여 저장합니다. 0.1은 2진수로 정확히 표현되지 않아 미세한 오차가 남습니다. 결함이 아니라 모든 언어에서 동일한 현상입니다.

측정값을 비교할 때  소수를 ==로 비교하지 않습니다. 차이가 충분히 작은지로 판단하거나 비교 전에 반올림합니다. 금액처럼 정확성이 필요한 영역에서는 소수 대신 정수 단위나 전용 자료형을 사용합니다.

파일 크기와 메모리 크기는 다르다

5MB 사진을 열었더니 메모리가 24MB 증가합니다. 오류가 아닙니다. 저장된 형태와 펼쳐진 형태가 다르기 때문입니다. 이것을 모르면 측정 결과를 해석할 수 없습니다.

이미지는 숫자의 격자입니다

픽셀Pixel
이미지를 구성하는 점 하나. 1920×1080이면 약 207만 개입니다.
채널Channel
한 점의 색을 구성하는 성분. 컬러는 빨강·초록·파랑 세 개, 흑백은 하나입니다.
비트 깊이Bit depth
한 채널을 몇 단계로 표현하는지. 일반적으로 8비트(0~255)이므로 한 채널이 1바이트입니다.

메모리 크기는 계산됩니다

펼쳐진 이미지의 크기계산
가로 × 세로 × 채널 수 × 채널당 바이트 1920 × 1080 × 3 × 1 = 6,220,800 바이트 ≈ 5.9 MB 3840 × 2160 × 3 × 1 = 24,883,200 바이트 ≈ 23.7 MB
핵심

메모리 크기는 해상도로 결정됩니다. 파일이 몇 MB인지와 관계가 없습니다. 같은 4K 사진이 2MB로 압축되어 있든 15MB든, 메모리에 펼치면 모두 약 24MB입니다.

파일 크기가 다른 이유

사진 파일은 압축되어 저장됩니다. 하늘처럼 유사한 색이 넓게 이어지면 크게 줄어들고, 잔디나 모래처럼 복잡하면 덜 줄어듭니다. 같은 해상도라도 내용에 따라 파일 크기가 달라집니다.

형식압축 방식특징
JPG손실 압축크게 줄어들지만 원본으로 완전히 복원되지 않음. 재저장할 때마다 품질이 저하됩니다
PNG무손실 압축원본 그대로 복원. 압축률은 낮음. 투명 배경 지원
BMP거의 압축 없음파일 크기가 메모리 크기와 거의 같음
WEBP손실·무손실 모두웹에서 널리 사용. 동일 품질에서 용량이 작음
측정에서 의미하는 것  JPG를 읽는 시간에는 압축을 해제하는 시간이 포함됩니다. 파일이 작다고 빨리 읽히는 것이 아닙니다. 메모리는 해상도가, 시간은 압축 방식이 좌우합니다.

RGB와 BGR

대부분의 도구는 빨강·초록·파랑 순서로 처리하지만 OpenCV는 파랑·초록·빨강 순서를 사용합니다. 초기 구현의 관행이 유지된 것입니다. 이 차이를 인지하지 못하면 빨강과 파랑이 뒤바뀐 상태로 저장됩니다. 색상이 이상할 때 가장 먼저 확인할 지점입니다.

컴퓨터는 글자를 숫자로 저장합니다. 어떤 숫자가 어떤 글자인지 정한 약속이 인코딩입니다. 저장할 때와 읽을 때 다른 약속을 사용하면 글자가 깨집니다.

두 가지 방식

이름범위사용처
UTF-8전 세계 모든 문자현재 표준. 웹·리눅스·Git·파이썬
CP949 · EUC-KR한글과 영문 위주구형 Windows 프로그램, 오래된 CSV
깨짐의 정체  UTF-8로 저장한 한글을 CP949로 읽으면 의미를 알 수 없는 기호가 표시됩니다. 파일이 손상된 것이 아니라 해석 방식이 어긋난 것입니다. 올바른 인코딩으로 다시 읽으면 정상적으로 표시됩니다.

인코딩 (계속) 31

BOM

일부 편집기는 UTF-8 파일 맨 앞에 보이지 않는 표시를 추가합니다. 화면에는 나타나지 않지만 프로그램이 읽으면 첫 글자가 비정상으로 인식됩니다. CSV의 첫 열 이름이 깨져 보이거나 스크립트의 첫 줄이 인식되지 않는 원인입니다. 저장 시 “BOM 없는 UTF-8”을 선택하면 해결됩니다.

확인과 예방

상황조치

파일·폴더 이름영문 소문자와 하이픈. 공백과 한글 제외

깨졌을 때 진단하는 순서

순서확인판단

예방 원칙

파일을 열 때 항상 인코딩을 명시하고, 파일명과 열 이름은 영문으로 작성합니다. 이 두 가지로 인코딩 문제의 대부분이 해결됩니다.

생겼을 때

장애 대응은 속도가 중요합니다. 오류 메시지를 읽을 수 있으면 몇 분, 읽지 못하면 몇 시간이 소요됩니다.

시스템 엔지니어가 이것을 알아야 하는 이유
  • 오류 메시지에서 원인과 위치를 스스로 찾을 수 있다
  • 자주 발생하는 오류의 유형을 구분할 수 있다
  • AI에게 오류를 전달할 때 무엇을 함께 줘야 하는지 안다
  • 오류 없이 실패하는 경우를 검증하는 코드를 넣을 수 있다
더 위험한 것은 오류 없이 잘못된 결과가 쌓이는 경우입니다. 조용한 실패는 한참 뒤에 발견되고, 그때는 이미 데이터가 오염된 상태입니다.
