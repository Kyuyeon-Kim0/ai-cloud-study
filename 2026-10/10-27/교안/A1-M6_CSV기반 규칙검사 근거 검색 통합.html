01. 업무 시나리오와 통합 목표

이미 만든 기술을 또 배우는 것이 아니라, 하나의 업무 요청을 실제 웹 검사 서비스로 끝까지 처리한다.

완성 목표: A1에서 각각 만들었던 규칙 검사·근거 검색·평가·전처리를 하나의 FastAPI 웹 서비스로 묶고, 검사 후 근거와 이력을 조회한다. AI 생성·벡터 DB·RAG는 아직 사용하지 않는다.

1-1. 이번 모듈에서 해결할 실제 업무

웹 개발팀이 새 상품 신청 화면을 완성했다고 가정하자. 담당자는 배포 전에 이미지, 링크, 입력 필드의 작성 기준을 확인해야 한다. 검사자가 HTML을 읽어 규칙을 하나씩 대조한다면 화면이 바뀔 때마다 같은 일을 반복하게 된다. 반대로 자동 검사 프로그램만 제공하면 어떤 규칙 때문에 검토해야 하는지, 비슷한 사내 정책이 있는지, 이전에 무엇을 검사했는지를 확인하기 어렵다.

이번 M6에서 만드는 것은 배포용 HTML 검사 웹 서비스의 첫 통합 버전이다. 브라우저에 HTML을 입력하고 검사 버튼을 누르면 Python 규칙 엔진이 실행된다. 부적합·판단 보류 항목은 원본 규칙 CSV의 ID에 정확히 연결되고, TF-IDF나 BM25가 관련된 다른 규칙 후보를 제안한다. 검사할 때마다 MySQL에 별도 기록을 남겨 이력 화면에서 다시 조회한다.

처음부터 끝까지 하나의 업무 샘플

진행업무 담당자의 행동시스템 내부 처리확인할 결과
① 요청개발팀이 HTML을 제출한다sample.html 또는 웹 텍스트 입력대상 URL 자동 수집은 하지 않음
② 규칙 확정현재 유효한 정책을 확인한다rules.csv에서 applied 7건 선택proposed 1건 제외
③ 자동 판정검사 실행 버튼을 누른다M2 checker.py를 호출passed/failed/cantTell/inapplicable
④ 근거 연결왜 이런 결과인지 확인한다rule_id로 CSV 원본 행과 트리 경로 직접 조회확정 규칙의 정확한 출처
⑤ 참고 검색다른 관련 규칙을 찾는다M3 TF-IDF 또는 BM25로 후보 문서 검색, M5 전처리 사용검색 점수는 참고값

왜 기존 파일을 새로 만들지 않는가?

선행 모듈현재 가져오는 자산이 모듈에서 재사용할 목적

A1-M3search_engine.pyTF-IDF·BM25로 참고 규칙 후보 검색
A1-M4metrics.py, gold/*.csv통합 후 이전 검사·검색 품질 유지 확인
A1-M5cleaner.py검색 본문 공백·Unicode 정제 및 정책 버전 유지

무엇이 이번 M6의 결과물인가?

실행되는 웹 화면(HTML 입력·검사·근거·이력), FastAPI(검사·이력·상태 조회), MySQL 테이블(검사 실행·상세 결과), 캐시 정책(규칙·트리 변경 감지), Docker 이미지와 Helm Chart가 하나로 묶인다.

판정 범위 주의: 이 시스템은 정적 HTML 일부를 검사하는 자체 규칙 엔진이다. failed는 해당 자체 검사 조건의 실패이며 공식 WCAG 인증 결과가 아니다. cantTell은 결함 확정이 아니라 추가 검토가 필요하다는 뜻이다.

02. CSV 규칙·검색·결과·이력 계약

같은 CSV를 판정 원본과 검색 원본으로 재사용하되 직접 근거와 검색 후보를 구분한다.

2-1. 입력과 출력은 왜 계약(Contract)으로 정의하나?

M2에서는 Python 함수를 직접 실행했지만 웹 서비스에는 UI·API·DB·검색기가 연결된다. 각자 임의의 키를 반환하면 시스템이 커질수록 데이터를 변환하는 코드가 늘어난다. 따라서 사용자 요청과 응답, DB 저장 필드를 같은 의미로 고정해야 한다. 이를 인터페이스 계약이라고 한다.

API 입력 샘플

POST /api/inspect
Content-Type: application/json

{
  "html": "<a href='/notice'>더보기</a>",
  "method": "bm25",
  "k": 2
}

결과 JSON 구조: 직접 연결과 검색 후보는 다르다

{
  "run_id": "실행마다 새로 발급되는 UUID",
  "cache_hit": false,
  "rule_hash": "rules.csv의 SHA-256",
  "tree_hash": "rule_tree.csv의 SHA-256",
  "preprocess_version": "nfc-ws-v1",
  "summary": {
    "rule_target_pairs": 3,
    "failed": 1,
    "cantTell": 1,
    "passed": 1,
    "inapplicable": 0
  },
  "review_items": [
    {
      "rule_id": "COMP-LINK-001",
      "outcome": "failed",
      "direct_rule": {
        "rule_id": "COMP-LINK-001",
        "source_file": "rules.csv",
        "tree_path": "웹 정합성 검사 규칙 > 회사 작성 정책 > ..."

        {"rule_id": "LINK-002", "score": 0.56}

위 응답은 구조 설명용 축약 샘플이며 점수·집계·트리 표기를 포함해 실제 호출 결과와 동일하다고 주장하는 예시는 아니다. 실제 확인은 웹 화면과 /docs에서 수행한다.

항목어디서 왔나의미RAG로 확장할 때

direct_ruleM2 CSV + 트리판정에 직접 적용된 규칙 기록판정 출처로 고정
related_rule_candidatesM3 검색 결과주제적으로 비슷한 다른 규칙참고 후보·재검색에 사용

rule_hash/tree_hash실제 CSV 파일 내용변경 감지와 캐시 갱신 기준색인·임베딩 갱신 판단
run_id새 검사 실행실행 단위의 DB 기본키LLM 검토·재검사와 이력 연계

2-2. 데이터는 어디에 저장하나?

저장 위치담당 데이터쓰지 않는 용도
rules.csv적용 규칙·설명·표준 참고 링크검사 실행 이력 저장소 아님
rule_tree.csv부모-자식 경로와 규칙 파일 참조규칙 본문 중복 저장 아님
inspection_runs실행 ID, 입력 해시, 규칙·트리 버전, 검색 설정, 요약, 배포 버전HTML 원문 보관하지 않음
inspection_findings대상+규칙별 상태, 이유, 직접 규칙 및 검색 후보검색 후보가 공식 위반 확정 아님

원본 HTML을 왜 저장하지 않는가?

사용자가 입력한 HTML에는 이름·이메일·내부 경로 등이 포함될 수 있다. 이 실습은 우선 입력 해시와 검사 결과만 저장하고 원본 HTML은 저장하지 않는다. 검사 결과 자체에도 민감한 텍스트가 유출될 수 있으므로 실제 개인정보가 포함된 페이지는 데모에 넣지 않는다. 추후 원본 보관이 필요해지면 접근권한·보존기간·삭제 절차를 별도로 설계한다.

03. 검사·검색 통합과 버전별 캐시

M2·M3·M5 코드를 재사용하고 M4 기준으로 회귀를 확인한다. 계산 캐시와 업무 이력을 분리한다.

3-1. M2 검사와 M3 검색을 어떻게 연결할까?

앞 모듈에서 각각 실행하던 함수를 호출하는 순서를 정하고, 공통 ID로 연결하면 된다. 검색기가 판정 결과를 바꾸거나 반대로 검사기가 유사도 점수를 계산하면 책임 경계가 무너진다. 검사→ID 직접 조회→관련 규칙 후보 검색의 세 단계를 분리한다.

from checker import load_rules, scan          # M2
from search_engine import build_documents, rank_bm25  # M3
from cleaner import clean_text                # M5

rules = load_rules(DATA / "rules.csv")
findings = scan(html, rules)
docs = build_documents(data_dir=DATA)

# 직접 연결: 검색 점수에 의존하지 않고 rule_id로 정확히 찾음
by_id = {doc.document_id: doc for doc in docs}
for finding in findings:
    doc = by_id[finding["rule_id"]]
    if finding["outcome"] in ("failed", "cantTell"):
        candidates = rank_bm25(clean_text(finding["reason"]), docs, top_k=3)
        print("직접 규칙:", doc.document_id)
        print("관련 검색 후보:", [(d.document_id, round(s, 3)) for d, s in candidates])

왜 직접 연결과 유사도 검색을 동시에 쓰나?

예를 들어 COMP-LINK-001 규칙이 부적합을 생성했다면 그 결과의 원본 규칙은 검색 점수가 가장 높은 문서가 아니라 반드시 COMP-LINK-001이다. 그러나 사용자는 이 문제가 표준 관련 링크 규칙과 어떻게 연결되는지도 알아야 하므로 BM25로 유사한 규칙을 추가 검색할 수 있다. 검색 후보가 부정확해도 실제 판정 출처는 바뀌지 않는다.

3-2. 캐시는 언제 필요하고 무엇이 바뀌면 무효화하나?

같은 HTML 검사와 같은 규칙 검색을 반복할 때 계산 비용을 줄이기 위해 결과 계산 캐시를 사용한다. 그러나 이전 결과를 캐시에서 읽었다고 해서 새로운 검사 실행을 저장하지 않는다면 감사·비교 이력이 사라진다. 따라서 계산 결과 재사용과 실행 기록 생성을 분리한다.

cache_key = (
    sha256(html.encode("utf-8")).hexdigest(),
    sha256(Path("data/rules.csv").read_bytes()).hexdigest(),
    sha256(Path("data/rule_tree.csv").read_bytes()).hexdigest(),
    PREPROCESS_VERSION,
    method,
    top_k,
)
# ① 똑같은 요청 → 계산 캐시 적중
# ② rules.csv 변경 → 규칙 해시 변경 → 캐시 폐기
# ③ rule_tree.csv 변경 → 트리 해시 변경 → 캐시 폐기
# ④ 전처리 정책 변경 → 캐시 키 변경
# ⑤ 방법 또는 k 변경 → 서로 다른 계산 캐시
# ⑥ 어떤 경우든 실행 기록은 MySQL에 새 run_id로 저장

핵심 제약: 이 예제 캐시는 각 Python 프로세스 안의 메모리에 있다. 멀티 Pod 사이에 캐시를 공유하거나 재배포 후 유지하지 않는다. M6에서는 캐시 키와 무효화 원리를 배우고, 다중 Pod 캐시 일관성은 후속 운영 단계에서 고도화한다.

버전 관리의 두 계층

버전의미검증 방식
rule_versionCSV 규칙 행의 논리 버전판정 결과마다 규칙 버전 기록
rule_hashCSV 원본 전체의 실제 내용 해시규칙값·설명이 달라져도 캐시 무효화
tree_hash트리 CSV 참조 관계 버전상위 규칙 경로 수정 시 재생성
preprocess_versionM5 정제 정책 버전검색 본문 처리 방식의 변화 추적
release_revision빌드한 Git 이미지 태그현재 서비스 배포 버전 추적

테스트 예시

python -m pytest -q
# 1. 검사 → 첫 실행 cache_hit=false
# 2. 동일 입력 재검사 → cache_hit=true / run_id는 다름
# 3. CSV 내용을 바꿈 → rule_hash 또는 tree_hash 변경
# 4. 다음 검사 → cache_hit=false

컨테이너 이미지는 불변이므로 가비아 K3s에서 CSV를 수동 편집하는 방식으로 갱신하지 않는다. Git으로 CSV를 변경하고 이미지를 새로 빌드·배포하면 새 Pod에서 새 데이터로 캐시를 시작한다. 로컬 파일 변경을 통한 캐시 실습과 운영 이미지 교체는 구분한다.

04. FastAPI·MySQL·검사 웹 화면

웹 브라우저에서 입력·검사·근거·이력 조회를 모두 수행한다.

4-1. 브라우저 화면에서 어디까지 확인할 수 있어야 할까?

이 모듈의 필수 결과물은 콘솔에서 JSON을 출력하는 프로그램이 아니다. 누구든 웹 브라우저에서 HTML을 제출하고, 결과를 읽고, 과거 검사 이력까지 다시 조회할 수 있어야 한다. 실습 ZIP의 web/index.html은 정적 페이지이고 실제 데이터는 FastAPI가 제공한다.

화면 구성사용자가 하는 일연동 API
검사 입력HTML을 붙여 넣고 TF-IDF/BM25·후보 수 선택POST /api/inspect
결과 요약검사 건수·부적합·판단 보류·직접 규칙 연결 수 확인검사 응답 summary

4-2. FastAPI 핵심 경로

@app.post("/api/inspect")
def inspect(body: InspectInput, _=Depends(auth)):
    result, cache_hit = service.inspect(body.html, body.method, body.k)
    run_id = store.save(result, cache_hit)  # 캐시 적중이어도 새 기록
    return {**result, "run_id": run_id, "cache_hit": cache_hit}

@app.get("/api/history")
def history(_=Depends(auth)):
    return store.history()

MySQL 저장 설계: 두 테이블로 시작

테이블핵심 컬럼무엇을 질문할 수 있나
inspection_runsid, created_at, input_hash, rule_hash, tree_hash, method, cache_hit, summary언제 어떤 규칙 버전으로 검사했는가?
inspection_findingsrun_id, target, rule_id, scope, outcome, message, evidence어떤 HTML 대상이 왜 검토 대상인가?

운영 DB 주의: 현재 MySQL은 Multipass VM에 존재한다. 가비아 K3s에서 VM의 MySQL을 쓸 경우 사설 연결·VPN 등 안전한 통신 경로가 먼저 필요하다. Windows PC의 127.0.0.1:3307 SSH 포트포워딩 주소를 가비아 Pod 안에서 그대로 사용할 수는 없다. 3306 공인 포트를 개방하지 않는다.

05. Git 이미지·Helm·가비아 K3s

이미 알고 있는 Docker·K3s·Helm을 재사용하여 서비스 배포와 실제 응답을 검증한다.

5-1. 기존 학습 경험을 이용해 Git → 컨테이너 → K3s로 배포한다

M6에서 Docker 설치·K3s 설치·Helm 명령어 기초를 다시 배우는 것이 목적은 아니다. 이전에 이미 학습한 도구를 사용해 같은 버전의 검사기·규칙 CSV·트리 CSV·웹 화면을 하나의 이미지에 묶어 배포한다. Dockerfile은 이미지 패키징에 쓰고, 가비아 K3s는 기본 containerd를 이용해 컨테이너를 실행한다. 별도의 docker run 운영은 하지 않는다.

단계별 검증 책임

단계수행반드시 확인할 것
① 로컬 검증pytest + FastAPI 브라우저 검사CSV 7건 로딩, 화면, 이력·캐시
② Git 반영CSV·Python·테스트·Chart 변경 후 push이미지와 규칙 데이터가 같은 소스 버전
③ GitHub Actions테스트 후 SHA 이미지 빌드·GHCR push성공한 커밋의 이미지 주소
④ 가비아 K3s 배포기존 Helm Chart에 이미지 태그 지정배포 세대, readiness, Pod 안정성
⑤ 외부 응답 확인포트포워딩 또는 승인된 Ingress/HTTPS실제 검사→검색→MySQL 저장→이력 조회
⑥ 규칙 변경 검증규칙 CSV를 새 버전으로 빌드·배포새 버전 해시·캐시 갱신 확인

GitHub Actions가 하는 일

main 브랜치 push
   → Python 의존성 설치
   → pytest (M2/M3/M5 통합 + API/DB/캐시)
   → 컨테이너 이미지 빌드
   → ghcr.io/<owner>/<repo>:<commit_sha> 발행
   → 배포 담당자가 승인된 SHA로 Helm 갱신

이 코드는 CI와 수동 승인 Helm 릴리스를 결합한 방식이다. Git push만으로 Helm 릴리스가 자동 반영되는 완전한 GitOps는 아니다. A4에서 Argo CD, 환경 분리, 승인 정책, 자동 롤백 등을 더 깊게 다룬다.

helm upgrade --install a1-m6 ./chart/a1-m6   -n a1-m6 --create-namespace   --set image.repository=ghcr.io/YOUR-OWNER/YOUR-REPO   --set image.tag=ACTUAL_COMMIT_SHA

6-3. 이해도 점검·추가 실습

문제 1. TF-IDF 점수가 높은 규칙으로 검사 결과의 rule_id를 바꿔도 될까?

안 된다. 검사 결과는 M2 엔진이 적용한 규칙 ID에 직접 연결한다. 검색 후보는 관련 근거 탐색 보조 자료다.

문제 2. 같은 HTML을 재검사해 계산 캐시가 적중하면 검사 이력을 저장하지 않아도 될까?

아니다. 계산 최적화와 실행 이력은 별개다. 새 run_id가 발급되고 새 검사 기록이 생성되어야 한다.

문제 3. rules.csv 설명 문장만 바뀌었다. 캐시를 그대로 사용해도 될까?

안 된다. 설명은 검색 본문과 사용자에게 제시하는 근거를 바꿀 수 있다. 파일 전체 SHA-256 기준으로 무효화한다.

문제 4. 현재 VM의 MySQL을 가비아 Pod에서 그대로 127.0.0.1:3307로 연결해도 될까?

안 된다. 그 주소는 각각 자신의 로컬 루프백을 의미한다. 가비아 Pod에서 접근 가능한 별도의 안전한 통신 경로가 필요하다.

문제 5. A1-M6 서비스의 결과를 공식 WCAG 검사 완료라고 표시해도 될까?

안 된다. 정적 HTML 일부에 대한 자체 검사 조건을 실행한다. 공식 접근성 평가 전체를 대체하지 않는다.

선택형 확장 실습

  1. 웹 검사 화면의 검토 결과를 표준 관련·사내 정책으로 필터링한다.
  2. 규칙을 applied에서 proposed로 바꾼 뒤 판정·검색 대상 수가 바뀌는지 로컬에서 확인한다. 운영에서는 새 이미지로 배포한다.
  3. 검사 ID별로 같은 입력 해시, 다른 실행 시각·캐시 여부를 비교한다.
  4. MySQL 연결 장애를 로컬 테스트 환경에서 재현한 후 /health와 /ready의 차이를 설명한다.
