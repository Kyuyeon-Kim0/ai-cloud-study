A1-M5. 텍스트 전처리와 한국어 형태소 분석

A1-M2에서 rules.csv로 검사를 정의했고, A1-M3에서는 같은 CSV의 title·description·reason·limitation을 TF-IDF·BM25로 검색했다. A1-M4에서는 그 판정과 검색을 평가했다. 이제 검색할 한국어 문장의 품질을 살펴본다.

이번 업무 질문: 원본 규칙과 메타데이터를 훼손하지 않으면서, 표현이 조금 다른 질문도 검색할 수 있도록 텍스트를 어떻게 다룰까? 전처리가 항상 성능을 올리는 것은 아니며, 원본과 비교·검증할 수 있어야 한다.

01-1. 실제 업무 시나리오: 검색이 왜 흔들릴까?

개발자가 “aria-label이 있는 링크의 이름 후보는 어떻게 검사하나요?”라고 묻는다. 그런데 규칙 문서에는 aria-label, “링크 이름 후보”, “대체 텍스트 후보” 등 다른 표현이 들어 있다. 동일한 내용을 가리켜도 띄어쓰기, 기호, 한국어 조사·어미, 새 사내 용어 때문에 단어가 서로 다르게 처리될 수 있다.

우리의 목표는 규칙 판정을 다시 만드는 일이 아니다. M2 검사기와 M3 검색기에는 손대지 않고, 검색용 텍스트 복사본을 어떻게 정제하고 어떤 경우에 형태소 분석이 필요한지 판단하는 것이다.

순서실제 업무대상 데이터확인할 것
①A1-M2에서 규칙을 작성하고 검사rules.csv + rule_tree.csv검사 조건과 지식 원본은 그대로 유지
②A1-M3에서 근거를 검색규칙 설명 네 필드문장/띄어쓰기/기술 식별자의 차이 관찰
③A1-M5에서 복사본을 정제raw_text → clean_textWCAG 번호·aria-label·부정 표현 보존

⑤A1-M4 기준으로 필요할 때만 품질 확인기존 질문/정답 규칙 ID검색이 실제 개선되었는지 측정 — 점수 추측 금지

01-2. 텍스트 분석과 CSV 구조는 서로 다른 층이다

CSV는 규칙의 필드와 행을 구분하는 저장 형식이고, 전처리는 reason 등의 필드 안에 들어 있는 한국어 텍스트를 다룬다. 즉 CSV로 저장됐다는 이유만으로 형태소 분석이 끝난 것은 아니다.

구분A1-M2/3에서의 값A1-M5 처리 방침
검색 본문title, description, reason, limitation원본 보존 + 검색용 정제본 생성
고유 식별자rule_id, rule_version, policy_id원형 유지, 필요하면 정확 일치 검색

01-3. 현재 모듈과 후속 모듈의 경계

여기서는 정제, 유니코드·공백, OOV, 공백/문자/n-gram/형태소 분할, 품사·사용자 사전을 배운다. 형태소 분석기 Kiwi 실습은 선택형이다. 임베딩·LLM 토크나이저나 벡터 검색은 이 모듈의 실습 범위에 넣지 않는다. A1-M6에서는 검사·검색을 통합하고, 이후 A2에서 모델 기반 처리를 별도로 진행한다.

02. 정제와 정규화

정제(Cleaning)는 분석에 방해되는 잡음이나 불필요한 요소를 다루고, 정규화(Normalization)는 서로 다른 표기를 일정한 규칙으로 통일하는 일이다. 두 과정이 겹치기도 하지만 무조건 삭제하는 것이 핵심은 아니다.

02-1. 실제 입력에서 먼저 관찰할 문제

문제입력 예시접근 방법주의
공백·줄바꿈배송 빠름 연속 공백을 하나로표·코드의 줄바꿈은 유지해야 할 수 있음
HTML 마크업&lt;p&gt;공지&lt;/p&gt;텍스트 노드와 속성 추출을 구분alt·aria-label은 화면 글자가 아님
유니코드 표기완성형·조합형 한글NFC 등 정책 선택NFKC는 ① 등을 1로 바꿀 수 있음
기술 식별자IMG-001, WCAG 1.1.1원형 보존 또는 보존 예외 설정무분별한 정규식 삭제 금지
개인정보이메일·전화번호가 포함된 로그수집·검색 목적에 맞게 비식별화삭제·마스킹 정책을 별도로 정의

02-2. 최소 Python 실습: 공백과 유니코드

기초 실습은 별도 문장을 이용한다. unicodedata.normalize("NFC", ...)는 유니코드 표현을 표준적으로 정리하고, re.sub(r"\s+", " ", ...)는 줄바꿈·탭을 포함한 연속 공백을 하나로 바꾼다. repr()을 사용하면 보이지 않는 공백도 확인할 수 있다.

import re
import unicodedata

raw = "  [공지]   WCAG 2.4.4\n aria-label 을  확인하세요.  "
text = unicodedata.normalize("NFC", raw)
clean = re.sub(r"\s+", " ", text).strip()

print("원본:", repr(raw))
print("정제:", repr(clean))
print("보존:", "2.4.4" in clean, "aria-label" in clean)

실행 결과와 해석

원본: '  [공지]   WCAG 2.4.4\n aria-label 을  확인하세요.  '
정제: '[공지] WCAG 2.4.4 aria-label 을 확인하세요.'
보존: True True

여기서는 불필요한 공백만 다뤘으므로 규칙 ID와 하이픈이 그대로 남아 있다. 숫자·기호 삭제를 추가해도 된다는 뜻이 아니다. 전처리 전후의 의미 보존 여부를 확인해야 한다.

02-3. NFC와 NFKC를 무조건 같은 것으로 보면 안 된다

NFC는 표준적인 정규형 중 하나이고, NFKC는 호환 문자를 변환하는 경우가 있다. 예를 들어 원문 ①가 NFKC에서 1로 바뀔 수 있다. 번호·코드·브랜드명·법령 텍스트에 어떤 정규형을 쓸지는 목적에 따라 결정해야 한다.

import unicodedata
print(unicodedata.normalize("NFC", "①"))    # ①
print(unicodedata.normalize("NFKC", "①"))   # 1

02-4. HTML에서 글자만 추출하면 끝일까?

HTML에서 get_text()는 보이는 텍스트 노드를 모으는 데 유용하지만 이미지의 alt나 요소의 aria-label처럼 속성값으로 존재하는 접근성 정보는 별도로 추출해야 한다. 화면 텍스트와 속성 텍스트를 구분해 남겨야 규칙 검사·검색·향후 재검증에 활용할 수 있다.

from bs4 import BeautifulSoup

html = '<img src="a.png" alt="결제 안내"><a href="/ship" aria-label="배송 정책 자세히 보기">더보기</a>'
soup = BeautifulSoup(html, "html.parser")
print("화면 텍스트:", soup.get_text(" ", strip=True))
print("alt:", [x.get("alt") for x in soup.select("img[alt]")])
print("aria-label:", [x.get("aria-label") for x in soup.select("[aria-label]")])

결과 읽기: 화면 텍스트에는 더보기만 나올 수 있지만, 별도 목록에는 결제 안내, 배송 정책 자세히 보기가 남는다. 이 정보를 합칠지, 필드로 분리할지는 검색·판정 목적에 따라 결정한다.

기초 확인

" 오류 없음\nWCAG 2.4.4 "를 정제한 뒤 조항 번호가 보존되었는지 확인한다. “왜 숫자를 제거하지 않았나?”를 한 문장으로 설명한다.

트러블슈팅: 코드 블록이나 표 형태의 문서는 공백을 무조건 하나로 합치면 구조가 깨진다. 문서 종류별 전처리 정책을 다르게 두고, 원본은 그대로 보관한다.

02-5. 실제 rules.csv에는 무엇을 적용할까?

rule_id=LINK-001을 예로 들면, description에 포함된 aria-label과 reason의 서술문에서 반복 공백과 NFC만 우선 적용한다. rule_id, wcag_ref, status는 원래 값으로 유지한다. 전체 코드의 실행 예는 05_prepare_m2_documents.py를 참조한다.

M2의 규칙 판정에는 정제 텍스트를 다시 입력하지 않는다. 검사 조건인 operator, values를 임의로 바꾸면 규칙 자체가 달라진다.

03. OOV와 토큰 분할 방식

03-1. OOV는 왜 생기나?

OOV(Out-of-Vocabulary, 미등록 어휘)는 사용하는 사전이나 어휘 목록에 없는 단어를 뜻한다. 문제는 절대적인 단어의 종류가 아니라 어떤 사전·분석기·업무 도메인을 기준으로 하느냐에 따라 달라진다. 신제품명·신조어·내부 시스템 코드·기술 이름은 일반 사전에 없거나 기대와 다른 단위로 분리될 수 있다.

예를 들어 메타정합검증이라는 새 사내 기술명을 입력했을 때, 분석기가 이를 통째로 인식하지 못하고 여러 단위로 나누거나 불확실하게 해석할 수 있다. 이것이 반드시 [UNK]라는 하나의 토큰으로 출력된다는 뜻은 아니다. 분석기의 처리 방식에 따라 결과가 달라진다.

상황예시실제 영향
새로운 사내 용어메타정합검증하나의 개념이 쪼개져 검색이 불안정할 수 있음
영문과 기호가 결합aria-label, COMP-LINK-001하이픈 삭제나 분리가 식별자 검색을 훼손할 수 있음
띄어쓰기 변형규칙 검사기 / 규칙검사기같은 개념을 서로 다르게 취급할 수 있음
오탈자·구어 표현배쏭, 좋아용정규화·교정이 필요할 수도, 원문 보존이 필요할 수도 있음

03-2. 분할 단위를 선택할 때의 장단점

방법실제 처리 단위장점한계
공백 기준"배송이 빠르다" → 배송이 / 빠르다간단하고 빠름조사·어미 변형을 별도 단어로 취급
문자 단위배 / 송 / 이새 단어에도 기본 적용 가능문맥·단어 경계 정보 약함, 길이 증가
문자 n-gram"배송이" → 배송 / 송이 (2-gram)부분 문자열·오탈자에 비교적 강함불필요한 조합과 오탐 가능성
사전 기반 단어 분할사전에 있는 어휘 단위정해진 업무 용어에 일관성사전 미등록·갱신 문제
형태소 분석배송/명사 + 이/조사품사·어미·조사 해석에 유리사전·문맥·오분석·속도 비용 고려

선택 근거: OOV가 있다고 해서 반드시 한 가지 분석기를 도입해야 하는 것은 아니다. ID 검색이라면 원문 보존·정확한 문자열 처리가 우선일 수 있고, 한국어 일반 문장을 분석한다면 형태소와 품사 정보가 유용할 수 있다.

03-3. 독립 기초 실습: 같은 문장을 다르게 분리하기

text = "배송이 빠르지 않습니다"
print("공백:", text.split())
print("문자:", list(text.replace(" ", ""))[:8])

word = "배송이"
print("2-gram:", [word[i:i+2] for i in range(len(word)-1)])

출력에서 공백 분할은 두 단어를, 문자 분할은 더 작은 단위를, 2-gram은 겹치는 문자 조합을 만든다. 분할이 더 잘게 된다고 의미 분석이 자동으로 좋아지는 것은 아니다. 어떤 질문을 해결하려는지 먼저 정해야 한다.

03-4. OOV 대응 전략을 설계로 선택한다

목적우선 검토할 방법추가 판단
규칙 ID·표준 번호의 정확한 검색원문 보존, 구조화 필드, 일치 검색코드 변형을 금지할지?
일반 한국어의 어휘 통일형태소 분석·용어 사전품사 제거로 문맥이 훼손되는지?
오타가 포함된 고객 문장교정 후보, 원본 유지, n-gram자동 교정으로 의미가 바뀌지 않는지?
자주 바뀌는 신조어·도메인 명칭검토 후 사용자 사전 갱신사전 버전을 어떻게 재현할지?

OOV 여부는 고정된 정답이 아니라 어휘 목록·도메인·분석기 버전에 의존한다. 따라서 “미등록 어휘가 발견됐다”는 현상과 “검색 품질이 떨어졌다”는 결과를 구분해야 한다.

03-5. 우리 CSV의 OOV를 어디서 찾을까?

규칙 ID인 COMP-LINK-001, HTML 속성인 aria-label, 업무용어인 메타정합검증은 성격이 서로 다르다. 코드·속성 이름은 정확히 보존해서 필터/문자열 일치가 우선이고, 사전에 없는 한국어 업무용어는 형태소 분석기·업무 사전 보완 여부를 판단한다. 분석기의 미등록 어휘와 M3 검색기의 미등록 특징(어휘)은 같은 말처럼 다루지 않는다.

[UNK] 등 특수 표식은 특정 토큰화 체계에서 쓰일 수 있지만, 모든 형태소 분석기가 OOV를 한 토큰으로 처리한다는 뜻은 아니다.

04. 한국어 형태소·품사와 Kiwi

04-1. 한국어는 왜 형태소 분석이 유용할까?

한국어는 교착어(agglutinative language)의 성격이 강해, 어근·어간 등에 조사와 어미 같은 문법 요소가 결합해 다양한 표현을 만든다. 공백 기준 분할만으로는 배송이와 배송은이 같은 명사 배송에서 나온 표현이라는 점을 직접 알려주지 않는다.

형태소(morpheme)는 뜻이나 문법 기능을 갖는 최소 언어 단위이다. 품사(part of speech)는 단어의 문법적 종류다. 형태소 분석기는 문장을 분석하여 각 단위의 형태와 품사 등을 반환한다.

구분예시설명
어근·어간먹-, 빠르-활용 과정에서 중심 의미를 담당
조사이/가, 은/는, 을/를체언 뒤에서 문법 관계 등을 나타냄
어미-다, -습니다서술어의 활용과 문장 끝 형태를 나타냄
형태소배송 / 이품사·문법 정보 단위로 더 잘게 분석

04-2. 자주 볼 품사 태그

태그품사예시·활용 시 주의
NNG일반명사배송, 서비스: 검색 키워드 후보

MAG일반부사매우·안: 감정·부정 정보를 포함할 수 있음

04-3. 선택 실습: Kiwi로 형태소 출력 확인

Kiwi는 Python에서 사용할 수 있는 한국어 형태소 분석기로 kiwipiepy 패키지를 통해 실행한다. 형태소의 form(형태), tag(품사), start(시작 위치), len(길이) 등을 확인할 수 있다. 결과는 사전·버전에 따라 달라질 수 있으므로 항상 실제 출력과 원문을 나란히 보며 해석한다.

# 설치: python -m pip install kiwipiepy
from kiwipiepy import Kiwi

kiwi = Kiwi()
text = "배송이 빠르지 않습니다."

for token in kiwi.tokenize(text):
    print(token.form, token.tag, token.start, token.len)

코드에서 처음 보는 부분 설명

구문역할결과에서 확인할 점
Kiwi()형태소 분석기를 초기화반복 호출 시 객체 재사용 가능
tokenize(text)문장을 형태소 단위로 분석단어가 분리되는 방식
token.form분석된 형태원문에 어떤 부분이 대응되는지
token.tag품사 정보명사·동사·어미·조사 구분
start / len원문 위치 정보전처리로 글자 위치가 달라지면 주의

04-4. 명사만 추출하면 왜 위험할까?

많은 텍스트 실습이 명사 추출부터 시작하지만, 모든 업무에 적합한 방법은 아니다. "배송이 빠르지 않습니다"에서 명사만 남기면 배송처럼 결과가 지나치게 짧아져 부정과 평가 정보를 잃는다. 따라서 형태소 분석은 단순한 단어 추출이 아니라 품사를 포함한 정보 선택의 문제로 이해해야 한다.

from kiwipiepy import Kiwi
kiwi = Kiwi()
text = "배송이 빠르지 않습니다."

nouns = [t.form for t in kiwi.tokenize(text) if t.tag in {"NNG", "NNP"}]
print("명사만:", nouns)
print("원본:", text)

트러블슈팅: 형태소 분석 결과가 기대와 달라도 곧바로 오류로 보지 않는다. 사전·문맥·입력 표기를 점검하고, 입력 텍스트가 원본과 달라졌는지 확인한다.

04-5. 형태소 분석 실습과 검색 성능은 분리한다

Kiwi가 메타정합검증을 원하는 단위로 분리했다는 사실만으로 검색 품질이 향상되지는 않는다. 색인 문서와 질의에 동일한 분할 정책을 적용했는지, 부정 표현과 규칙 식별자가 유지되는지 확인해야 한다. 이후 A1-M4 정답 질문으로 다시 측정할 수 있으나 M5에서 새 성능 수치를 임의로 만들지는 않는다.

06. 이해도 테스트·추가 실습·GPT 검토


형태소 분석기를 의무적으로 적용하는 것이 목표가 아니다. 원본을 유지하고, 텍스트 전처리 정책을 선택한 이유와 예상 위험을 설명할 수 있는가를 확인한다.


06-1. 이해도 테스트 — 먼저 답한 후 펼쳐보기


1. CSV 규칙을 이미 저장했는데 텍스트 전처리가 왜 필요한가?
해설: CSV는 행·열 구조이고 전처리는 description·reason 등 필드 내부 문장의 표현을 다루는 별개 작업이다.
2. WCAG 2.4.4에서 구두점·숫자를 제거하면 어떤 문제가 생기나?
해설: 정확한 조항 식별자를 잃어 관련 문서의 정확 검색·검증이 어려워질 수 있다.
3. OOV라면 반드시 [UNK]라는 값으로 처리되는가?
해설: 아니다. 어떤 어휘 목록에 없느냐에 따라 발생하고, 분석기/분할 방식마다 처리 방법이 다르다.
4. 한국어에서 명사만 남기면 위험한 문장을 들어보라.
해설: 예: “접근성이 좋지 않다”. 명사만 남기면 부정·판단 정보가 빠질 수 있다.
5. status=proposed 규칙을 현재 적용 중인 것처럼 검색해도 되는가?
해설: 안 된다. 승인·적용 여부는 메타데이터로 확인하고 기본 검색에서 제외한다.
6. 전처리된 결과로 M2의 rules.csv 원본을 덮어써도 되는가?
해설: 안 된다. 판정 조건은 원본을 유지하고, 검색용 파생 텍스트를 별도로 만든다.
7. Kiwi 사용자 사전 등록이 검색 성능 향상을 보장하는가?
해설: 아니다. 실제 분할 결과를 확인하고 동일 평가셋으로 검색 품질을 검증해야 한다.
8. M2의 트리와 RAG 메타데이터 연결을 어떻게 보존하나?
해설: 규칙 ID를 기준으로 rule_tree.csv의 file·node_id·parent_id·tree_path를 조인하고 그 값을 변경하지 않는다.
06-2. 순수 Python 필수 실습
실습 A — 변형을 최소화한다
01_cleaning_basics.py를 실행해 NFC와 반복 공백 정리를 확인한다. WCAG 2.4.4, aria-label, 부정 표현이 보존되는지 확인하고, NFKC가 일부 문자를 다르게 만드는 이유를 설명한다.

실습 C — M2 CSV 재사용
05_prepare_m2_documents.py를 실행한다. 기본 7건, proposed 포함 8건이 나오는 이유를 확인하고 각 레코드의 검색 본문·메타데이터·트리 경로를 구분한다. CSV 원본은 수정하지 않는다.
