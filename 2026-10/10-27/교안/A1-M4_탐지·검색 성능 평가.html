A1-M4. 탐지·검색 성능 평가

“동작한다”와 “정확하다”는 다릅니다. A1-M2가 판정한 결과와 A1-M3가 찾은 규칙 문서를 어떻게 객관적으로 검증할지 배웁니다.

02. 탐지 성능 — 혼동행렬·Precision·Recall·F1

작은 숫자를 직접 계산한 후, passed·failed·cantTell을 어떻게 취급할지 명확히 정합니다.

탐지 평가의 양성(Positive)은 해당 규칙상 조치가 필요한 failed이다. passed는 음성(Negative)이다. 표준 관련 검사와 사내 정책의 결과를 섞어 “WCAG 위반 확률”로 해석하지 않는다.

먼저 10건을 손으로 분류해 본다

가상의 검사 10건 중 실제로 조치가 필요한 건이 5건이라고 가정한다. 검사기가 그중 4건을 정확히 발견했지만, 조치가 필요하지 않은 2건도 잘못 경고했다.

구분정답: 조치 필요정답: 조치 불필요의미
검사기: 문제 발견TP = 4FP = 2발견한 6건 중 2건은 오탐
검사기: 문제 없음FN = 1TN = 3실제 문제 1건은 놓침

TP·FP·FN·TN은 어떤 관점의 약자인가?

True/False는 예측이 정답과 일치하는지, Positive/Negative는 문제를 발견했다고 판단했는지를 나타낸다. 따라서 FN은 “문제가 실제로 있었지만 놓친 사건”, FP는 “문제가 없는데 있다고 경고한 사건”이다. 취업 전 검사처럼 누락이 치명적인 업무는 FN을, 검토 인력이 부족한 업무는 FP를 특히 관리한다.

숫자로 지표를 계산한다

지표계산 과정결과·해석
Precision(정밀도)TP / (TP + FP) = 4 / 60.6667 · 경고한 6건 중 약 66.7%가 실제 문제
Recall(재현율)TP / (TP + FN) = 4 / 50.8000 · 실제 문제 5건 중 4건 발견
F12 × Precision × Recall / (Precision + Recall)0.7273 · 정밀도·재현율의 조화평균
Accuracy(정확도)(TP + TN) / 전체 = 7 / 100.7000 · 불균형 데이터에서는 착시 가능
# 01_basics_detection.py
from metrics import binary_scores
truth = [1]*5 + [0]*5
prediction = [1,1,1,1,0, 1,1,0,0,0]
s = binary_scores(truth, prediction)
print(s.tp, s.fp, s.fn, s.tn)  # 4 2 1 3
print(round(s.precision,4),round(s.recall,4),round(s.f1,4))
# 0.6667 0.8 0.7273

문제: cantTell을 무조건 빼면?

현재 M2는 passed / failed / cantTell / inapplicable 네 가지 결과를 출력한다. 판단 보류가 많아도 분류 결과가 좋아 보이는 오류를 피하려면, “이진 지표를 계산한 건수”와 “검토 대상 전체 건수”를 분리해서 보여줘야 한다.

상태평가 처리별도 확인할 내용
passed · failed사전 검토된 정답도 확정일 때 TP/FP/FN/TN 계산규칙 범위(scope)와 판정 단위 일치 여부
cantTell강제로 passed/failed로 바꾸지 않음보류 건수·사유·전문가 검토 필요성
inapplicable적용 대상이 아닌 사례로 별도 집계모든 HTML 요소를 분모에 넣지 않음
정답은 확정인데 예측이 보류이진 지표에서 제외하더라도 숨기지 않음판정 커버리지 저하로 별도 표시

decision_coverage = 확정 정답 중 검사기가 확정 결과를 낸 건수 ÷ 확정 정답 전체 건수. 예를 들어 확정 정답 20건 중 15건만 확정한 경우 커버리지는 75%다. 나머지를 빼고 계산한 F1만 제시하면 안 된다.

실습 질문

FP가 2건에서 1건으로 줄면 Precision은 얼마나 바뀌는가? FN을 1건 줄이면 Recall은 어떻게 달라지는가? 지표 변화가 업무에 어떤 이득을 주는지 먼저 예상하고 코드를 변경해 보자.

03. 근거 검색 — Recall@k·Hit@k·MRR

M3의 검색 점수가 아니라 정답 규칙 ID가 몇 위에 나타났는지 평가합니다.

탐지에서의 Recall은 누락된 위반 건수를 세지만, 검색의 Recall@k는 질문에 관련된 문서 ID가 상위 k위 안에 얼마나 들어왔는지 본다. 이름이 같아도 평가 대상이 다르다.

질문과 정답 규칙 ID를 먼저 정한다

예를 들어 사용자가 “더보기 링크의 목적과 회사 작성 정책을 설명해 줘”라고 질문했다면, 관련 문서는 LINK-002(표준 관련 맥락 검토), COMP-LINK-001(사내 금칙어) 두 건일 수 있다. 검색 점수 자체가 정답은 아니므로 평가 전에 관련 문서 목록을 만들어야 한다.

상위 검색 결과를 이용해 직접 계산한다

교육용 가상 검색에서 관련 문서가 {A,B,C} 세 개이고, 검색된 순서가 [X, A, B, C]라고 가정한다. X는 관련 없는 문서다.

지표k=3일 때 계산업무적 의미
Recall@3상위 3개 중 정답 2개 / 전체 정답 3개 = 2/3필요한 근거 중 얼마나 확보했나
Hit@3상위 3개 안에 정답이 한 개라도 있으므로 1관련 근거가 하나라도 검색됐나
RR@3첫 관련 문서 A의 순위 2 → 1/2첫 번째 유용한 근거를 얼마나 빨리 만나나
nDCG@3상위 순위의 관련성에 더 큰 가중치를 둠관련 문서가 앞에 배치됐는지

MRR@k(Mean Reciprocal Rank)은 질문 여러 개에 대한 RR@k의 평균이며, Hit@k 평균도 질문 단위의 적중률이 된다. nDCG@k는 관련도 등급까지 반영할 수 있는 지표지만 이 실습에서는 정답/비정답 이진 관련도로 계산한다. A2-M4에서 더 깊게 다룬다.

# 02_basics_retrieval.py
relevant = {'IMG-001', 'LINK-002', 'COMP-LINK-001'}
ranked = ['FORM-001', 'IMG-001', 'LINK-002', 'COMP-LINK-001']
s = retrieval_scores(relevant, ranked, k=3)
print(round(s['recall'],4))  # 0.6667
print(round(s['hit'],4))     # 1.0000
print(round(s['rr'],4))      # 0.5000

검색 결과가 2위여도 충분한가?

다음 질문을 살펴보자. Q02: 더보기 사내 링크 금지의 정답은 COMP-LINK-001이다. 실제 M3 검색기는 TF-IDF와 BM25 모두에서 COMP-LINK-002(“자세히” 제한)를 1위로, 진짜 정답을 2위로 반환한다. 그래서 Recall@1은 0이지만 Recall@2는 1이다. 이 사례는 M4에서 평가가 왜 필요한지 보여준다.

검색 평가의 함정잘못된 방식올바른 방식
점수 비교TF-IDF 0.25 vs BM25 14.1 → BM25가 더 정확각 알고리즘의 순위와 정답 ID로 비교
관련 문서 수가 다른 질문관련 문서 1건과 3건을 원점수로 비교Recall@k 등 질문별 비율 계산 후 평균
검토 중 규칙proposed를 현행 정답으로 취급applied 규칙을 기본 평가 대상으로 사용

05. 결과 해석·정답셋·트러블슈팅

점수가 높거나 낮을 때 무엇부터 확인해야 하는지, 높은 점수를 오해하지 않으려면 무엇을 기록해야 하는지 살펴봅니다.

실제 오류를 진단하는 질문을 먼저 만든다

평가 점수가 낮으면 곧바로 알고리즘을 바꾸기보다 정답셋이 맞는지 → 검색 대상이 맞는지 → 질문 표현이 맞는지 → 인덱스/버전이 최신인지 순서로 살펴보자.

증상가능한 원인확인 방법

정답셋은 어디에서 나와야 하나?

프로젝트에는 실제 독립 검토자 결과가 없으므로 본 실습의 검토 정답은 샘플 HTML과 규칙 조건을 읽어 만든 교육용 기준표다. 현업으로 확장하려면 규칙 조건별로 다양한 HTML 사례를 수집하고, 가능한 한 검사기 결과를 보기 전에 제3자가 판단하도록 해야 한다. 의견이 갈리는 사례는 정답을 억지로 확정하지 않고 cantTell과 검토 사유를 보존한다.

기준선을 저장해 두는 이유

다음 모듈에서 텍스트 전처리를 바꾸거나 A2에서 임베딩·벡터 DB를 추가하면 검색 결과는 달라진다. report.json에는 규칙 CSV, 트리 CSV, 샘플 HTML, 정답셋의 SHA-256 축약 해시를 기록한다. 이것이 같은 조건에서 비교했는지 확인하는 가장 간단한 출발점이다. 실제 배포에서는 검사기·인덱스·모델 버전도 함께 관리한다.

개선 실험의 책임 구분

A1-M4는 어떻게 측정할지 배우는 단계다. 벡터 DB·LLM 답변 품질 평가는 A2-M4에서, 검색 품질을 운영 데이터로 체계적으로 개선하는 작업은 후속 고도화 과정에서 수행한다. 이 모듈에서는 성능 개선을 과도하게 주장하지 않는다.

06. 이해도 테스트·추가 실습·GPT 검토

계산·해석·데이터 일관성을 스스로 확인하고, 다음 모듈에서 재사용할 평가 기준을 정리합니다.

이해도 테스트 — 먼저 예상한 뒤 해설을 펼친다

문제 1. TP=4, FP=2, FN=1일 때 정밀도·재현율·F1은?

해설: Precision=4/6=0.6667, Recall=4/5=0.8, F1=8/11≈0.7273. TN은 이 세 지표의 계산식에 직접 들어가지 않는다.

문제 2. M2 검사기의 failed를 “WCAG 위반 확정”으로 불러도 되나?

해설: 안 된다. M2는 자체 정의한 검사 조건만 평가한다. 표준 관련 조건 실패와 인증 여부는 별도다.

문제 3. 판단 보류 30건을 제외한 F1이 1이라면 검사가 완벽한가?

해설: 아니다. 커버리지와 보류 사유를 반드시 함께 제시해야 하며, 보류 제외는 성능을 왜곡할 수 있다.

문제 4. 관련 규칙 2개 중 Top-2에서 1개만 찾았다면 Recall@2는?

해설: 1/2 = 0.5다. Hit@2는 하나 이상 찾았으므로 1이다.

문제 5. 첫 관련 문서가 3위이고 다른 관련 문서는 검색되지 않았다면 RR@3은?

해설: 1/3≈0.3333이다. MRR은 이런 reciprocal rank를 여러 질문에 대해 평균 낸다.

문제 6. TF-IDF 점수 0.2, BM25 점수 10 중 더 정확한 검색은?

해설: 원시 점수의 절대값만으로 비교할 수 없다. 질문별 정답 규칙 ID와 순위 기반 지표를 사용해야 한다.

문제 7. status=proposed인 규칙을 평가 정답에 섞으면?

해설: 아직 유효하지 않은 규칙이 현재 정책 근거로 취급될 위험이 생긴다. 적용 상태·시점을 보존해 필터링한다.

문제 8. 교육용 22건 검사 정답 일치율 100%는 현업 완전 정확도인가?

해설: 아니다. 동일한 샘플 기반의 한정된 규칙 조건 결과일 뿐이며 독립적인 실제 데이터에서 별도 검증이 필요하다.

추가 실습 1. 검사 결과에 잘못된 예측 하나를 넣어 본다

01_basics_detection.py에서 정상 항목에 대한 예측 0 하나를 1로 바꾸어 FP를 증가시켜 본다. Precision과 F1 변화가 계산식과 일치하는지 확인한다. 기존 M2 규칙 원본은 고치지 않는다.

추가 실습 2. Q02에서 Top-1과 Top-2를 비교한다

화면에서 Q02: 더보기 사내 링크 금지를 찾고 k를 1에서 2로 바꾼다. 두 검색기에서 정답 문서가 몇 위에 있는지, Recall@k와 RR@k가 왜 달라지는지 설명한다.

추가 실습 3. 평가 질문을 늘릴 때 무엇을 기록해야 할까?

gold/search_gold.csv에 새로운 질문 1건을 추가한다. 검색 결과를 먼저 확인하고 정답을 맞추는 대신, 질문의 목적을 읽고 관련 규칙을 먼저 지정한 후 검색을 실행한다. 이 질문을 튜닝과 최종 보고에 동시에 사용하지 않는 이유를 토론한다.

GPT 활용 — 평가 함수 검토 프롬프트

지금 작성한 검사·검색 평가 코드를 점검해 줘.
1. TP/FP/FN/TN의 양성 정의가 규칙의 failed와 일치하는지
2. cantTell·inapplicable을 숨기지 않고 별도로 기록하는지
3. Recall@k와 MRR이 관련 문서 ID 집합을 기준으로 계산되는지
4. proposed 규칙이 현행 검색과 평가에서 제외되는지
5. CSV·트리·검사기 결과의 규칙 ID가 일치하는지
6. 교육용 정답셋에 대한 높은 점수를 실무 성능으로 과장했는지
실제 코드/CSV에 없는 성능 값은 만들지 말고, 오류가 있으면 최소 수정안을 제시해 줘.
