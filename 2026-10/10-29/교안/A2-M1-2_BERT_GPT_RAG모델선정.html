01. BERT는 무엇이며 어떻게 학습하는가?

BERT(Bidirectional Encoder Representations from Transformers)는 Transformer의 Encoder를 중심으로 만든 언어 이해 모델이다. 이름 자체가 양방향 문맥 표현을 뜻한다.

BERT 입력에 등장하는 특수 토큰부터 알아보기

일반 단어가 아닌 특수 토큰(Special Token)은 문장의 시작·구분·학습할 빈칸처럼 모델에 필요한 표식을 붙인다. A2-M1-1에서 배운 PAD·UNK와 같은 종류의 약속이지만 용도는 다르다. 여기서 먼저 뜻을 알고 나면 뒤의 코드에서 처음 보는 기호가 갑자기 등장하지 않는다.

표기의미어디에 쓰이나?
[CLS]Classification: 입력 시퀀스 앞에 붙는 표식BERT의 문장 단위 분류에서는 이 위치의 문맥 표현을 활용할 수 있다. BERT가 모든 작업에서 이 토큰으로만 결과를 내는 것은 아니다.
[SEP]Separator: 시퀀스 구분 및 끝 표식한 문장 끝 또는 두 문장 사이 경계를 표시한다.
[MASK]Masked Token: 가려진 위치 표식BERT의 MLM 사전학습에서 원래 토큰을 맞히도록 지정한 위치. 일반적인 문장 분류 입력에 항상 넣는 것은 아니다.
[PAD]Padding: 배치 길이 맞추기실제 내용이 없는 위치를 채우며 마스크로 제외한다.
[UNK]Unknown: 사전에 없는 토큰해당 토크나이저가 표현하지 못한 조각의 대체 표식이다.
한 문장과 두 문장의 입력 예시

[CLS] 오늘 점심은 [MASK] 를 먹었다 [SEP] — [MASK] 위치의 단어를 예측하는 교육용 예시다. [CLS] 질문 [SEP] 문서 [SEP] — 두 시퀀스를 구분한 형태다. 실제 토큰 분할과 ID는 모델 토크나이저에 따라 달라진다.

왜 등장했을까?

같은 단어도 앞뒤 문맥에 따라 의미가 달라진다. BERT는 입력 전체를 함께 참고해 각 토큰의 문맥 표현을 학습한다. 대표적인 사전학습 방식은 문장의 일부 토큰을 가리고 원래 토큰을 예측하는 Masked Language Modeling(MLM)이다.

후보는 설명용이며 실제 모델의 출력이나 순위를 뜻하지 않습니다.

사전학습과 파인튜닝의 차이

MLM으로 언어 표현을 학습한 뒤, 분류 작업에는 분류 헤드를 붙이고 정답 라벨로 추가 학습한다. 임베딩 검색에는 문장 유사도에 맞게 별도로 훈련된 인코더 모델이 유리하다.

bert_mask.py
from transformers import AutoTokenizer, AutoModelForMaskedLM, pipeline
name = "klue/bert-base"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForMaskedLM.from_pretrained(name)
print("마스크 토큰:", tok.mask_token, tok.mask_token_id)
text = "나는 오늘 점심으로 " + tok.mask_token + "를 먹었다."
ids = tok(text, return_tensors="pt")
print("입력 토큰:", tok.convert_ids_to_tokens(ids["input_ids"][0]))
print("토큰 ID:", ids["input_ids"][0].tolist())
print("다시 디코딩:", tok.decode(ids["input_ids"][0]))
fill = pipeline("fill-mask", model=model, tokenizer=tok, device=-1)
for result in fill(text, top_k=5):
    print(result["token_str"], round(result["score"], 4), result["sequence"])

02. GPT는 무엇이며 어떻게 생성하는가?

GPT(Generative Pre-trained Transformer)는 앞서 주어진 토큰을 바탕으로 다음 토큰을 예측하며 텍스트를 생성하는 모델 계열이다.

왜 필요한가?

문서 이해나 분류만으로는 답변을 새로 작성하기 어렵다. GPT 계열은 다음 토큰 예측을 반복해 문장을 이어 만든다. 일반적인 Decoder-only 언어 모델은 미래 토큰을 볼 수 없게 Causal Mask를 적용한다.

구성뜻예
Prompt이미 주어진 입력나는 오늘 점심으로
Next-token logits다음 토큰 후보들의 점수피자 / 밥 / 국수
Decoding확률 분포에서 토큰 선택Greedy 또는 샘플링
Autoregressive선택된 토큰을 붙이고 다음 토큰을 다시 예측나는 오늘 점심으로 피자를 …
KV Cache이전 위치의 Key·Value를 재사용해 중복 계산을 줄임긴 문장 생성 효율화

이어 말하기 학습 목업

왼쪽 문맥으로 다음 토큰 예측

나는오늘점심으로다음 토큰 ?

이미 입력된 토큰만 참고하여 다음 위치의 후보 분포를 만든 뒤 하나를 선택

피자를→먹었다→…

예시는 모델이 실제로 생성한 문장이 아니라 작동 방식 설명용입니다.

생성 옵션의 의미

max_new_tokens는 새로 생성할 토큰 수의 상한이다. do_sample=False는 일반적인 Greedy 계열 결정적 선택에 사용된다. temperature, top_k, top_p는 샘플링할 때 다양성을 조정한다.

gpt_generate.py
from transformers import AutoTokenizer, AutoModelForCausalLM, pipeline, set_seed
name = "skt/kogpt2-base-v2"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)
set_seed(42)
prompt = "나는 오늘 점심으로"
ids = tok(prompt)["input_ids"]
print("토큰:", tok.convert_ids_to_tokens(ids))
print("ID:", ids)
print("복원:", tok.decode(ids))
print("pad / eos:", tok.pad_token_id, tok.eos_token_id)
gen = pipeline("text-generation", model=model, tokenizer=tok, device=-1)
result = gen(prompt, do_sample=False, max_new_tokens=30,
             pad_token_id=tok.eos_token_id)
print(result[0]["generated_text"])

04. WordPiece·BPE·Unigram 실전 예제

단어 단위와 문자 단위의 단점을 살펴본 뒤, 서브워드가 왜 등장했는지 배우고 WordPiece·BPE·Unigram의 원리와 장단점을 비교한다.

서브워드(Subword)가 무엇인가?

서브워드는 하나의 단어 전체와 글자 하나 사이의 중간 크기 조각이다. 모든 단어를 통째로 저장하는 대신, 자주 등장하는 단어는 하나의 토큰으로, 드물거나 새로운 단어는 여러 조각으로 표현한다. 이 조각은 반드시 사전적 형태소나 의미 단위와 일치하는 것은 아니다.

방식예시: playing문제 또는 특징
단어 단위[playing]간단하지만 play, playing, played를 각각 등록하면 어휘가 커지고 미등록 단어 문제가 발생한다.
문자 단위[p,l,a,y,i,n,g]대부분의 글자를 표현하기 쉽지만 시퀀스가 길어지고 한 토큰이 지닌 언어 정보가 적다.
서브워드 단위[play, ##ing] (가상 WordPiece 사전)여러 단어가 play 조각을 공유한다. 어휘 크기와 입력 길이를 절충한다.

한국어에서도 학교에가 학교 + 에처럼 나뉠 수 있지만, 실제 분할은 학습된 어휘와 규칙에 따라 결정된다. 따라서 서브워드 토크나이저가 형태소 분석기를 그대로 대체하거나 문법적으로 정확하게 분리한다고 생각하면 안 된다.

왜 여러 서브워드 알고리즘이 생겼을까?

기본 아이디어는 같아도 어떤 조각을 어휘로 채택하는지와 입력 시 어떤 순서로 결합하는지가 다르다. 그 결과 어휘 크기, 미등록 토큰 처리, 한국어 문장 길이, 추론 비용에 차이가 생긴다. 어느 한 알고리즘이 언제나 우수하다고 단정할 수 없으므로 동일 문장으로 실제 모델을 비교한다.

WordPiece — BERT 계열

어휘 사전에 포함된 가능한 긴 부분 문자열부터 찾는 방식으로 인코딩한다. 단어 중간에 이어지는 조각은 ##로 표시할 수 있다. 예시 어휘에 play, ##ing이 있으면 playing → [play, ##ing]으로 표현할 수 있다. 실제 분리는 사전에 따라 달라진다.

순서입력/조회결과
①playing 전체가 어휘에 있는지 확인없음
②왼쪽에서 가장 긴 조각 play 선택play
③나머지 접미부를 중간 토큰으로 조회##ing
④원래 문자열 복원play + ing = playing
BPE 실습: 먼저 원문부터 확인

아래는 학습 원리를 보여주기 위한 가상 말뭉치입니다. 같은 글자 조각이 반복되어 자주 등장하는 인접 쌍을 병합할 수 있다는 점을 확인합니다. 실제 GPT-2 토크나이저가 아래 병합 순서를 그대로 따른다는 의미가 아닙니다.

원문에 등장한 단어반복 횟수초기 문자 분리
low5l | o | w
lower2l | o | w | e | r
lowest3l | o | w | e | s | t
newer2n | e | w | e | r

예를 들어 low의 문자 쌍 l+o와 o+w는 여러 단어에서 반복됩니다. 전체 말뭉치의 인접 쌍 빈도를 세고 가장 자주 등장한 쌍을 병합하는 절차를 반복합니다. 학습된 규칙에 따라 l|o|w → lo|w → low처럼 조각이 변할 수 있습니다.

새로운 원문 lower를 인코딩할 때는 low|e|r 또는 low|er처럼 학습된 병합 규칙에 존재하는 조합만 만들어집니다. BPE의 병합 규칙을 모르는 상태에서 최종 분할을 단정하지 않습니다.

BPE — GPT-2 등에서 사용

BPE는 학습 말뭉치에 많이 반복되는 인접 기호 쌍을 반복해서 병합해 토큰 목록과 병합 규칙을 구성한다. 예를 들어 l o w에서 l+o → lo, lo+w → low 같은 규칙이 학습될 수 있다. 이는 빈도나 학습된 병합 순서에 따른 예시이며 무조건 그 순서로 합쳐지는 것은 아니다.

단계기호 배열설명
0l | o | w초기 기호
1lo | w병합 규칙 적용
2low다음 규칙이 존재하면 결합
실제 GPT-2Byte-level BPE문자를 UTF-8 바이트 수준으로 다루므로 공백 표시도 특수하게 보일 수 있음

두 방식의 핵심 차이

비교WordPieceBPE
사전 학습문장 확률을 높이는 병합 기준빈번한 기호 쌍의 순차 병합
인코딩Longest-match 기반 조회학습된 병합 규칙 적용

WordPiece와 BPE의 장단점은 무엇인가?

방식장점한계·주의점
WordPiece자주 쓰이는 부분 문자열을 재사용해 단어 단위보다 어휘 수를 절약할 수 있고, ## 경계가 읽기 쉽다. BERT 계열에서 널리 검증되었다.사전에 적합한 조각이 없으면 [UNK]가 발생할 수 있으며, 토크나이저 구현에 따라 전체 단어가 UNK로 바뀌기도 한다. 일반적인 탐욕적 최장 일치가 문법적 최선은 아니다.
BPE빈번한 인접 기호를 병합해 반복 패턴을 압축한다. 바이트 기반 BPE는 임의의 UTF-8 텍스트도 표현할 수 있어 OOV에 강하다.병합 규칙에 따라 형태소 경계와 무관하게 나뉘며, 드문 한국어 표현에서 여러 토큰으로 길어질 수 있다. 모든 BPE가 바이트 기반인 것은 아니다.
Unigram여러 분할 후보를 확률적으로 평가할 수 있고, 일부 구현은 학습 중 분할 다양성을 활용할 수 있다.학습·분할 원리가 상대적으로 복잡하며, 품질은 말뭉치와 어휘 설계에 좌우된다.
선택 기준

WordPiece=언어 이해, BPE=생성이라는 등식은 성립하지 않는다. 모델 학습에 사용된 토크나이저와 정확히 일치시켜야 하며, 한국어 성능은 실제 토큰 수·복원 정확성·모델 성능으로 비교한다.

Unigram도 구분

Unigram은 여러 분할 후보 가운데 확률적 점수가 높은 분할을 찾는 계열이다. SentencePiece는 이처럼 BPE나 Unigram을 구현할 수 있는 라이브러리이므로, SentencePiece 자체를 별도의 한 가지 토큰화 알고리즘이라고 단정하지 않는다.

실제 토큰은 모델에서 확인

단순 예시는 원리 설명용이다. 정확한 결과는 tokenizer.tokenize(), convert_ids_to_tokens(), decode()로 확인한다.

tokenizer_wordpiece_bpe_real.py
from transformers import AutoTokenizer
samples = ["나는 오늘 점심으로 피자를 먹었다.", "파이썬으로 RAG 검색을 구현합니다."]
names = ["klue/bert-base", "skt/kogpt2-base-v2"]
for name in names:
    tok = AutoTokenizer.from_pretrained(name)
    print("\n모델:", name, "어휘 크기:", tok.vocab_size)
    for sent in samples:
        ids = tok(sent)["input_ids"]
        print("문장:",sent)
        print("토큰:",tok.convert_ids_to_tokens(ids))
        print("개수:",len(ids), "복원:",tok.decode(ids, skip_special_tokens=True))

07. 검색 임베딩·생성·평가의 역할

RAG에서는 문서를 찾는 모델과 답변을 생성하는 모델의 목적이 다르다. 동일한 벡터가 모든 업무를 자동으로 해결하는 것은 아니다.

검색과 생성 연결

왜 BERT와 GPT를 함께 배우나?

검색할 근거를 잘 찾는 문제와 읽기 쉬운 답을 만드는 문제는 서로 다르다. 둘의 차이를 알면 사용 목적에 맞는 모델을 선택하고, 모델 비용·응답 속도·출처 정확도까지 설계할 수 있다.

모델을 고르는 일이 왜 RAG의 출발점인가?

RAG는 한 모델이 모든 일을 하는 서비스가 아니다. 텍스트 분할과 길이 제한, 질문·문서의 검색 벡터, 검색 결과의 재정렬, 근거를 읽고 답하는 생성 모델이 각각 다른 조건을 요구한다. 검색이 틀리면 생성 모델이 훌륭해도 필요한 근거를 받지 못한다. 도구를 사용하는 에이전트에서는 이 문제에 더해 도구 호출 형식·인자·권한·실패 복구까지 검토해야 한다.

선정은 점수가 아니라 근거를 기록하는 과정

먼저 각 질문에 대한 Hit@1·Hit@2를 비교한다. 두 모델의 검색 품질이 비슷하다면 로딩을 제외한 추론 지연·메모리·배포 라이선스를 확인한다. 검색에 실패한 질문을 찾았다면 토큰 분할과 잘림, 관련 문서의 표현, 접두사 정책을 다시 조사한다. 세 문장의 교육용 점수만으로 실제 서비스에 적합하다고 확정하지 않는다.

선정 근거 작성 실습

  1. 두 모델의 토크나이저로 aria-label, WCAG 2.4.4, 메타정합검증을 인코딩하고 실제 토큰 수를 기록한다.
  2. 제공된 검색 비교 프로그램을 실행하여 모델별 문서 순위와 Hit@1·Hit@2를 적는다.
  3. 모델 A와 B 중 어떤 후보를 임시 선정했는지, 품질 근거와 아직 검증하지 못한 기준을 3문장으로 작성한다.
  4. 상위 문서가 맞더라도 생성 모델이 근거를 잘못 설명할 수 있는지 확인한다. 생성 품질은 검색 품질과 별도 평가한다.
  5. 도구 호출이 필요한 에이전트에서는 검색 점수와 별개로 도구 선택, 인자 검증, 권한과 중단 조건을 평가한다.
실습 결과의 의미

“가장 성능 좋은 모델”을 발표하는 것이 아니다. 우리 업무에서 정답 근거가 잘 검색되는지, 그 판단을 어떤 평가 자료로 뒷받침하는지를 설명할 수 있어야 한다. RAG 구현의 난이도는 이 선택과 검증에서 시작된다.

토크나이저를 독립적으로 갈아 끼우면 안 되는 이유

대부분의 사전학습 모델은 특정 어휘 사전, 토큰 ID, 임베딩 행렬 조합으로 학습되어 있다. BERT 모델에 GPT-2 토크나이저를 임의로 결합하면 ID가 가리키는 행의 의미가 달라지거나 크기가 맞지 않는다. 따라서 실무에서는 모델과 공식 토크나이저를 함께 후보로 선정하고, 같은 평가 질문으로 여러 모델 조합을 비교해야 한다.

모델 비교의 최소 실험 설계

후보 모델 두 개를 같은 5~20개 질문과 정답 문서 ID로 평가한다. 질의별 정답 근거가 검색 상위 1개 또는 3개에 들어오는지 기록한다. 벡터 차원이나 코사인 점수의 절대값만으로 모델을 평가하지 않는다.

측정의미주의
Hit@1, Hit@3정답 근거가 상위 1·3개 안에 있는 질문의 비율정답 문서 ID가 먼저 정의되어야 함
MRR첫 정답 문서가 나타난 순위를 역수로 평균상위 순위의 차이를 반영
토큰 수·Truncation한국어·기술 용어가 얼마나 잘리고 분할되는지모델의 전용 토크나이저 사용
추론 시간·메모리운영 환경에서 실행 가능한가CPU/GPU와 배치 크기를 함께 기록
라이선스·보안서비스 사용과 데이터 처리 가능 여부실제 모델 카드와 사내 정책 확인
실습의 결론을 먼저 정하지 않는다

어떤 임베딩 모델이 항상 더 좋다고 가정하지 않는다. 동일한 문서·질문·정답 ID로 비교하고, 검색 실패 문장을 분석한 다음 목적에 맞는 모델을 선택한다. 다음 실습은 후보 모델을 바꾸어 직접 비교할 수 있다.

08. 모델 선택 실험에서 RAG 연결까지

이 실습에서 확인할 핵심 질문: “왜 이 검색 모델을 골랐는가?”, “어떤 질문을 놓쳤는가?”, “검색 모델과 생성 모델이 서로 다른 이유는 무엇인가?” 코드를 실행한 뒤 두 모델의 Hit@1·Hit@2와 실패 사례를 반드시 비교한다.

후보 토크나이저·임베딩 모델의 차이를 확인하고, 정답 문서를 찾은 뒤 생성 모델에 전달하는 통합 실습.

이해도 확인

BERT가 문장을 자유롭게 계속 생성하지 않는 이유는?

기본 BERT는 인코더 기반 MLM을 중심으로 사전학습하며, GPT와 같은 다음 토큰 생성 헤드 및 인과적 생성 목적과 다르기 때문이다.

WordPiece의 ##은 모든 토크나이저에 공통인가?

아니다. WordPiece 계열에서 이어지는 조각을 표시하는 방식이며 GPT-2 Byte-level BPE는 다른 공백 표기를 사용한다.

RAG에서 GPT가 검색 엔진까지 대체하는가?

아니다. 검색용 임베딩·인덱스 및 규칙 필터와 생성 모델의 역할을 구분해야 한다.

마무리 실습의 목적

모델 선택이 왜 어려운지 이해하기 위해 다국어 임베딩 모델의 토크나이저와 평균 풀링을 사용해 문서를 검색하고, 검색한 근거를 별도 생성 모델에 전달합니다. 벡터 DB·LangChain 없이 RAG의 핵심 단계를 한 파일에 담았습니다. 아래 문서는 A1의 실제 rules.csv를 수정하거나 판정하지 않는 교육용 예시입니다.

마무리 실습의 학습 목표

코드 한 줄로 RAG를 만들었다고 끝나는 것이 아니다. 후보 임베딩 모델 선택 → 전용 토크나이저 확인 → 동일한 정답 질문으로 Hit@k 비교 → 검색 실패 확인 → 문서 근거를 생성 모델에 전달이라는 모델 선정과 검증의 전체 흐름을 직접 경험한다.

아래 파일의 MODEL_IDS를 바꾸면 각 모델에 맞는 토크나이저를 함께 불러온다. 실제 검색 품질은 모델을 내려받아 실행해야 확인할 수 있으며, 예제 데이터 3개 질문의 결과로 실무 성능을 단정해서는 안 된다.

검색과 생성의 연결 — 단계별로 확인

1. 임베딩 모델

intfloat/multilingual-e5-small 모델과 호환 토크나이저를 함께 불러옵니다.

2. 문서 임베딩

passage: 접두어가 붙은 문서를 토큰화해 은닉 벡터를 추출하고 Masked Mean Pooling과 L2 정규화를 적용합니다.

3. 질문 검색

query: 접두어로 질문 벡터를 만들고 정규화된 벡터 간 내적으로 코사인 유사도 Top-2 문서를 찾습니다.

4. 생성 모델

검색된 문서 ID와 본문만 근거로 답하도록 OpenAI API에 전달합니다. API 키가 없어도 검색 결과까지 확인할 수 있습니다.

A2_M1_2_mini_rag.py — 전체 실행 코드
"""A2-M1-2: RAG 모델 선택 미니 실습 — 모델 비교 -> 검색 -> 근거 기반 생성.
설치: pip install torch transformers openai python-dotenv
실행: python A2_M1_2_mini_rag.py
선택: .env 파일의 OPENAI_API_KEY=... 를 설정하면 생성 모델까지 호출한다.
"""
import os
import time
import torch
import torch.nn.functional as F
from dotenv import load_dotenv
from transformers import AutoTokenizer, AutoModel

# 1. 문서 원본: A1 규칙의 주제를 단순화한 학습용 데이터이며 실제 rules.csv가 아님.
DOCS = [
    {"id": "R01", "text": "의미 있는 이미지에는 이미지 목적을 설명하는 alt 대체 텍스트가 필요합니다."},
    {"id": "R02", "text": "장식용 이미지에는 문맥에 따라 빈 alt 속성(alt="")을 사용할 수 있습니다."},
    {"id": "R03", "text": "링크 텍스트만으로 링크의 목적을 이해할 수 있도록 작성해야 합니다."},
    {"id": "R04", "text": "입력 필드에는 화면 레이블 또는 접근 가능한 이름을 제공해야 합니다."},
    {"id": "R05", "text": "모호한 '자세히' 링크는 문맥에서 목적이 명확한지 확인해야 합니다."},
]

# 2. 질문마다 '정답 근거 문서 ID'를 미리 지정해야 검색 모델을 평가할 수 있음.
#    현업에서는 도메인 담당자가 정답 데이터를 검수해야 함.
TESTS = [
    {"question": "의미 있는 이미지에 alt가 없으면 무엇을 확인하나요?", "gold": "R01"},
    {"question": "장식용 이미지의 alt를 비워도 되나요?", "gold": "R02"},
    {"question": "입력창에 레이블이 필요한가요?", "gold": "R04"},
]

# 3. 모델 후보: 각각 자신의 토크나이저/임베딩 모델을 한 쌍으로 로딩.
#    두 번째 모델은 비교 실습용이며 다운로드 시간이 더 걸릴 수 있음.
MODEL_IDS = [
    "intfloat/multilingual-e5-small",
    "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2",
]
TOP_K = 2


def encode_texts(texts, tokenizer, model, prefix=""):
    """문장 -> 토큰 ID -> 은닉 벡터 -> PAD 제외 평균 -> L2 정규화."""
    batch = tokenizer([prefix + t for t in texts],
                      padding=True, truncation=True, max_length=256,
                      return_tensors="pt")
    with torch.inference_mode():  # 추론은 역전파가 필요 없으므로 메모리를 절약
        hidden = model(**batch).last_hidden_state  # (문장 수, 토큰 수, 차원)
    mask = batch["attention_mask"].unsqueeze(-1)  # PAD=0, 실제 토큰=1
    pooled = (hidden * mask).sum(dim=1) / mask.sum(dim=1).clamp(min=1)
    return F.normalize(pooled, p=2, dim=1)  # 내적을 코사인 유사도로 사용


def search(question, doc_vecs, tokenizer, model, q_prefix=""):
    """질문 벡터와 문서 벡터의 코사인 유사도 상위 문서 반환."""
    q = encode_texts([question], tokenizer, model, q_prefix)
    similarities = (q @ doc_vecs.T)[0]  # 정규화 후 내적 = 코사인 유사도
    scores, indices = torch.topk(similarities, k=min(TOP_K, len(DOCS)))
    return [(DOCS[idx], score) for score, idx in zip(scores.tolist(), indices.tolist())]


def main():
    load_dotenv()  # API 키는 .env로만 관리. 코드에 키 직접 입력 금지.
    reports = []
    best = None

    # 4. 후보별로 같은 문서/질문을 사용해야 공정한 비교가 됨.
    for model_id in MODEL_IDS:
        print("\n=== 모델 후보:", model_id, "===")
        started = time.perf_counter()
        tokenizer = AutoTokenizer.from_pretrained(model_id)
        model = AutoModel.from_pretrained(model_id).eval()
        # e5의 query:/passage: 접두사 정책을 반드시 지킨다.
        is_e5 = "multilingual-e5" in model_id
        q_prefix = "query: " if is_e5 else ""
        p_prefix = "passage: " if is_e5 else ""
        doc_vecs = encode_texts([d["text"] for d in DOCS], tokenizer, model, p_prefix)
        print("문서 벡터 shape:", tuple(doc_vecs.shape))
        print("질문 첫 문장 토큰 수:", len(tokenizer(q_prefix + TESTS[0]["question"])["input_ids"]))

        hits1 = hits2 = 0
        for case in TESTS:
            ranked = search(case["question"], doc_vecs, tokenizer, model, q_prefix)
            retrieved = [doc["id"] for doc, _ in ranked]
            hits1 += int(case["gold"] in retrieved[:1])
            hits2 += int(case["gold"] in retrieved[:2])
            print("질문:", case["question"])
            print("정답:", case["gold"], "검색:", [(d["id"], round(sc, 4)) for d, sc in ranked])
        score1, score2 = hits1 / len(TESTS), hits2 / len(TESTS)
        elapsed = time.perf_counter() - started  # 로딩+인코딩 포함: 순수 추론속도 아님
        reports.append((model_id, score1, score2, elapsed))
        print(f"Hit@1={score1:.2f}, Hit@2={score2:.2f}, 총시간={elapsed:.1f}초")
        # 실제 프로젝트라면 더 많은 평가 질문·품질·비용·라이선스를 함께 비교
        if best is None or (score1, score2) > (best[0], best[1]):
            best = (score1, score2, model_id, tokenizer, model, doc_vecs, q_prefix)

    print("\n=== 모델 비교표 (소규모 교육용 평가) ===")
    for mid, h1, h2, secs in reports:
        print(mid, f"Hit@1={h1:.2f} Hit@2={h2:.2f} 전체={secs:.1f}s")

    # 5. 선정 모델로 검색된 근거가 답변에 어떤 영향을 주는지 확인.
    _, _, selected_id, tokenizer, model, doc_vecs, q_prefix = best
    question = TESTS[0]["question"]
    ranked = search(question, doc_vecs, tokenizer, model, q_prefix)
    context = "\n".join(f"[{doc['id']}] {doc['text']}" for doc, _ in ranked)
    print("\n선정 모델:", selected_id, "\n검색 근거:\n", context)

    # 6. API 키가 없으면 검색 결과까지만 실행하여 비용 없이 원리 확인 가능.
    if not os.getenv("OPENAI_API_KEY"):
        print("OPENAI_API_KEY 미설정: 생성 단계 생략. .env에 키를 추가하면 실행됩니다.")
        return

    # 7. 생성 모델은 검색 모델과 역할이 다름: 검색 근거를 읽고 문장으로 답함.
    from openai import OpenAI
    client = OpenAI()
    response = client.responses.create(
        model="gpt-4.1-mini",  # 계정에서 이용 가능한 모델로 변경 가능
        instructions=("제공한 근거에만 기반하여 답하세요. 근거가 부족하면 보류하세요. "
                      "근거 문서 ID를 표시하세요. 검색 점수는 정답 확률이 아닙니다."),
        input=f"질문: {question}\n\n검색 근거:\n{context}",
    )
    print("\n[생성 답변]\n", response.output_text)


if __name__ == "__main__":
    main()
