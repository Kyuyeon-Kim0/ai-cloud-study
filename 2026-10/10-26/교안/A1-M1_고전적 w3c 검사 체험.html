시각장애인은 HTML을 어떻게 읽을까?

웹페이지를 볼 수 없어도 화면 낭독기(스크린리더)를 이용하면 글과 버튼, 링크 등의 정보를 음성으로 들을 수 있습니다. 그런데 이미지 안에 적힌 문구는 어떻게 전달할까요?

alt란 무엇인가?

alt는 alternative text(대체 텍스트)의 줄임말로, HTML의 <img> 요소에 이미지의 정보나 기능을 글로 제공하는 속성입니다. 화면을 볼 수 없는 사용자는 스크린리더를 통해 이 텍스트를 들을 수 있습니다. 예를 들어 alt="오늘 배송 마감 오후 6시"는 배너의 핵심 안내를 글로 전달합니다.

중요: 모든 이미지에 긴 설명을 적는 것은 아닙니다. 정보가 있는 이미지는 목적에 맞는 대체 텍스트를 제공하고, 단순 장식 이미지는 보통 alt=""로 처리합니다.

① 이미지에 왜 alt가 필요한가?

브라우저는 이미지를 화면에 표시하지만, 이미지 안의 글자나 의미를 HTML 텍스트처럼 자동으로 제공하지는 않습니다. 화면 낭독기는 이미지 요소에 제공된 접근 가능한 이름, 대표적으로 alt 대체 텍스트를 활용해 정보를 전달합니다.

예를 들어 배송 배너에 ‘오늘 배송 마감 오후 6시’라고 적혀 있다면, 이미지를 직접 보지 않아도 같은 핵심 정보를 알 수 있도록 alt에 해당 내용을 작성합니다.

배송 안내 배너

<img src="delivery.svg" alt="오늘 배송 마감 오후 6시">

버튼을 누르면 브라우저가 이미지의 alt 문구를 읽어 줍니다.

② 체험 결과 해석

버튼에서 들리는 ‘오늘 배송 마감 오후 6시’는 이미지에 작성한 alt 속성값입니다. 즉, 이미지의 픽셀을 분석해 음성을 생성한 것이 아니라 HTML에 작성된 대체 텍스트를 읽는 것입니다.

이번 버튼은 설치 없는 체험을 위한 Web Speech API 음성 합성으로, 실제 스크린리더를 대신하지 않습니다. 진짜 스크린리더는 웹페이지의 제목·링크·입력 요소·역할·상태 등 접근성 정보까지 해석합니다. 음성 기능은 브라우저와 운영체제의 한국어 음성 지원에 따라 달라질 수 있습니다.

③ W3C는 무엇을 요구하는가?

WCAG 2.2 성공 기준 1.1.1(비텍스트 콘텐츠)은 의미 있는 이미지 등 비텍스트 콘텐츠에 적절한 텍스트 대안을 제공하도록 요구합니다. 중요한 것은 alt라는 속성을 단순히 넣는 일이 아니라 이미지의 정보나 기능을 알맞게 전달하는 일입니다. 장식용 이미지는 일반적으로 alt=""로 처리합니다.

그렇다면 기존 W3C Validator와 접근성 검사 도구는 대체 텍스트가 제대로 작성됐는지 어디까지 검사할 수 있을까요? 이어지는 본문에서 고전적인 검사 방법과 그 한계를 확인합니다.

참고. 웹 접근성은 프론트엔드만의 일이 아니다

alt는 HTML 속성이지만, 이미지 설명을 누가 입력하고 어디에 저장하며 어떤 화면에 제공할지는 서비스 전체의 설계 문제입니다. 백엔드가 접근성에 필요한 데이터와 동작을 제공하지 않으면 프론트엔드만으로 해결하기 어려운 경우가 있습니다.

영역백엔드에서 고려할 일예시
이미지 대체 텍스트이미지 업로드 시 설명 입력·저장·조회 API 제공image_url과 alt_text를 함께 전달해 화면에서 alt로 출력
서버 생성 HTMLJSP·PHP·Django 등의 템플릿에서 올바른 문서 구조와 속성 출력lang="ko", 제목·폼의 label 연결
오류 안내API에서 항목별 오류 원인과 수정 가능한 안내 제공‘입력값 오류’보다 ‘비밀번호는 8자 이상이어야 합니다’
세션 시간 제한시간 만료 정책·연장 API를 마련하고 프론트엔드의 사전 경고와 연동세션 종료 전에 알림과 연장 선택지 제공. 보안상 예외가 있는지 함께 검토
인증·CAPTCHA이미지 판독이나 단일 기기 사용만 강제하지 않는 대체 수단 마련접근 가능한 다른 인증 방식 또는 음성·비시각적 대안 지원
생성 문서·이메일서버가 생성하는 문서와 메시지의 접근성 고려태그된 PDF 영수증, 이메일 이미지의 적절한 대체 텍스트

역할 구분: 프론트엔드는 정보를 사용자가 인식하고 조작할 수 있게 표현하고, 백엔드는 그 표현에 필요한 데이터·검증·인증 선택지·서버 정책을 제공합니다. 기획·콘텐츠 작성·QA까지 함께 검토해야 실제 접근성이 완성됩니다.

A1-M1. 고전적 W3C 검사 체험

학습 범위: HTML 문법 검사와 WCAG 접근성 평가는 별개다. 같은 HTML 사례를 실제 검사해 결과를 해석하고, 기존 방식에서 반복되는 불편함을 찾아낸다. 이 모듈에서는 새 탐지기나 RAG를 구현하지 않는다.

웹 접근성 검사라는 실무 소재로 기존 도구의 입력·출력과 한계를 이해하고, 이어지는 규칙 기반 탐지와 근거 검색을 준비한다.

이 Part의 질문은 하나다. “기존 방법으로 어떤 오류를 찾을 수 있고, 무엇은 찾기 어려운가?” 그 답이 다음 단계의 규칙 기반 판정과 근거 검색을 설계하는 출발점이 된다.

1. 개념: 정합성 판정이란?

정합성(Conformance)은 미리 정한 기준과 실제 결과물이 일치하는지를 확인하는 것이다. 예를 들어 HTML 문서의 구조가 HTML 표준에 맞는지, 이미지·링크·입력창이 웹 콘텐츠 접근성 지침(WCAG)의 요구사항을 충족하는지 검토한다. 다만 HTML 표준 적합성과 WCAG 접근성 적합성은 검사 기준부터 다르므로 같은 판정으로 취급하면 안 된다.

검사 영역기준 문서주요 질문대표 검사 방법
HTML 표준WHATWG HTML Living Standard태그 중첩, 필수 속성, 중복 ID 등이 올바른가?Nu Html Checker (W3C Validator)
웹 접근성W3C WCAG 2.2 (국내 적용 시 KWCAG 병행)보조기술 사용자를 포함해 콘텐츠와 기능에 접근할 수 있는가?Lighthouse·WAVE·axe 등의 자동 점검 + 수동 평가
사용성사용자 과업·디자인 지침문제없이 사용하더라도 이해하고 사용하기 편리한가?관찰, 시나리오 및 사용성 테스트

2. WCAG의 네 가지 원칙

WCAG는 접근성을 인식 가능(Perceivable), 운용 가능(Operable), 이해 가능(Understandable), 견고함(Robust)으로 조직한다. 각 원칙 아래에 구체적인 성공 기준이 있고, A·AA·AAA 등급이 정해져 있다. 일반적인 AA 적합성 검토는 A와 AA 성공 기준 모두를 만족해야 한다.

원칙쉽게 설명하면대표적인 질문

운용 가능마우스 외의 방식으로도 조작할 수 있는가?키보드로 링크와 버튼을 사용할 수 있는가?

견고함브라우저와 보조기술이 정보를 해석할 수 있는가?컨트롤의 이름·역할·상태를 프로그램이 알 수 있는가?

3. 이번 Module의 범위

기존 도구로 이미지의 alt, 링크의 이름·목적, 폼의 레이블, 키보드 접근을 우선 점검한다. 이는 뒤에서 동일한 검사 대상을 규칙 기반 방식으로 구현하고 평가하기 위한 공통 사례다. 이 Part 자체에서 특정 사이트의 WCAG AA 완전 적합성을 선언하지 않는다.

A1-M1 · 기존 검사 체계

M1-01 고전적 웹 접근성 정합성 판정 개요

웹페이지가 화면에 잘 보이는 것과 모든 사람이 이용할 수 있는 것은 다르다. 웹 접근성 평가는 기준을 정하고, 자동 검사로 확인할 수 있는 항목을 살핀 다음, 맥락과 사용 과정을 사람이 검토하는 방식으로 진행한다.

왜 검사하는가?

이미지가 전달하는 정보, 링크의 이동 목적, 입력창의 이름과 오류 안내는 화면에 보이는 외형만으로 모두 확인되지 않는다. 특히 키보드나 보조기술로 이용할 때 발생하는 문제는 직접 점검해야 한다. 따라서 웹 접근성 정합성 판정은 WCAG 성공 기준에 비추어 실제 콘텐츠와 동작을 검토하는 과정이다.

고전적 검사의 세 가지 축

구분확인하는 사항의미
① HTML 문법 검사잘못된 요소 중첩, 중복 ID, 필요한 속성 누락 등HTML 표준 적합성 검사이며, WCAG 전체의 합격 판정은 아니다.
② 접근성 자동 검사프로그램으로 판정 가능한 이름·속성·색 대비 등의 문제탐지 가능한 규칙은 빠르게 확인하지만 문맥 판단은 제한된다.
③ 수동 점검실제 이미지와 alt 내용 비교, 링크 맥락, 키보드 조작 등자동 검사로 확인할 수 없는 의미와 사용 경험을 검토한다.

자동 검사만으로는 충분하지 않다

예를 들어 매출 차트의 alt="아름다운 풍경"은 문자열이 존재하므로 일부 자동 검사에서 통과할 수 있다. 하지만 차트 내용을 전달하지 못하므로 사람이 실제 이미지와 비교해야 한다. 더보기 링크도 주변 제목이나 표의 행과 연결되는지에 따라 WCAG 2.4.4 평가가 달라질 수 있다.

기준 참고: WCAG 2.2 · WCAG-EM 평가 방법론. 구체적인 검사 도구 링크는 다음 실습 하단에 모아 두었다.

M1-02 HTML 검사 적용 실습

W3C Validator에 HTML 코드를 직접 붙여 넣어 문법 오류를 확인한다. 그런 다음 문법 검사에서 문제가 없더라도 접근성 검토가 남는 사례를 구분한다.

① W3C 검사기에 HTML 붙여 넣기

  1. W3C Markup Validation Service — Direct Input를 연다.
  2. 아래 코드를 전부 복사해 입력 영역에 붙여 넣는다.
  3. Check 버튼을 눌러 메시지에서 문제가 된 요소를 찾는다.
  4. 검사 메시지와 아래 해설을 대조하고, 검사기가 놓친 접근성 문제를 찾아본다.

이미지 파일은 실제로 없어도 HTML 소스의 문법 검사는 수행할 수 있다. 다만 이미지 내용과 alt의 의미가 맞는지 판단하려면 실제 이미지가 필요하다.

<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <title>웹 접근성 검사 실습</title>
</head>
<body>
  <h1>쇼핑몰 안내</h1>

  <!-- A: 이미지 대체 텍스트 누락 -->
  <img src="event.jpg">

  <!-- B: alt가 있지만 의미가 부족한 사례 -->
  <img src="sale.jpg" alt="이미지">

  <!-- C: 주변 맥락을 점검할 링크 -->
  <a href="/notice">더보기</a>

  <!-- D: 보이는 레이블 없이 placeholder만 사용 -->
  <input type="text" placeholder="이름">

  <!-- E: 중복된 id -->
  <label for="email">이메일</label>
  <input id="email" type="email">
  <input id="email" type="text">

  <!-- F: 의미가 적절하다고 가정한 예 -->
  <img src="logo.png" alt="쇼핑몰 로고">
</body>
</html>

사례HTML 문법 검사접근성 관점에서 추가로 확인할 점
A · alt 누락누락 관련 오류가 보고될 수 있다.이미지 정보를 대체할 텍스트가 필요한지, 무엇을 써야 하는지 확인

C · 더보기문법상 정상링크 자체 또는 프로그램으로 파악 가능한 맥락에서 목적이 드러나는가?
D · placeholder만 있는 input문법상 정상일 수 있다.보이는 안내와 프로그램이 인식하는 이름이 적절한가?
E · 중복 ID중복 ID 관련 오류레이블 연결과 스크립트 참조에 혼동을 주는가?

이 표는 개념을 설명하기 위한 예상 결과다. 실제 메시지 수와 표현은 검사 환경 및 Nu Html Checker 버전에 따라 다를 수 있다.

M1-03 방금 검사한 HTML에서 무엇을 알 수 있을까?

M1-02에서는 쇼핑몰 안내 페이지의 HTML을 W3C Validator에 붙여 넣었다. 여기서는 그 코드에 표시한 A~F 여섯 사례를 다시 보며 검사기가 찾은 것과 직접 확인해야 하는 것을 구분한다. 새로운 검사나 파일 작성은 하지 않는다.

① 먼저, Validator가 확인한 것부터 읽어 보자

W3C Validator는 HTML 표준에 맞게 작성됐는지 검사한다. 실습 코드에서 A의 alt 누락과 E의 중복 id는 문법 검사 메시지로 확인할 수 있다. 메시지의 행 번호와 원본 코드의 A·E 주석을 대조해 보자.

M1-02의 코드검사에서 확인할 내용의미
A · <img src="event.jpg">alt 관련 오류 메시지이미지에 필요한 대체 텍스트가 빠져 있다. 다만 적절한 대체 문구는 이미지의 용도를 보고 결정해야 한다.
E · id="email" 두 번중복 ID 관련 오류 메시지같은 문서에서 ID가 중복된다. 특히 label for="email"의 참조 대상이 모호해질 수 있다.

실제 메시지의 표현과 개수는 검사기 버전에 따라 차이가 있다. 중요한 것은 오류 개수가 아니라 어떤 코드가 왜 지적됐는지 이해하는 것이다.

② 그렇다면 메시지가 없던 B·C·D·F는 모두 적합할까?

그렇지 않다. HTML 문법상 허용되는 것과 접근성 기준에 맞는 것은 다르다. 같은 실습 코드에서 다음과 같은 질문이 남는다.

M1-02의 코드문법 검사가 놓칠 수 있는 질문고전적 확인 방법
B · alt="이미지"실제 할인 이미지의 정보나 목적이 이 문장만으로 전달되는가?이미지와 대체 텍스트를 사람이 비교
C · 더보기어떤 내용을 더 보는 링크인지 주변 제목이나 문맥에서 알 수 있는가?링크와 주변 콘텐츠를 함께 확인
D · placeholder="이름"입력창의 이름이 보조기술에 전달되는가? 입력 중에도 레이블이 식별되는가?접근성 도구로 이름 검사 + 화면·레이블 확인
F · alt="쇼핑몰 로고"실제 파일이 쇼핑몰 로고인가? 링크라면 기능도 적절히 전달되는가?실제 이미지와 사용 맥락을 확인

예를 들어 C의 더보기는 문구만 보면 모호하지만, 표에서 '주문번호 1234' 바로 옆에 있으면 링크 목적을 주변 맥락으로 알 수도 있다. 따라서 문자열 하나만 보고 모든 사례를 동일하게 부적합 판정해서는 안 된다.

③ 그래서 고전적 방법은 도구 검사와 사람의 검토를 함께 쓴다

이번 실습에서 확인한 A·E처럼 기계가 쉽게 찾아내는 문제는 자동화하기 좋다. 반면 B·C·D·F는 자동 접근성 도구의 도움을 받더라도 이미지 내용, 화면 표시, 주변 맥락 등을 사람이 살펴야 할 수 있다. Validator 통과는 웹 접근성 전체 통과가 아니다.

④ 이 방식만 반복하면 어떤 점이 불편할까?

방금 한 실습에서실제 작업이 많아지면
A·E를 찾으려고 Validator를 실행했다화면마다 코드를 검사하고 오류 위치를 다시 확인해야 한다.
B·C·D·F는 별도 접근성 검사나 맥락 확인이 남았다도구를 바꾸거나 사람이 반복해서 확인해야 하고, 판단에 시간이 든다.
왜 문제인지 해설을 읽어야 이해할 수 있었다검사 결과를 해당 WCAG 조항·해설·기법과 연결해 찾는 작업이 반복된다.
문구가 적절한지 직접 판단했다서로 다른 검토자가 다른 결론을 내릴 수 있어 판단 조건과 예외를 명시해야 한다.

⑤ 이번 단계에서 얻은 결론

고전적 검사는 필요하다. HTML 문법과 자동으로 확인할 수 있는 접근성 문제를 빠르게 발견해 주기 때문이다. 하지만 같은 기준으로 반복 판정하는 일과 위반에 연결되는 근거를 바로 찾는 일은 여전히 번거롭다.

이 두 가지 불편함이 A1-M2 규칙 설계, A1-M3 규칙 검사기, A1-M5 근거 검색으로 이어지는 출발점이다. 판정 가능한 항목은 명시적인 규칙으로 만들고, 관련 W3C 근거 문서는 TF-IDF·BM25 같은 검색 방법으로 찾아본다. 이미지 의미나 주변 맥락처럼 규칙만으로 결론 내리기 어려운 부분은 그 한계를 남겨 두고 이후 RAG 확장의 필요성을 검토한다.

이번 단계에서는 정밀도·재현율이나 Recall@k를 계산하지 않는다. 먼저 검사 대상, 발견 가능한 오류, 남는 판단 문제를 구분하는 데 집중한다.

⑥ 간단한 이해도 확인 · 다음 모듈로 연결

이 실습의 목적은 WCAG 조항을 외우는 것이 아니라 기존 검사 도구의 입력·출력·판정 범위를 구분하는 것이다. M1-02의 HTML을 다시 보면서 다음 질문에 답해 보자.

질문확인할 관점
Q1. Validator에서 오류가 없으면 그 페이지는 접근성 기준을 모두 충족하는가?HTML 표준 적합성 검사와 WCAG 접근성 평가의 범위를 구분한다.
Q2. alt="이미지"가 형식상 유효해도 문제가 남는 이유는?속성의 존재와 이미지의 실제 의미 전달 여부는 별개다.

Q4. 여러 페이지에서 같은 누락 패턴이 반복된다면 무엇을 자동화할 수 있을까?명확한 조건은 재사용 가능한 Python 규칙으로 정의할 수 있다.
