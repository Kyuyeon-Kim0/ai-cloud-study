A1-M2. CSV로 검사 규칙을 정의하고 웹페이지 자동 검사하기

개발팀이 웹페이지를 출시하기 전에 검사 요청을 보내면, 담당자는 정해진 기준으로 페이지를 확인해 결과를 전달해야 합니다. 이번 모듈에서는 사람이 읽기 쉬운 CSV에 검사 기준을 작성하고, Python이 그 CSV를 직접 읽어 HTML을 검사하는 프로그램을 만듭니다.

이번 모듈의 결과물은 rules.csv(검사 기준) + checker.py(검사기) + results.json(검사 결과)입니다. rule_tree.csv를 추가로 사용하면 업무 분류를 클릭하여 규칙 원본 파일과 정확한 규칙 ID를 찾을 수 있습니다. YAML 변환은 하지 않습니다.

실제 요청 상황부터 이해하기

가상의 쇼핑몰 개발팀이 상품 신청 화면을 만들었습니다. 배포 전 품질 담당자에게 이미지, 링크, 입력창을 검사해 달라고 요청합니다. 품질 담당자는 웹 접근성 기준과 관련된 위험 후보뿐 아니라, 회사에서 별도로 정한 작성 지침도 점검해야 합니다.

예를 들어 <a href="/notice/3">더보기</a>는 주변 문맥을 살펴야 하므로 표준 관련 점검에서는 cantTell이 될 수 있습니다. 그러나 회사가 '더보기' 단독 사용을 금지하면 사내 정책 검사에서는 failed가 됩니다. 두 결과는 서로 다른 기준에 근거하므로 모순이 아닙니다.

업무 순서 — 누가 무엇을 입력하고, 무엇을 얻는가?

이번 모듈에서 하지 않는 일

YAML 생성, 별도 변경 이력 CSV, Git 실습, 임베딩, LLM 호출, 벡터 DB 구축은 하지 않습니다. 규칙 파일이 바뀌면 이전 규칙과 달라질 수 있다는 이력 개념은 이후 Git의 변경 이력 관리와 비슷하다고 이해하면 충분합니다.

우리 검사기는 정적 HTML에 대한 제한된 교육용 규칙 검사기입니다. W3C Validator·axe·공식 WCAG 적합성 평가를 대신하지 않으며, passed는 지금 정의한 검사 항목의 충족만 의미합니다.

A1-M2 · 규칙 원본 설계

02. rules.csv와 향후 RAG 필드 구분

CSV를 선택한 이유는 쉽기 때문만이 아닙니다. 현재는 규칙 실행 데이터로 쓰고, 나중에는 규칙의 의미와 이유를 설명하는 RAG 지식 원본으로 재사용하기 위해서입니다.

CSV 한 행이 의미하는 것

rules.csv의 한 행 = 하나의 검사 규칙입니다. selector는 검사할 HTML 요소를, operator는 Python에 미리 구현해 둔 검사 함수를 선택합니다. 코드 대신 CSV에 임의의 Python 표현식을 넣어 실행하지 않습니다.

규칙 ID검사 대상실행 연산자결과의 의미
IMG-001imghas_attributealt 속성 존재 여부만 확인
LINK-002a[href]link_purpose_review모호한 문구는 cantTell
COMP-LINK-001a[href]clear_link_text회사 금칙어와 일치하면 failed
COMP-LINK-003a[href]clear_link_textproposed라서 판정에는 적용하지 않음

같은 필드를 RAG에 사용할 때는 역할이 달라진다

RAG에서는 CSV 행 전체를 무작정 한 문장으로 합칠 필요가 없습니다. 의미를 검색할 본문(page_content)과 검색 결과를 식별·필터링할 메타데이터(metadata)를 분리하면 됩니다. 실제 변환 코드는 뒤의 정보검색·임베딩·LangChain 모듈에서 다룹니다.

용도CSV 필드왜 이쪽인가?
RAG 검색 본문title, description, reason, limitation사용자의 '왜?' 질문과 의미가 연결되는 문장
RAG 메타데이터rule_id, rule_version, status, scope, policy_id, reference_url, effective_from정확한 규칙 연결·출처 인용·현재 정책만 검색하기 위한 필터
구조화된 조건 메타데이터selector, operator, attribute, values, wcag_ref, kwcag_ref조건 검색·표준 번호 필터·판정기 연계에 활용. 필요하면 특정 값만 검색 본문에 덧붙일 수 있음
트리 메타데이터node_id, parent_id, file, rule_id, path(계산)상위 분류 탐색·원본 CSV 역추적. path는 트리 조회 시 생성 가능

예시: 본문은 '모호한 링크 문구를 제한하는 이유'이고, 메타데이터는 rule_id=COMP-LINK-001, scope=company, status=applied입니다. 공식 표준 관련 조항이 있다는 사실만으로 회사 위반을 WCAG 위반으로 확정해서는 안 됩니다.

규칙 상태와 버전은 왜 필요한가?

샘플에는 적용 상태 applied 7건과 제안 상태 proposed 1건을 넣었습니다. 판정기는 기본적으로 applied만 사용합니다. 훗날 RAG도 '현재 적용 중인 규칙'을 묻는 질문에서는 같은 조건으로 검색해야 합니다. rule_version은 해당 규칙의 버전이며, 현재 실습은 규칙 버전의 날짜별 이력을 별도 테이블로 관리하지 않습니다.

두 번째 CSV: 규칙 트리는 분류·파일·ID만 관리한다

계층형 규칙 목차는 rule_tree.csv에 둡니다. parent_id는 상위 분류, node_type은 폴더 같은 그룹인지 실제 규칙인지 표시하며, 실제 규칙 행은 file과 rule_id로 찾아갑니다.

node_id,parent_id,node_type,label,file,rule_id,sort_order
ROOT,,group,웹 정합성 검사 규칙,,,1
COMP,ROOT,group,회사 작성 정책,,,2
COMP_LINK,COMP,group,링크 작성 규칙,,,1
N_COMP_LINK_001,COMP_LINK,rule,사내 더보기 문구 제한,rules.csv,COMP-LINK-001,1

조회 과정: 트리에서 N_COMP_LINK_001 선택 → file=rules.csv 확인 → 해당 CSV에서 rule_id=COMP-LINK-001 행 검색 → 설명·검사 조건·메타데이터 표시.

현재 두 CSV 모두 규칙의 단일 원본을 중복 생성하지 않습니다. rule_tree.csv는 규칙 내용 대신 참조 주소를 관리합니다. 다른 파일이 추가되는 미래에는 파일 등록·권한 검증이 필요하며, 이번 예제는 안전을 위해 rules.csv만 허용합니다.

A1-M2 · 실행 코드

03. Python으로 CSV를 직접 읽어 HTML 검사하기

규칙이 CSV라는 사실은 실행 코드를 복잡하게 만들지 않습니다. csv.DictReader로 한 행을 딕셔너리로 읽고, Pydantic으로 데이터 계약을 검사한 뒤, 등록된 함수만 호출합니다.

0단계. 실습 파일 준비

파일역할

1단계. CSV의 한 행을 가져온다

import csv

with open("rules.csv", encoding="utf-8-sig", newline="") as f:
    rows = list(csv.DictReader(f))

for row in rows:
    print(row["rule_id"], row["operator"], row["status"])

DictReader는 첫 행의 필드 이름을 딕셔너리 키로 사용합니다. utf-8-sig는 한글 CSV에 BOM이 포함된 경우에도 헤더를 올바르게 읽도록 합니다. values의 더보기|보기|여기는 여러 문자열을 보관하기 위해 이 예제에서 선택한 구분자 표현입니다.

2단계. 데이터 검증 후 적용 중인 규칙만 고른다

from pydantic import BaseModel

class Rule(BaseModel):
    rule_id: str
    selector: str
    operator: str
    status: str

active = [Rule(**row) for row in rows if row["status"] == "applied"]

위 코드는 원리를 보여 주는 축약본입니다. 실제 제공한 checker.py에서는 Literal과 모델 검증으로 허용된 CSS 선택자, 연산자 조합, 필수 필드, 규칙 ID 중복까지 확인한 후 적용 여부를 선택합니다. 따라서 제안 중인 규칙이 실수로 실행되거나 CSV 셀에 적힌 임의 코드가 실행되는 일을 방지합니다.

3단계. HTML을 문자열이 아닌 요소 구조로 검사한다

from bs4 import BeautifulSoup

soup = BeautifulSoup('<img src="a.png"><img src="b.png" alt="">', "html.parser")
for img in soup.select("img"):
    print(img.has_attr("alt"))  # False, True

alt=""는 대체 텍스트 속성이 없는 것이 아니라 빈 문자열로 존재하는 것입니다. 경우에 따라 장식 이미지에 적절할 수 있으므로 속성의 존재 여부와 텍스트 의미 판단을 혼동하지 않습니다.

4단계. CSV의 operator는 허용된 Python 검사 함수만 선택한다

def has_attribute(tag, rule):
    return "passed" if tag.has_attr(rule.attribute) else "failed"

CHECKERS = {"has_attribute": has_attribute}

# CSV의 operator="has_attribute"와 일치하는 함수를 실행한다.
result = CHECKERS[rule.operator](tag, rule)

이것이 규칙 데이터와 실행 코드를 분리한다는 의미입니다. 지원하지 않는 새로운 판정 조건을 구현하려면 Python 검사 함수를 추가해야 하지만, 이미 지원하는 금칙어 목록의 변경은 CSV만 수정하면 됩니다.

5단계. 검사 결과를 JSON으로 기록한다

{
  "target": "L02",
  "rule_id": "COMP-LINK-001",
  "rule_version": "1.0.0",
  "scope": "company",
  "outcome": "failed",
  "source_file": "rules.csv",
  "reason": "링크 텍스트만 읽어도 이동 목적이 명료해야 한다는 사내 작성 정책이다."
}

위 JSON은 중요한 필드만 보여 주는 예시이며 실제 results.json에는 관련 출처·한계 등의 필드도 들어갑니다. JSON은 페이지를 검사한 결과 데이터이고 CSV는 기준이 된 규칙 원본입니다.

6단계. 트리 CSV의 file 필드로 원본 규칙을 다시 찾는다

# tree_lookup.py의 핵심 논리 (축약)
node = next(n for n in tree_rows if n["node_id"] == "N_COMP_LINK_001")
assert node["file"] == "rules.csv"  # 허용된 파일만 열도록 검증

rule = next(r for r in rule_rows if r["rule_id"] == node["rule_id"])
print(rule["title"], rule["reason"])

이 구조가 있으면 규칙을 2번 복사하지 않고도 상위 분류를 여러 단계로 탐색할 수 있습니다. 실제 코드에는 잘못된 부모 참조·순환 참조·중복 ID·허용되지 않은 파일 경로를 검증하는 로직을 넣었습니다.

04. CSV 샘플 화면 — 트리에서 규칙 찾아보기

아래는 제공되는 rule_tree.csv와 rules.csv의 실제 샘플 데이터를 연결한 동작형 탐색 화면입니다. 왼쪽에서 업무 분류를 펼치고 규칙을 선택하면, 오른쪽에서 file·rule_id에 맞는 원본 CSV 행과 RAG 본문·메타데이터 필드를 확인할 수 있습니다.

A1-M2 · 이해도 테스트·추가 실습

06. 이해도 테스트 · 응용 실습 · GPT 검토

규칙 검사기가 어떤 업무를 해결하는지, CSV 두 개가 서로 다른 책임을 갖는지, 검색용 지식 원본과 검사 결과가 어떻게 다른지 확인합니다.

이해도 테스트

1. rules.csv와 rule_tree.csv를 둘 다 사용하는 이유는?

정답: 규칙 내용은 하나의 rules.csv에 두고, 트리는 parent_id 계층·파일 위치·규칙 식별자를 제공하는 목차만 담당하기 때문입니다.

2. tree의 file=rules.csv, rule_id=COMP-LINK-001은 무엇을 뜻하나?

정답: 해당 원본 CSV를 연 뒤 동일한 rule_id를 가진 행을 정확히 검색하라는 참조 정보입니다.

3. 적용 상태가 proposed인 규칙을 검사기에 바로 적용해야 할까?

정답: 아닙니다. 현재 적용 중인 applied만 검사 대상으로 선택합니다.

4. RAG에서 reason과 rule_id는 같은 역할일까?

정답: 아닙니다. reason은 검색 본문이고 rule_id는 출처 연결·정확 검색용 메타데이터에 적합합니다.

5. alt 속성이 존재하면 WCAG 준수가 확정될까?

정답: 아닙니다. 이 예제의 IMG-001은 단지 속성 존재만 검사합니다.

6. CSV의 operator가 신규 함수 이름이면 무엇을 해야 하나?

정답: 기존에 허용된 연산자가 아니라면 Python 검사 함수를 새로 구현하고 검증 계약에 등록해야 합니다. 임의 실행은 금지합니다.

응용 실습 1. 새로운 규칙을 트리에 연결하기

  1. 기존 규칙 ID와 중복되지 않는 사내 규칙을 rules.csv에 한 행 추가합니다.
  2. 적절한 상위 분류의 parent_id 아래에 트리 leaf 한 행을 추가합니다.
  3. 해당 트리 leaf의 file=rules.csv와 새 rule_id를 채웁니다.
  4. python tree_lookup.py --node 새노드ID로 연결을 확인합니다.
  5. 규칙의 status를 proposed로 두고 판정에서 제외되는지 확인합니다.

응용 실습 2. 한 행을 검색 본문·메타데이터로 나눠 보기

rule = next(r for r in rows if r["rule_id"] == "COMP-LINK-001")

page_content = "\n".join([rule["title"], rule["description"], rule["reason"], rule["limitation"]])
metadata = {k: rule[k] for k in ["rule_id", "rule_version", "scope", "status", "reference_url"]}
print(page_content)
print(metadata)

이번에는 데이터가 두 종류로 나뉜다는 사실만 확인합니다. 실제 임베딩·LangChain Document 변환은 A2·A3에서 진행합니다.
