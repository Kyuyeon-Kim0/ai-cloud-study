Part 0. 왜 벡터 DB인가 · A3-M0

00. 벡터 DB가 필요한 이유 — 단어가 아니라 뜻으로 찾기

벡터 DB는 문장·이미지 같은 데이터를 숫자 벡터(임베딩)로 저장하고, ‘뜻이 가까운 것’을 빠르게 찾아 주는 저장소입니다. RAG에서 질문에 맞는 근거 문서를 찾는 일, 추천에서 비슷한 상품을 찾는 일이 모두 벡터 검색입니다.

이 모듈에서 할 일

A3 과정(토크나이저 → FAISS → Chroma → pgvector·Qdrant)에 들어가기 전에 큰 그림을 잡습니다. 벡터 DB가 무엇을 해결하는지, 안에 어떤 부품이 있는지, 어떤 종류가 있고 요즘 어디로 가고 있는지, 무엇을 기준으로 고르는지를 표와 그림으로 정리합니다. 코드는 없습니다.

02. 근사 검색(ANN) 인덱스 — 덜 비교하기와 작게 저장하기

문서가 많아지면 전부 비교(Flat)할 수 없습니다. 벡터 DB의 인덱스는 두 방향으로 이 문제를 풉니다. 덜 비교하기(묶어 두거나 이어 두고 일부만 보기)와 작게 저장하기(벡터 압축). 대신 정답 일부를 놓칠 수 있어 ‘근사(Approximate)’ 검색이라 부릅니다.

인덱스 계보
방향인덱스아이디어손잡이쓰는 곳
기준Flat전부 비교 (정확 100%)—작은 데이터, 정답 측정
덜 비교IVFK-means로 묶고 가까운 묶음 몇 개만nlist · nprobeFAISS, pgvector(ivfflat), OpenSearch, Milvus
덜 비교HNSW이웃끼리 이은 층층 그래프를 따라감M · ef_construction · ef_search거의 모든 벡터 DB의 기본
덜 비교DiskANN 계열그래프를 SSD에 두고 일부만 메모리에그래프 차수 · 탐색 폭Milvus, 대규모·저메모리

03. 밀집 벡터, 희소 벡터, 그리고 하이브리드 검색

‘벡터’에는 두 종류가 있습니다. 임베딩 모델이 만드는 밀집(dense) 벡터와, 단어마다 칸이 하나인 희소(sparse) 벡터. 키워드 검색(BM25)도 희소 벡터의 일종으로 볼 수 있어, 요즘 벡터 DB는 둘을 한 번에 다룹니다.

희소 (BM25 · TF-IDF · SPLADE)밀집 (e5 · OpenAI · BGE …)
모양수만 차원, 대부분 0384~3,072차원, 모든 칸에 값
강점정확한 단어·코드·숫자다른 표현, 같은 뜻
약점동의어·말투희귀 고유명사·모델명
인덱스역색인HNSW·IVF

04. 벡터 검색 도구의 다섯 갈래

벡터 검색을 제공하는 도구는 출발점에 따라 다섯 갈래로 나뉩니다. 같은 HNSW를 쓰더라도 갈래마다 잘하는 일과 운영 방식이 다릅니다.

다섯 갈래 지도
갈래대표한 줄 정의강점약점
① 라이브러리FAISS, hnswlib, ScaNN프로그램 안에서 쓰는 인덱스 코드가장 빠르고 자유로움저장·필터·운영은 직접
② 전용 벡터 DBQdrant, Milvus, Weaviate, Chroma, Pinecone벡터 검색만을 위해 만든 DB필터·양자화·확장 기능이 깊음DB를 하나 더 운영
③ 범용 DB의 벡터 기능pgvector(PostgreSQL), MongoDB Atlas Vector Search, Oracle AI Vector Search, SQL Server 2025, Redis이미 쓰는 DB에 벡터 열·인덱스 추가SQL·트랜잭션·JOIN·백업 재사용아주 큰 규모·복잡한 필터에서 한계
④ 검색엔진의 벡터 기능OpenSearch, Elasticsearch, Vespa키워드 검색엔진에 벡터 필드 추가하이브리드 검색, 집계, 대규모 운영설정이 많고 무거움

06. 요즘 벡터 DB는 어디로 가고 있나

2023년의 ‘벡터 DB 붐’ 이후 2025~2026년에는 방향이 꽤 분명해졌습니다. 공식 발표로 확인되는 변화를 여섯 가지로 묶었습니다.

06-1. ① 압축(양자화)이 기본값이 되다

무엇내용출처

공통 방식은 ‘메모리에는 아주 작게 압축한 벡터로 후보를 넉넉히 뽑고, 원본 벡터로 다시 계산(rescoring)’입니다. A3-M2에서 본 PQ·SQ와 재정렬의 연장선입니다.

06-4. ④ 하이브리드 검색이 기본

BM25 + 벡터 + 메타데이터 필터를 한 질의에서 섞고 RRF·리랭커로 순서를 정하는 방식이 주요 제품의 기본 기능이 되었습니다. 순수 벡터 검색만으로 운영하는 경우는 줄어드는 흐름입니다.

06-5. ⑤ 기존 DB·검색엔진으로 수렴

pgvector(0.8.2, 2026.2), OpenSearch·Elasticsearch, MongoDB·Oracle·SQL Server·Redis 등 이미 쓰는 시스템이 벡터 기능을 갖추면서 ‘벡터 DB를 따로 두지 않는’ 선택이 늘었습니다. 전용 벡터 DB는 대규모·저지연·복잡한 필터처럼 전문성이 필요한 영역으로 자리를 옮기는 중이라는 분석이 많습니다(시장 분석 글들의 공통 의견이며 수치로 확정된 사실은 아님).

08. 정리 — 벡터 DB 한 장

다음 모듈부터는 직접 코드를 돌립니다. A3-M1에서 벡터를 만들고, M2에서 인덱스의 원리를, M3·M4에서 DB 운영을 익힌 뒤 OpenSearch로 이어집니다.

  1. 벡터 DB = 임베딩 · 저장 · 인덱스 · 필터 · 운영 다섯 부품.
  2. 인덱스는 덜 비교하기(IVF·HNSW)와 작게 저장하기(SQ·PQ·BQ)의 조합이고, 손잡이(nprobe·ef_search·압축률)로 정확도와 속도를 바꾼다.
  3. 키워드와 벡터는 보완 관계 — 하이브리드 검색이 기본.
  4. 다섯 갈래: 라이브러리 · 전용 DB · 범용 DB 확장 · 검색엔진 · 오브젝트 스토리지. 이미 가진 시스템에서 출발한다.
  5. 추세: 양자화 기본화, 디스크·오브젝트 스토리지, 필터 정확도, 하이브리드, 기존 DB로 수렴, 임베딩·GPU 내장.
